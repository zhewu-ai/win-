# QA M12：工作日历基础体验返修

日期：2026-08-09

## 一、结论

当前工作日历已经勉强跑起来，但基础体验仍有 5 个必须返修的问题。本轮不要再扩 AI、快速录入或复杂功能，只修这些影响实际使用的基础体验。

目标：

1. 项目可以完整管理：新建、编辑、归档/删除。
2. 页面去掉教学式解释文案。
3. 添加排期时取消“连续节点/单日节点”的心智负担。
4. 周视图和今日视图重新排版，不要全部挤在顶部。
5. 从日历里的便签链接进入便签后，必须能返回工作日历上下文。

## 二、问题与返修要求

### 2.1 项目管理缺失

现状：

- 目前只有“新建项目”。
- 没有明显的“删除项目”或“减少项目”入口。
- 项目多了以后无法清理，会越来越乱。

要求：

- 项目必须支持编辑名称/颜色/时间。
- 项目必须支持归档。
- 项目必须支持删除或软删除。
- 删除/归档入口可以放在项目详情右侧面板中，不要放在顶部挤占空间。

建议交互：

- 点击项目 chip 或项目名称，右侧显示项目详情。
- 右侧项目详情底部提供：
  - 编辑项目
  - 归档项目
  - 删除项目

删除规则：

- 优先软删除。
- 删除项目前要有确认。
- 如果项目下已有排期，确认文案要说明“该项目下排期也会从当前视图隐藏/删除”。
- 更稳妥的默认操作是“归档”，删除作为二级危险操作。

验收：

- 新建项目后可以编辑。
- 项目可以归档，归档后不出现在当前项目筛选区。
- 项目可以删除，删除后刷新页面不再出现。
- 删除/归档后月/周/今日视图同步更新。

### 2.2 解释性词语过多

现状：

- 页面上出现很多解释性文案，例如：
  - “添加连续阶段和单日节点，保存后写入数据并在日月今日同步显示”
  - “点月周今日任意一条，可修改保存后会写入……”
- 这些文案像产品说明书，不像正式工具界面。

要求：

- 删除所有教学式、解释式、实现说明式文案。
- 页面只保留必要标签和状态。
- 不在界面上解释“保存后会写入数据库”“三视图同步”等内部机制。

保留示例：

- 工作日历
- 今日
- 月
- 周
- 新建项目
- 添加排期
- 项目
- 开始日期
- 结束日期
- 关联便签
- 保存
- 删除
- 归档

删除示例：

- “保存后写入数据并在日月今日同步显示”
- “点月周今日任意一条，可修改保存后会写入……”
- “先把基础日历样式和手动添加闭环做清楚……”
- “快速录入不是主流程……”

验收：

- 页面不出现开发解释、验收解释、教学说明。
- 用户不需要读大段文字，也能看出可操作入口。
- 界面看起来像正式产品，不像 demo。

### 2.3 取消“连续节点 / 单日节点”的显式类型

现状：

- 添加时要求用户选择“连续阶段 / 单日节点”。
- 用户理解成本高，而且没有必要。

产品判断：

- 一个排期是否连续，应由日期范围决定。
- 开始日期 = 结束日期，就是单日事项。
- 开始日期 < 结束日期，就是连续事项。
- 不需要让用户额外理解“节点类型”。

要求：

- 表单里删除“类型：连续阶段 / 单日节点”字段。
- 只保留：
  - 标题
  - 项目
  - 开始日期
  - 结束日期
  - 关联便签
  - 状态
- 系统根据日期自动判断展示方式：
  - `startDate === endDate`：按单日节点显示。
  - `startDate < endDate`：按连续阶段显示。

数据层处理：

- 如果当前数据库仍有 `type` 字段，可以保留内部字段，但前端不暴露给用户。
- 保存时自动写：
  - 日期相同：`type = "node"`
  - 日期不同：`type = "range"`
- 后续如果要保留不同视觉语义，可在内部处理，不增加用户负担。

验收：

- 添加排期时看不到“连续阶段/单日节点”选择器。
- 只填一天，月/周/今日按单日显示。
- 填多天，月/周/今日按连续条显示。
- 修改结束日期后，展示类型自动变化。

### 2.4 周视图和今日视图排版太挤

现状：

- 周视图和今日视图内容挤在顶部一小块。
- 页面下方大量空间没被利用。
- 看起来不像工作空间，更像一组压缩列表。

要求：

#### 周视图

- 周视图必须充分使用垂直空间。
- 七列应该撑满主体区域。
- 每天是一列，每列内部有足够留白。
- 每个事项用卡片显示，不要压成过小 chip。
- 空白日期列可以保持干净，不要挤在顶部。

建议布局：

```text
周一 10      周二 11      周三 12 ...
┌────────┐  ┌────────┐
│ A 修改  │  │ A 修改  │
│ 阶段中  │  │ 阶段中  │
└────────┘  └────────┘

页面高度尽量铺满，不要只占顶部一小段。
```

#### 今日视图

今日视图应像工作台，不是小列表。

分区：

- 今天要做
- 今天节点
- 今天编辑的便签

每个分区可以用卡片/分栏承载，充分利用主区域宽度和高度。

要求：

- 不要所有内容都挤在左上角。
- 信息卡片要有稳定宽度。
- 空状态要干净。
- 今天要做的内容优先级最高。

验收：

- 1440px 桌面宽度下，周视图和今日视图不只占顶部 20% 高度。
- 320px/390px 下不横向溢出。
- 周视图能一眼看出一周每天有什么。
- 今日视图能一眼看出今天要做什么、今天有什么节点、今天改了什么便签。

### 2.5 从日历便签链接进入后缺少返回

现状：

- 在“今日”里点击便签后，会进入便签。
- 进入后没有类似内链跳转的“返回上一级”层级导航。
- 用户无法顺畅回到刚才的工作日历位置。

要求：

- 日历进入便签应接入现有“内部链接返回栈”或等价返回机制。
- 从日历的便签链接打开便签后，编辑器顶部应显示返回入口。
- 返回入口文案建议：
  - 返回工作日历
  - 或 返回 8月9日 今日
  - 或 返回上一层

行为：

1. 用户在工作日历今日视图点击某条便签。
2. 右侧打开便签编辑器。
3. 顶部出现返回入口。
4. 点击返回后，回到工作日历，并保持之前的视图上下文：
   - 如果从今日视图进入，返回今日视图。
   - 如果从周视图进入，返回周视图。
   - 如果从月视图进入，返回月视图。

实现建议：

- 复用 M11 内链返回栈思路。
- 当前 `page.tsx` 已有便签内链返回栈，不要另起一套割裂逻辑。
- 可新增一个 `calendarReturnState`：
  - `view`
  - `date`
  - `projectFilter`
  - `selectedProjectId`
- 从日历打开便签时，保存该状态。
- 编辑器顶部返回按钮点击后，恢复 `calendarOpen=true` 与对应日历状态。

验收：

- 从今日视图便签链接进入便签后，可以返回今日视图。
- 从周视图便签链接进入便签后，可以返回周视图。
- 返回后筛选状态不丢。
- 返回后不会新开页面，不跳独立 `/calendar`。

## 三、本轮不做

- 不做 AI 导入。
- 不做 Excel/PDF/图片识别。
- 不做复杂快速录入。
- 不做提醒通知。
- 不做多人协作。
- 不做拖拽调整排期。
- 不做新的大范围数据模型重构。
