# M13 AI 识别模型拆分选型报告

日期：2026-08-10

## 一、结论

建议将 M13 AI 排期导入拆成两套模型配置：

- Excel 导入：`Qwen/Qwen3-30B-A3B-Instruct-2507`
- 图片导入：`Qwen/Qwen3-VL-32B-Instruct`

原因：Excel 文件在后端已经被 SheetJS 转成结构化文本，不需要多模态模型；图片上传才需要视觉理解能力。拆分后可以同时降低 Excel 成本、缩短 Excel 超时风险，并让图片识别使用更适合视觉 OCR/表格理解的模型。

## 二、当前问题

当前默认模型为 `Qwen/Qwen3.5-9B`。同一份 `HW V+ ID视频-时间表0802.xlsx` 实测：

- 文件读取：约 1ms
- Excel 转结构化文本：约 15ms
- 等待模型返回：约 61.9s 到 66.4s
- 当前代码超时阈值：60s

因此主要耗时不在本地读取、解析 Excel 或网络握手，而是在远端模型排队/生成阶段。该模型经常接近或超过 60s 超时线，用户体验不稳定。

## 三、为什么 Excel 选 `Qwen/Qwen3-30B-A3B-Instruct-2507`

### 3.1 Excel 不需要多模态

当前 Excel 链路不是把 Excel 当图片传给模型，而是先转成文本：

- 文件名
- Sheet 名
- 合并单元格
- 非空单元格坐标和值

所以 Excel 识别本质是「结构化文本 -> 排期 JSON」，更适合文本模型，不需要视觉模型。

### 3.2 实测速度更快

同一份 Excel 转文本输入下：

| 模型 | 耗时 | 输出情况 | 判断 |
|---|---:|---|---|
| `Qwen/Qwen3-30B-A3B-Instruct-2507` | 27.5s | 1 项目 / 27 条 | 推荐 |
| `zai-org/GLM-4.5-Air` | 37.8s | 1 项目 / 25 条 | 备选 |
| 当前 `Qwen/Qwen3.5-9B` | 61.9s | 1 项目 / 25 条 | 慢，容易超时 |
| `DeepSeek-V3.2` | 99.1s | 1 项目 / 29 条 | 太慢 |
| `MiniMaxAI/MiniMax-M2.5` | 104.3s | 1 项目 / 26 条，含 reasoning | 太慢 |
| `moonshotai/Kimi-K2.7-Code` | 109.2s | 1 项目 / 33 条，含 reasoning | 太慢 |
| `deepseek-ai/DeepSeek-V4-Flash` | >120s | 未返回，被中止 | 不适合 |

`Qwen/Qwen3-30B-A3B-Instruct-2507` 相比当前模型，耗时从约 62s 降到约 28s，能明显避开 60s 超时线。

### 3.3 成本更低

按硅基流动公开价格页与本次 token usage 粗算：

- 当前 `Qwen/Qwen3.5-9B`：约 ¥0.030/次
- `Qwen/Qwen3-30B-A3B-Instruct-2507`：约 ¥0.006/次

Excel 默认模型切换后，单次成本约降到当前方案的五分之一。

### 3.4 体验更稳定

该模型本次未返回 `reasoning_content`，没有出现大量 reasoning token 消耗；同时支持 JSON mode，能直接配合当前 `response_format: { type: "json_object" }` 的结构化输出链路。

## 四、为什么图片选 `Qwen/Qwen3-VL-32B-Instruct`

### 4.1 图片需要视觉理解，不适合纯文本模型

图片导入场景需要模型完成：

- OCR
- 表格结构理解
- 日期与任务对应关系识别
- 排期节点抽取
- JSON 草稿生成

因此图片应使用 VLM 多模态模型，而不是 Excel 的纯文本模型。

### 4.2 实测质量更稳

将同一份 Excel 渲染成排期表 PNG 后，用图片输入测试：

| 模型 | 耗时 | 输出情况 | 判断 |
|---|---:|---|---|
| `Qwen/Qwen3-VL-32B-Instruct` | 36.5s | 1 项目 / 23 条 | 推荐 |
| `Qwen/Qwen3-VL-30B-A3B-Instruct` | 16.7s | 1 项目 / 9 条 | 快，但漏识别明显 |
| `Qwen/Qwen3-VL-8B-Instruct` | 58.1s | 打满 4096 输出 token，未完成 | 不稳 |
| `PaddlePaddle/PaddleOCR-VL-1.5` | 2.6s | 未形成可用排期 JSON | 不适合端到端 |
| `zai-org/GLM-4.5V` | 不适配当前 JSON mode；此前文本测 89.5s 且含大量 reasoning | 不建议 |

`Qwen/Qwen3-VL-30B-A3B-Instruct` 虽然最快，但漏识别太多；图片导入更依赖识别质量，默认模型应优先选更稳的 `Qwen/Qwen3-VL-32B-Instruct`。

### 4.3 成本仍可控

`Qwen/Qwen3-VL-32B-Instruct` 比 30B-A3B 视觉模型更贵一些，但图片导入频率通常低于 Excel 导入，且它显著降低漏识别风险。对用户体验而言，图片场景更应该优先保证可用性和准确率。

## 五、代码改造建议

建议新增两个环境变量：

```env
SILICONFLOW_EXCEL_MODEL="Qwen/Qwen3-30B-A3B-Instruct-2507"
SILICONFLOW_IMAGE_MODEL="Qwen/Qwen3-VL-32B-Instruct"
```

保留旧变量作为兼容兜底：

```env
SILICONFLOW_MODEL="Qwen/Qwen3.5-9B"
```

选择逻辑：

- `kind === "excel"`：优先使用 `SILICONFLOW_EXCEL_MODEL`
- `kind === "image"`：优先使用 `SILICONFLOW_IMAGE_MODEL`
- 未配置时再回退到 `SILICONFLOW_MODEL`

## 六、重要兼容风险

当前代码按 `/Qwen3/i` 一刀切传：

```ts
enable_thinking: false
```

但 `Qwen/Qwen3-VL-8B-Instruct`、`Qwen/Qwen3-VL-30B-A3B-Instruct`、`Qwen/Qwen3-VL-32B-Instruct` 在硅基流动接口上会报错：

```text
current model does not support parameter `enable_thinking`
```

因此不能只改模型名。技术部需要把参数逻辑改成按模型能力配置，至少做到：

- `Qwen/Qwen3.5-9B`：传 `enable_thinking: false`
- `Qwen3-VL-*-Instruct`：不要传 `enable_thinking`
- 明确带 `Thinking` 的模型：默认不要用于该功能

## 七、验收建议

模型切换后至少复测：

1. Excel 样本 `HW V+ ID视频-时间表0802.xlsx`：耗时应稳定低于 45s，不能触发 60s 超时。
2. Excel 输出项目名、主要阶段、日期范围应可用；允许用户在预览中修正少量拆分差异。
3. 图片样本应输出可编辑草稿，不应返回空 JSON 或打满 token。
4. 日志继续只记录模型、耗时、token、项目数、条目数、warnings 数，不打印 key、base64、文件全文或明文草稿。
5. 前端 usage 展示应能区分 Excel 模型和图片模型，便于后续继续 A/B。

## 八、最终建议

短期推荐：

- Excel：`Qwen/Qwen3-30B-A3B-Instruct-2507`
- 图片：`Qwen/Qwen3-VL-32B-Instruct`

中期可继续 A/B：

- 图片如果更重视速度，可灰度测试 `Qwen/Qwen3-VL-30B-A3B-Instruct`，但必须增加漏识别检查。
- Excel 可保留 `zai-org/GLM-4.5-Air` 作为备用模型，但它不支持当前 JSON mode，需要单独兼容输出解析。
