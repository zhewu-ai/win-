# SPEC M13：AI 排期导入完整执行方案

日期：2026-08-10

## 一、目标

在 M12 工作日历基础功能稳定后，接入硅基流动 AI，先跑通“图片 / Excel 排期导入”的测试闭环。

本轮目标不是做复杂自动化，而是验证：

1. 用户上传真实排期图片或 Excel。
2. AI 识别并生成可编辑排期草稿。
3. 用户确认/修改草稿。
4. 系统把确认后的草稿写入工作日历。
5. 月视图、周视图、今日视图能看到导入结果。

## 二、范围

### 2.1 本轮支持

1. 图片导入：
   - `png`
   - `jpg/jpeg`
   - `webp` 可选
2. Excel 导入：
   - 第一优先级：`xlsx`
   - `xls` 可选，若成本高可暂缓
3. AI 生成结构化草稿。
4. 草稿预览、编辑、删除。
5. 用户确认后写入 `WorkProject` / `WorkScheduleItem`。
6. 记录调用耗时、token usage、估算成本。

### 2.2 本轮不做

1. 不支持 PDF。
2. 不支持 Word。
3. 不支持多文件批量导入。
4. 不做后台自动识别。
5. 不做 AI 直接写入正式日历。
6. 不做 AI 自动覆盖已有排期。
7. 不做复杂对话式项目管理。
8. 不做拖拽、提醒、多人协作。

## 三、模型与密钥

### 3.1 模型

测试阶段模型：

```text
Qwen/Qwen3.5-9B
```

使用原因：

- 已用真实排期图片测试过，转写准确率可接受。
- 成本、速度、能力适合第一版排期识别。
- 任务主要是识别排期、整理日期和输出 JSON 草稿，不需要更大模型。

### 3.2 环境变量

必须使用环境变量：

```env
SILICONFLOW_API_KEY=由部署环境配置
SILICONFLOW_MODEL=Qwen/Qwen3.5-9B
```

要求：

- `.env.example` 只写变量名，不写真实 key。
- 本地 `.env.local` 可配置测试 key，但不得提交。
- 服务器通过服务环境变量配置。
- 代码、文档、commit、截图、日志、交付报告中都不得出现真实 key。
- 全量测试/生产验证前会更换新的 key。

## 四、产品原则

AI 不负责“操作页面”。AI 只负责把文件识别成结构化草稿。

正确流程：

```text
上传图片 / Excel
→ 后端构造 AI 输入
→ Qwen/Qwen3.5-9B 输出 JSON 草稿
→ 后端校验和规范化
→ 前端展示导入预览
→ 用户修改确认
→ 写入正式工作日历
```

禁止流程：

```text
上传文件
→ AI 直接创建正式项目和排期
```

AI 结果必须经过用户确认。

## 五、上传体验

### 5.1 入口

入口建议放在工作日历右侧面板或顶部次级操作区。

建议文案：

```text
导入排期
[ 上传图片 ] [ 上传 Excel ]
```

要求：

- 不要支持 PDF。
- 不要把 AI 导入做得比“手动添加”更抢眼。
- 手动添加仍是第一主流程。
- AI 导入是辅助生成草稿。

### 5.2 上传限制

建议限制：

- 图片：≤ 8 MB。
- Excel：≤ 5 MB。
- 单次只允许一个文件。

错误提示：

- PDF：`暂不支持 PDF，请上传图片或 Excel。`
- 文件过大：`文件过大，请压缩后重试。`
- 类型不支持：`仅支持图片和 Excel。`
- AI 失败：`识别失败，请换一张更清晰的图片或手动添加。`

### 5.3 状态

上传中：

- 显示“识别中”。
- 禁止重复上传。
- 不要卡死页面。

识别成功：

- 进入导入预览。

识别失败：

- 显示失败原因。
- 保留重新上传入口。

## 六、AI 输入构造

### 6.1 图片

图片直接传给硅基流动多模态接口。

后端处理：

1. 校验文件类型和大小。
2. 读取图片为 base64 或可访问 URL。
3. 调用 `/chat/completions`。
4. 要求模型只输出 JSON。

### 6.2 Excel

Excel 不写死业务识别规则。

程序只负责把 Excel 转成 AI 可读材料，不负责判断排期含义。

应提取：

- 文件名。
- sheet 名。
- 非空单元格文本。
- 单元格坐标。
- 日期值。
- 合并单元格范围。
- 必要时保留行列结构。

建议给 AI 的文本结构：

```text
文件：xxx.xlsx
Sheet：MG视频
合并单元格：
- C28:F28 = 动态打光渲染合成制作
表格内容：
- B8 = Project/ Date
- C8 = 2026-06-15
- D8 = 2026-06-16
- C11 = 模型资产整理
...
```

AI 负责判断：

- 项目名称。
- 阶段名称。
- 单日节点。
- 开始日期。
- 结束日期。

## 七、统一草稿格式

后端必须把 AI 输出规范化成统一草稿。

```ts
type CalendarImportDraft = {
  projects: Array<{
    tempId: string;
    name: string;
    colorKey?: "blue" | "red" | "green" | "purple" | "gray";
  }>;
  items: Array<{
    tempId: string;
    projectTempId: string;
    title: string;
    startDate: string; // YYYY-MM-DD
    endDate: string;   // YYYY-MM-DD
    note?: string;
    confidence?: number;
    sourceRef?: string;
  }>;
  warnings: string[];
};
```

注意：

- 前端不显示“连续阶段 / 单日节点”类型。
- `startDate === endDate`：确认入库时内部保存为 `type=node`。
- `startDate < endDate`：确认入库时内部保存为 `type=range`。
- 日期必须是 `YYYY-MM-DD`。
- 不确定项必须进入 `warnings` 或降低 `confidence`。

## 八、提示词要求

系统提示词必须强调：

```text
你是排期表识别助手。请从用户提供的图片或表格文本中提取项目排期。
只输出 JSON，不输出解释。
日期必须输出 YYYY-MM-DD。
如果某个任务跨多天，输出 startDate 和 endDate。
如果只发生一天，startDate 和 endDate 相同。
不要编造日期。
不确定时写入 warnings，并降低 confidence。
输出必须符合 CalendarImportDraft。
```

禁止让模型输出大段解释文字。

## 九、API 设计

### 9.1 解析上传

```text
POST /api/calendar-imports/parse
```

请求：

- `multipart/form-data`
- `file`: 图片或 Excel
- `kind`: `image | excel`

权限：

- 仅管理员。
- 未登录 401。
- 普通用户 403。

返回：

```json
{
  "ok": true,
  "draft": {
    "projects": [],
    "items": [],
    "warnings": []
  },
  "usage": {
    "model": "Qwen/Qwen3.5-9B",
    "promptTokens": 0,
    "completionTokens": 0,
    "durationMs": 0
  }
}
```

失败：

```json
{
  "ok": false,
  "error": "AI_PARSE_FAILED",
  "message": "识别失败，请换一张更清晰的图片或手动添加。"
}
```

### 9.2 确认导入

```text
POST /api/calendar-imports/confirm
```

请求：

```json
{
  "draft": {
    "projects": [],
    "items": []
  }
}
```

行为：

1. 后端再次校验所有字段。
2. 创建缺失项目。
3. 创建排期条目。
4. 写入 `source=ai_import`。
5. 返回创建数量。

返回：

```json
{
  "ok": true,
  "created": {
    "projects": 1,
    "items": 8
  }
}
```

## 十、导入预览 UI

识别成功后必须进入“导入预览”，不能直接入库。

导入预览至少支持：

- 修改项目名。
- 修改排期标题。
- 修改开始日期。
- 修改结束日期。
- 删除某条草稿。
- 删除某个项目草稿。
- 确认导入。
- 取消导入。

低置信度项：

- 标出“请确认”。
- 不要用大段 AI 解释。

建议结构：

```text
导入预览

项目：HUAWEI Laputa MG

8/24 - 8/27  动态打光渲染
8/29         A call
8/31         下月计划

[取消] [确认导入]
```

## 十一、写入规则

确认导入后：

- 每个项目写入 `WorkProject`。
- 每个条目写入 `WorkScheduleItem`。
- `source = "ai_import"`。
- `type` 由日期自动推导：
  - 同一天：`node`
  - 多天：`range`

不做自动去重第一版可以接受，但如果实现成本低，建议：

- 同项目、同标题、同开始日期、同结束日期的条目提示可能重复。
- 由用户确认是否导入。

## 十二、安全与日志

禁止：

- 打印 API Key。
- 打印完整图片 base64。
- 打印完整用户文件内容到生产日志。
- AI 返回后不校验直接入库。

允许记录：

- 模型名称。
- 调用耗时。
- token usage。
- 识别成功/失败。
- 草稿项目数。
- 草稿条目数。

## 十四、验收标准

### 14.1 图片导入

必须通过：

- 上传图片成功。
- AI 返回草稿。
- 草稿中至少识别出项目名。
- 草稿中至少识别出 3 条排期。
- 日期格式为 `YYYY-MM-DD`。
- 用户可编辑草稿。
- 用户可删除草稿条目。
- 确认后写入工作日历。
- 月/周/今日能看到导入结果。
- 刷新页面后数据仍存在。

### 14.2 Excel 导入

必须通过：

- 上传 `.xlsx` 成功。
- 能识别 sheet 中的项目/阶段/节点。
- 能生成可编辑草稿。
- 至少从每个测试 Excel 中识别出 3 条以上排期。
- 用户确认后写入工作日历。
- 月/周/今日能看到导入结果。
- 刷新页面后数据仍存在。

### 14.3 PDF 拒绝

必须通过：

- 上传 PDF 时明确提示“不支持 PDF，请上传图片或 Excel”。
- 不调用 AI。
- 不静默失败。

### 14.4 权限

必须通过：

- 管理员可导入。
- 普通用户看不到导入入口。
- 普通用户直接调用 API 返回 403。
- 未登录返回 401 或现有登录拦截行为。

### 14.5 密钥保护

必须通过：

- 仓库中没有真实 API Key。
- `.env.example` 只有变量名。
- 日志中没有真实 API Key。
- 交付报告没有真实 API Key。

### 14.6 成本与速度

交付报告必须记录：

- 图片样本识别耗时。
- Excel 样本识别耗时。
- token usage。
- 单次估算成本。
- 失败样本和失败原因。

第一版不要求 100% 准确。重点是流程跑通和评估人工修正成本。
