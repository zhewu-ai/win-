## 3. 临时密码提示（mustChangePassword）

### 3.1 数据模型
`User.mustChangePassword Boolean @default(false)`。`prisma db push` 非破坏性加列，既有 8 个真实用户默认 `false`，不受影响。

### 3.2 API 行为
- `GET/PATCH /api/auth/me` → 返回 `mustChangePassword`。
- `PATCH /api/admin/users/:id/password`（管理员重置）→ 成功后 `mustChangePassword=true`。
- `POST /api/auth/change-password`（用户改密）→ 成功后 `mustChangePassword=false`。
- `POST /api/auth/reset-password`（邮件重置）→ 成功后 `mustChangePassword=false`（用户自设新密码，不再要求再改）。

### 3.3 界面
`MustChangePasswordBanner` 挂在受保护布局，所有已认证页面可见：

- 自取 `/api/auth/me`，`mustChangePassword=true` 时显示固定顶栏轻提示条（不遮内容，z-40，低于弹窗 z-50）。
- 「去修改」→ 打开既有 ChangePasswordModal；改密成功关闭弹窗后重新取 me → 提示条消失。
- 右上 × 可关闭本次会话；窗口 focus 时自动刷新，覆盖「从账号菜单改密成功后提示条同步消失」的场景。
- 不强制跳转、不阻塞数据查看（SPEC §5.1.1.4/5）。

## 4. 头像服务端缩放压缩

### 4.1 处理库与限制（SPEC §7.3.1 要求写明）
| 项 | 值 |
|---|---|
| 处理库 | `sharp`（v0.35.3，既有依赖） |
| 输入格式 | image/jpeg、image/png、image/webp（MIME + sharp 解码双重校验，拦可执行文件伪装） |
| 输入大小上限 | 原始文件 ≤1MB（保持 M10.8 既有更严限制，SPEC 上限为 5MB） |
| 输入尺寸上限 | ≤4096x4096，超限 413 `AVATAR_DIMENSIONS_TOO_LARGE`（新增，防无保护解码超大图） |
| 输出尺寸 | 等比缩放 fit=inside ≤512x512，`withoutEnlargement`（小图不放大） |
| 输出格式 | webp（sharp `.webp()`） |
| 输出大小 | 质量档 80→5 逐步降质，取首个 ≤256KB 的输出 |
| 失败清理 | 压缩全在内存完成；额度校验通过后才落盘；写库失败删文件，不残留孤儿 |

### 4.2 处理流程（全内存，最后落盘）
1. MIME + 文件大小校验 → 2. sharp metadata 解码校验 → 3. 尺寸上限检查 → 4. 内存缩放压缩 → 5. 按**压缩后大小**做额度检查（`used - oldAvatarSize + compressed <= quota`，超额 413 不落盘）→ 6. 写 `.webp` 文件 → 7. 更新 `avatarMimeType=image/webp`、`avatarSize=压缩后字节` → 8. 删除旧头像文件 → 9. `addStorageUsed(压缩后 - 旧)`。

替换头像释放旧文件占用；移除头像释放占用；上传失败不留下临时文件。旧头像（jpg/png）URL 继续可读，无需迁移。

## 8. 风险与后续建议

1. mustChangePassword 提示为轻提示（可关闭、不拦截），用户可暂不改密继续使用；如产品后续要求「强制改密后放行」，可在现有字段上收紧（拦截导航），无需改模型。
2. 头像原始文件上限保持 1MB（严于 SPEC 5MB），当前满足产品口径；如需放宽可单独调 `AVATAR_MAX_SIZE_BYTES`。
3. 头像输出统一 webp；极个别极老旧浏览器不支持 webp 时显示会退化，现代浏览器均支持，风险可忽略。
4. 服务器上根 `schema.prisma` 与 `prisma/schema.prisma` 双份坑位仍在，每次 schema 变更需双同步；建议后续把根文件删除、统一到 `prisma/`（一次性治理）。
