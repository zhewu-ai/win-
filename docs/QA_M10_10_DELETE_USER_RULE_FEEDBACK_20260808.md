# M10.10 补丁反馈：放宽管理员删除废用户规则

日期：2026-08-08  
来源：M10.10 验收后产品反馈  
结论：当前删除用户规则过严，需要调整为“禁用后可删除，并级联清理该用户个人数据”。

## 1. 背景

M10.10 已新增“管理员删除废用户”能力，但当前实现要求用户必须同时满足：

- 已禁用
- 非管理员
- 非当前登录管理员本人
- 完全无业务数据

实际验收中发现：新注册小号即使手动删除了可见内容，后台仍可能因为历史数据、回收站数据、示例便签、公告已读记录、反馈记录、附件记录等残留关系而无法删除账号。

这个限制对真实内测运营不友好。管理员清理废号时，目标通常不是“只删空账号”，而是“确认这是废弃账号后，把该账号和它自己的数据一起清掉”。

## 2. 需求调整

将删除用户规则从：

> 仅允许删除 disabled 且无业务数据的用户

调整为：

> 仅允许删除 disabled 的普通用户；删除时自动级联清理该用户个人数据。

## 3. 必须保留的安全边界

以下限制仍必须保留：

1. 不能删除当前登录管理员自己。
2. 不能删除任何 admin 角色用户。
3. 不能直接删除 active 用户，必须先禁用再删除。
4. 删除仍需要两层确认：
   - 第一层：确认弹窗说明删除不可恢复。
   - 第二层：输入用户邮箱或 `DELETE` 后才能执行。
5. 删除操作必须只作用于目标用户自己的数据，不能影响其他用户。

## 4. 需要移除的限制

移除以下阻塞条件：

- 用户存在 Note 时禁止删除。
- 用户存在 Attachment 时禁止删除。
- 用户存在 FeedbackTicket 时禁止删除。
- 用户存在 AnnouncementRead 时禁止删除。
- 用户存在其他可安全清理的个人关联数据时禁止删除。

也就是说，不再返回 `USER_HAS_DATA` 作为删除阻塞。

## 5. 删除时应级联清理的数据

删除 disabled 普通用户时，服务端应自动清理：

- 该用户所有便签，包括正常、归档、回收站中的便签。
- 该用户所有附件记录。
- 该用户附件文件和对应便签附件目录。
- 该用户头像文件及头像字段。
- 该用户反馈工单。
- 该用户公告已读记录。
- 该用户密码重置 token。
- 该用户创建的邀请码。
- 该用户使用过的邀请码关系：建议将 `usedById` 置空，避免外键阻塞。
- 最后删除 User 记录。

注意：如果该用户曾创建公告，按当前产品定位普通用户不应创建公告；但服务端仍需避免外键异常。建议技术部根据现有 schema 决定：

- 如果普通用户不可能创建公告：可在删除前断言无 `Announcement.createdById = userId`。
- 如果历史数据可能存在：应先删除该用户创建公告的 read 记录，再删除公告，或拒绝并返回明确错误。

## 6. API 行为建议

接口：`DELETE /api/admin/users/:id`

保留错误：

- `401`：未登录。
- `403`：非管理员。
- `400 CANNOT_DELETE_SELF`：不能删除自己。
- `400 CANNOT_DELETE_ADMIN`：不能删除管理员。
- `400 MUST_DISABLE_FIRST`：用户未禁用，需先禁用。
- `404 USER_NOT_FOUND`：用户不存在。

移除错误：

- `409 USER_HAS_DATA`：不再作为阻塞条件。

成功返回建议：

```json
{
  "ok": true,
  "deletedUserId": "xxx",
  "counts": {
    "notes": 3,
    "attachments": 1,
    "feedbackTickets": 0,
    "announcementReads": 2
  }
}
```

## 7. UI 调整

管理员用户列表中，“删除用户”按钮仍只在以下条件下显示：

- `status === "disabled"`
- `role === "user"`
- 非当前登录用户

删除确认文案需要从“仅当无有效数据时使用”改为：

> 删除用户后不可恢复。此操作会同时清理该用户的便签、附件、反馈记录和公告已读记录。

第二层确认弹窗建议展示影响范围：

> 将永久删除该用户及其 X 条便签、Y 个附件、Z 条反馈记录、N 条公告已读记录。请输入用户邮箱或 DELETE 确认。

如果短期不方便在列表接口返回计数，也可以先不展示精确数字，但必须明确说明会清理该用户个人数据。

## 8. 实现注意事项

1. 数据库删除建议放在事务内，避免删一半留下外键残留。
2. 文件删除可以在事务成功后尽力清理；文件不存在不应导致接口失败。
3. 附件文件路径必须继续使用现有安全路径策略，不能允许路径穿越。
4. 删除 Note 前需先删除 Attachment 记录，避免外键约束问题。
5. 删除用户后不需要再维护该用户 `storageUsedBytes`，因为 User 已不存在。
6. 不要删除其他用户创建的邀请码、公告、便签、附件。

## 9. 验收用例

### 9.1 可删除场景

1. 注册一个测试用户。
2. 登录该用户，确认自动生成 3 条示例便签。
3. 新建一条普通便签。
4. 删除部分便签到回收站。
5. 让该用户打开一次公告，产生公告已读记录。
6. 管理员禁用该用户。
7. 管理员删除该用户。
8. 预期：
   - 删除成功。
   - 用户列表不再出现该用户。
   - 该用户的 Note / Attachment / FeedbackTicket / AnnouncementRead / PasswordResetToken 均无残留。
   - 附件文件、头像文件尽力清理。

### 9.2 保护场景

1. active 用户直接删除：应返回 `MUST_DISABLE_FIRST`。
2. 删除当前管理员自己：应返回 `CANNOT_DELETE_SELF`。
3. 删除 admin 用户：应返回 `CANNOT_DELETE_ADMIN`。
4. 普通用户调用删除接口：应返回 403。
5. 删除不存在用户：应返回 404。

### 9.3 隔离场景

1. 准备用户 A 和用户 B，各自有便签和附件。
2. 管理员禁用并删除用户 A。
3. 预期：
   - 用户 A 数据被清理。
   - 用户 B 的便签、附件、反馈、公告已读记录完全不变。

## 11. 本轮不做

- 不允许删除 active 用户。
- 不允许删除 admin 用户。
- 不新增“恢复已删除用户”。
- 不做用户数据导出。
- 不做复杂审计日志；如需审计，放到 M10.11 管理后台稳定性专项。
