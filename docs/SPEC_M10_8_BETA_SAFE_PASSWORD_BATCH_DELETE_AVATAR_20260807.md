# PinNote M10.8 内测体验补强：修改密码、多选删除、自定义头像、更新时间准确性、反馈工单

日期：2026-08-07

## 1. 背景

当前已有 6 个内测用户，后续更新必须优先保证：

1. 不误删任何真实用户数据。
2. 不破坏登录、注册、管理员后台、忘记密码说明页。
3. 不影响现有便签列表、编辑、图片附件、存储额度。
4. 新功能必须先本地验收，再生产备份后上线。

M10.7 已完成“人工邮箱验证找回密码”：用户用绑定邮箱发信到 `yan251@foxmail.com`，管理员核验后人工重置临时密码。

但“用户登录后自行修改密码”没有来得及交给技术部实现，需要合并到本轮。

同时收到内测反馈：

1. 左侧便签列表栏需要多选删除。
2. 用户希望可以自定义头像。
3. 只要打开便签/待办，列表排序时间就被刷新，导致用户只是查看或找东西也会把日期顺序打乱。
4. 既然已有内测用户，需要提供用户反馈入口，并让管理员能在后台集中查看。

本轮还要补一条运营体验：管理员人工重置的是临时密码，用户登录后必须被清楚提醒“请尽快修改密码”。

## 2. 本轮目标

M10.8 做五件事：

1. **用户修改密码 + 临时密码提示**：已登录用户可在账号菜单修改自己的密码；人工重置后用户看到“请修改临时密码”的提示。
2. **左栏多选删除**：在首页左侧便签列表多选便签，批量移入回收站。
3. **自定义头像**：用户可上传头像图片，服务端必须缩放/压缩，避免超大图片压垮服务器，并可移除恢复文字头像。
4. **更新时间准确性**：打开/查看便签不更新 `updatedAt`；只有真实编辑或状态变化才更新时间。
5. **用户反馈工单**：用户可提交反馈，管理员可在后台查看、处理、关闭。

## 3. 本轮不做

明确不做：

1. 不永久删除多选便签，多选删除只进入回收站。
2. 不做跨用户批量操作。
3. 不做回收站多选永久删除。
4. 不做归档页多选删除。
5. 不做头像裁剪器复杂编辑。
6. 不接第三方头像服务。
7. 不做公开头像墙或用户资料页。
8. 不做其它设备/session 全量下线。
9. 不做密码历史记录。
10. 不新增“访问时间/最近查看”排序。
11. 不做用户自定义排序规则。
12. 不做邮件/短信反馈通知。
13. 不做多管理员协作流转。
14. 不做附件型反馈上传。

## 4. 数据安全总原则

### 4.1 所有写操作必须按 userId 隔离

本轮所有新增 API 必须通过当前 session 获取用户，并在数据库操作中带上：

```ts
where: { userId: currentUser.id }
```

或等价的用户归属校验。

禁止只按 note id / attachment id / user id 参数直接操作。

### 4.2 批量删除只能软删

多选删除的行为等同单条删除：

```ts
deletedAt = now
```

不能物理删除 Note。

不能删除 Attachment 文件。

附件仍随便签留在回收站中，等待后续永久删除/回收站清理逻辑处理。

### 4.3 上线前后必须对比生产数据

部署前后记录：

```text
User
Note
Attachment
InviteCode
PasswordResetToken
```

如新增头像字段或头像文件，也要记录头像文件数量/大小。

验收测试数据必须清理，最终数量回到基线或说明合理变化。

## 5. 功能一：用户修改密码

### 5.1 入口

在账号菜单中新增：

```text
修改密码
```

建议放在“修改昵称”附近，与退出登录、管理用户同一菜单层级。

如果用户是刚通过管理员人工重置临时密码登录，账号菜单或首页顶部应给出轻提示：

```text
你当前可能正在使用临时密码，建议尽快修改密码。
```

提示应包含“去修改”按钮，点击打开修改密码弹窗。

### 5.1.1 临时密码提示策略

本轮先做轻量策略，不强制拦截用户。

技术部可二选一：

1. **无 schema 方案**：管理员重置密码后不记录状态，M10.8 只在“忘记密码说明页/产品文案/管理员回复模板”中提示用户登录后修改密码，并在账号菜单常驻“修改密码”入口。
2. **推荐 schema 方案**：User 增加 `mustChangePassword Boolean @default(false)`。管理员重置密码时置为 `true`；用户成功修改密码后置为 `false`；前端看到 `mustChangePassword=true` 时显示轻提示。

如果采用推荐 schema 方案：

1. `GET /api/auth/me` 返回 `mustChangePassword`。
2. 管理员重置密码 API 成功后设置 `mustChangePassword=true`。
3. 用户修改密码成功后设置 `mustChangePassword=false`。
4. 提示只对当前用户显示，不影响便签编辑。
5. 不做强制跳转，不阻塞用户查看数据。

### 5.2 界面

使用弹窗或独立页面均可，优先弹窗。

字段：

1. 当前密码。
2. 新密码。
3. 确认新密码。

按钮：

1. 取消。
2. 保存。

前端校验：

1. 新密码至少 8 位。
2. 两次新密码一致。
3. 当前密码不能为空。

成功文案：

```text
密码已修改
```

错误文案：

```text
当前密码不正确
密码至少 8 位
两次输入的密码不一致
账号已被禁用，请联系管理员
```

### 5.3 API

新增：

```text
POST /api/auth/change-password
```

请求：

```json
{
  "currentPassword": "old-password",
  "newPassword": "new-password"
}
```

成功：

```json
{
  "ok": true,
  "message": "密码已修改"
}
```

错误：

| 场景 | HTTP | error |
|---|---:|---|
| 未登录 | 401 | `UNAUTHORIZED` |
| disabled 用户 | 403 | `ACCOUNT_DISABLED` |
| 当前密码错误 | 400 或 401 | `INVALID_CURRENT_PASSWORD` |
| 新密码少于 8 位 | 400 | `PASSWORD_TOO_SHORT` |
| 请求体非法 | 400 | `INVALID_REQUEST` |

后端要求：

1. 必须重新查库确认用户存在且 `status=active`。
2. 使用 bcrypt compare 校验当前密码。
3. 使用 bcrypt hash 保存新密码。
4. 不返回 passwordHash。
5. 不记录明文密码日志。
6. 修改成功后当前会话保持登录。
7. 旧密码立即失效，新密码可登录。
8. 如果采用 `mustChangePassword`，修改成功后清除该标记。

## 6. 功能二：左栏多选删除

### 6.1 使用场景

用户在首页左侧便签列表中，希望一次选择多个便签并删除到回收站。

### 6.2 入口与交互

在左侧列表顶部增加“选择”入口。

建议交互：

1. 正常模式：列表保持现状。
2. 点击“选择”进入多选模式。
3. 每条便签左侧显示 checkbox。
4. 顶部显示已选择数量。
5. 顶部显示操作：
   - 全选当前列表
   - 取消选择
   - 删除
6. 点击“删除”弹确认框：

```text
确定将选中的 X 条便签移入回收站？
```

7. 确认后批量软删。
8. 删除成功后退出多选模式，并刷新列表。

### 6.3 范围

本轮只支持首页未归档列表。

搜索状态下：

1. “全选当前列表”只选择当前搜索结果中可见的便签。
2. 批量删除只删除已选择项。

置顶便签：

1. 可被选择。
2. 删除后进入回收站。

当前正在编辑的便签：

1. 如果被选中并删除，编辑区应清空或自动切换到下一条便签。
2. 不能显示已删除便签继续可编辑的状态。

### 6.4 API

建议新增：

```text
POST /api/notes/bulk-delete
```

请求：

```json
{
  "ids": ["note_id_1", "note_id_2"]
}
```

限制：

1. `ids` 必须是非空数组。
2. 单次最多 100 条。
3. 重复 id 去重。
4. 只删除当前用户拥有、未删除的便签。
5. 不能删除别人的便签。
6. 不能删除已经在回收站的便签。

成功：

```json
{
  "ok": true,
  "deletedIds": ["note_id_1"],
  "notFoundIds": ["note_id_2"]
}
```

说明：

1. `deletedIds` 是实际软删成功的 id。
2. `notFoundIds` 包含不存在、不属于当前用户、已在回收站、不可删除的 id。
3. 如果 `deletedIds` 为空但请求格式有效，仍返回 200，并说明没有可删除项。

### 6.5 离线与同步

当前产品有离线防丢基础。本轮多选删除至少要做到：

1. 在线状态批量删除正常。
2. 删除失败时不从 UI 永久移除。
3. 如果复用单条离线删除逻辑逐条执行，需要交付报告说明。
4. 不允许因为批量删除失败导致本地便签内容丢失。

如果离线批量删除复杂，可先在离线时禁用“批量删除”按钮，并提示：

```text
离线时暂不支持批量删除，请联网后再试。
```

## 7. 功能三：自定义头像

### 7.1 当前状态

当前已有：

1. `displayName`
2. `avatarColor`
3. 文字头像 fallback

本轮新增头像图片上传。保留文字头像作为 fallback。

### 7.2 用户体验

账号菜单中新增：

```text
更换头像
```

点击后打开头像设置弹窗。

弹窗包含：

1. 当前头像预览。
2. 上传图片按钮。
3. 移除头像按钮。
4. 保留/选择颜色头像入口。

上传后：

1. 账号菜单头像立即更新。
2. 管理员用户列表中的该用户头像也更新。
3. 刷新页面后仍保留。

移除头像后：

1. 恢复文字头像。
2. 保留用户选择的 `avatarColor`。

### 7.3 图片限制

支持：

```text
image/jpeg
image/png
image/webp
```

限制：

1. 原始上传文件最大 5MB，超过直接拒绝。
2. 原始图片尺寸最大 4096 x 4096，超过直接拒绝。
3. 服务端必须将头像缩放为最大 512 x 512。
4. 服务端必须压缩输出，目标文件不超过 256KB。
5. 输出格式建议统一为 webp；如运行环境不支持 webp，可输出 jpeg。
6. 保存和计入额度的是压缩后的头像文件大小，不是原图大小。
7. 不允许 SVG。
8. 不允许 GIF 动图。
9. 不允许可执行文件伪装。

错误：

| 场景 | HTTP | error |
|---|---:|---|
| 未登录 | 401 | `UNAUTHORIZED` |
| disabled 用户 | 403 | `ACCOUNT_DISABLED` |
| 文件过大 | 413 | `AVATAR_TOO_LARGE` |
| 图片尺寸过大 | 413 | `AVATAR_DIMENSIONS_TOO_LARGE` |
| 类型不支持 | 400 | `UNSUPPORTED_AVATAR_TYPE` |
| 图片解码失败 | 400 | `INVALID_AVATAR_IMAGE` |
| 请求体非法 | 400 | `INVALID_REQUEST` |

### 7.3.1 服务端缩放压缩要求

头像处理必须在服务端完成，不能只依赖前端压缩。

原因：用户可能上传 4000 x 4000 甚至更大的图片。即使文件大小不大，解码和展示也会给服务器、浏览器和移动端带来不必要压力。

处理流程：

1. 接收 multipart 文件。
2. 校验 MIME 和文件头。
3. 解码图片，读取实际宽高。
4. 如果宽高超过上限，直接拒绝或先限制解码资源后拒绝，不能无保护处理超大图。
5. 将图片等比缩放到不超过 512 x 512。
6. 压缩输出到不超过 256KB。
7. 只保存压缩后的文件。
8. 删除临时原图。
9. 上传失败或压缩失败不能留下临时文件。

技术部可选用 `sharp` 等成熟图片处理库。交付报告必须写明：

1. 使用的库。
2. 输入大小限制。
3. 输出尺寸。
4. 输出格式。
5. 输出文件大小。
6. 失败清理策略。

### 7.4 存储与额度

头像图片应计入用户存储额度，避免绕过 M10.3。

规则：

1. 上传前先按原始文件大小做基础防护，避免超大文件进入处理流程。
2. 压缩完成后检查 `storageUsedBytes - oldAvatarSize + compressedAvatarSize <= storageQuotaBytes`。
2. 超额返回 413。
3. 替换头像时，应释放旧头像占用，再计算新头像是否可放入。
4. 移除头像时，应释放头像占用。
5. 上传失败不能留下孤儿文件。

### 7.5 数据模型

建议在 `User` 增加字段：

```prisma
avatarUrl String?
avatarStoragePath String?
avatarMimeType String?
avatarSize Int @default(0)
```

也可以命名为：

```prisma
avatarPath
avatarFileSize
```

但交付报告必须写清楚最终字段名。

### 7.6 API

建议新增：

```text
POST /api/auth/avatar
DELETE /api/auth/avatar
```

`POST /api/auth/avatar`：

1. multipart 上传头像。
2. 校验登录和 active 状态。
3. 校验类型、大小、额度。
4. 保存新头像文件。
5. 删除旧头像文件。
6. 更新 User avatar 字段和 storageUsedBytes。
7. 返回最新 user。

`DELETE /api/auth/avatar`：

1. 删除当前用户头像文件。
2. 清空 User avatar 字段。
3. 扣减 storageUsedBytes。
4. 返回最新 user。

`GET /api/auth/me` 应返回头像字段。

管理员用户列表也应返回头像字段。

### 7.7 文件访问安全

头像可以按两种方式处理，技术部二选一并写入交付报告：

1. 头像公开读取：返回受控静态 URL，但文件路径必须不可猜测。
2. 头像鉴权读取：通过 API 校验登录后读取。

考虑头像是用户主动展示信息，本轮可接受“受控公开 URL”，但必须满足：

1. 文件名随机。
2. 禁止路径穿越。
3. 只允许读取头像目录下文件。
4. 删除头像后旧 URL 不再可用。

## 8. 功能四：更新时间准确性

### 8.1 当前问题

当前表现是：用户只要打开便签或待办，即使没有实际编辑，`updatedAt` 也可能被刷新，左侧列表按更新时间排序后会被打乱。

这会带来两个问题：

1. 用户只是查看或查找内容，便签却被移动到最新位置。
2. 时间排序不再代表“最近真正修改”，用户对列表顺序失去信任。

### 8.2 产品规则

从 M10.8 开始：

```text
只有真实编辑或真实状态变化，才更新 updatedAt。
```

只读行为不得更新 `updatedAt`：

1. 打开便签。
2. 切换选中便签。
3. 聚焦标题/正文/待办输入框但不输入。
4. 搜索命中并打开便签。
5. 展开查看附件。
6. 打开/关闭更多菜单、颜色菜单、图片预览。
7. 浏览归档/回收站列表。
8. 自动保存触发但 payload 与服务端内容完全相同。

真实变化应更新 `updatedAt`：

1. 修改标题。
2. 修改正文。
3. 修改待办文本。
4. 勾选/取消勾选待办。
5. 新增/删除/重排待办项。
6. 修改颜色。
7. 修改置顶状态。
8. 归档/取消归档。
9. 删除到回收站。
10. 恢复便签。
11. 上传或删除附件。
12. 修改窗口置顶/便签置顶等会持久化到 Note 的字段。

### 8.3 后端要求

所有更新 Note 的 API 必须避免“无变化更新”。

建议做法：

1. PATCH 前先读取当前 Note。
2. 对请求字段做归一化。
3. 与当前值比较。
4. 如果没有任何字段发生变化，直接返回当前 Note，不执行 update，`updatedAt` 不变。
5. 如果有字段变化，再执行 update，让 Prisma/数据库更新 `updatedAt`。

待办数组、分组数组等结构化字段必须用结构化比较，不能只比较对象引用。

如果当前 schema 使用 `@updatedAt`，技术部要特别确认：只要执行 `prisma.note.update()` 就会刷新 `updatedAt`。因此无变化时必须避免调用 update。

### 8.4 前端要求

前端也应减少无意义保存：

1. 打开便签时不主动 PATCH。
2. 切换便签时，如果草稿未变化，不 PATCH。
3. autosave 只有检测到内容真实变化才发 PATCH。
4. 从服务端加载后建立 baseline，用于判断是否 dirty。
5. 保存成功后更新 baseline。

前端优化不能替代后端防线。即使前端误发无变化 PATCH，后端也必须保证 `updatedAt` 不变。

### 8.5 排序要求

左侧列表继续按 `updatedAt` 排序。

但 `updatedAt` 的含义必须变为：

```text
最近真实修改时间
```

不是最近打开时间。

## 9. 功能五：用户反馈工单

### 9.1 使用场景

已有 6 个内测用户后，必须给用户一个明确反馈渠道，不能只靠私聊或口头收集。

用户应能在应用内提交：

1. 问题反馈。
2. 功能建议。
3. 使用疑问。

管理员应能在后台集中查看反馈，并标记处理状态。

### 9.2 用户入口

在账号菜单中新增：

```text
反馈问题
```

点击后打开反馈弹窗。

弹窗字段：

1. 类型：问题 / 建议 / 其他。
2. 标题。
3. 详细描述。
4. 当前页面/环境信息自动附带，用户不可编辑或可折叠查看。

按钮：

1. 取消。
2. 提交反馈。

提交成功文案：

```text
反馈已提交，感谢你帮助改进 PinNote。
```

### 9.3 用户提交限制

字段限制：

1. 标题 1-80 字。
2. 描述 1-2000 字。
3. 类型只能是 `bug` / `feature` / `other`。
4. 单用户 1 分钟最多提交 3 条，避免误触刷屏。
5. disabled 用户不能提交。

本轮不支持反馈附件上传。

### 9.4 数据模型

建议新增：

```prisma
model FeedbackTicket {
  id          String   @id @default(cuid())
  userId      String
  type        String
  title       String
  content     String
  status      String   @default("open")
  pageUrl     String?
  userAgent   String?
  appVersion  String?
  adminNote   String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  user User @relation(fields: [userId], references: [id])

  @@index([userId])
  @@index([status])
  @@index([createdAt])
}
```

`User` 增加反向关系：

```prisma
feedbackTickets FeedbackTicket[]
```

允许的 `status`：

```text
open
reviewing
resolved
closed
```

### 9.5 API

用户 API：

```text
POST /api/feedback
```

请求：

```json
{
  "type": "bug",
  "title": "左侧列表排序异常",
  "content": "我只是打开便签查看，排序就变化了。",
  "pageUrl": "/"
}
```

成功：

```json
{
  "ok": true,
  "ticket": {
    "id": "..."
  }
}
```

管理员 API：

```text
GET /api/admin/feedback
PATCH /api/admin/feedback/:id
```

`GET` 返回：

1. 反馈列表。
2. 提交用户 email / username / displayName。
3. 类型。
4. 状态。
5. 标题。
6. 创建时间。
7. 最新更新时间。

`PATCH` 支持：

```json
{
  "status": "reviewing",
  "adminNote": "已复现，排入 M10.8"
}
```

所有管理员 API 必须 `requireAdmin()`。

## 11. 验收标准

### 11.1 修改密码验收

1. 已登录 active 用户可打开修改密码弹窗。
2. 当前密码错误 -> `INVALID_CURRENT_PASSWORD`，密码不变。
3. 新密码少于 8 位 -> `PASSWORD_TOO_SHORT`。
4. 两次新密码不一致 -> 前端拦截。
5. 当前密码正确 + 新密码合法 -> 200。
6. 修改后旧密码登录失败。
7. 修改后新密码登录成功。
8. 当前会话保持登录。
9. disabled 用户不能修改密码。

### 11.2 多选删除验收

1. 左侧列表有“选择”入口。
2. 进入多选模式后每条便签有 checkbox。
3. 可选择 1 条、2 条、多条。
4. 可全选当前列表。
5. 可取消选择并退出多选模式。
6. 删除前有确认弹窗，显示选中数量。
7. 确认后选中便签进入回收站。
8. 未选中便签不受影响。
9. 别的用户便签不受影响。
10. 当前编辑便签被删除后，编辑区不再显示可编辑状态。
11. 搜索状态下只删除选中结果。
12. 320px 宽度下不横向溢出。

### 11.3 自定义头像验收

1. 账号菜单显示“更换头像”入口。
2. 可上传 jpg/png/webp。
3. 超过 5MB 原图被拒绝。
4. 超过 4096 x 4096 原图被拒绝。
5. 4000 x 4000 合法图片上传后被缩放到不超过 512 x 512。
6. 输出头像文件不超过 256KB。
7. SVG/GIF/文本文件被拒绝。
8. 上传成功后账号菜单头像更新。
9. 刷新页面后头像仍存在。
10. 管理员用户列表头像更新。
11. 替换头像后旧头像文件被删除或不可访问。
12. 移除头像后恢复文字头像。
13. 头像占用按压缩后文件大小计入 storageUsedBytes。
14. 超出存储额度时上传失败且不留孤儿文件。
15. 320px 宽度下头像弹窗不横向溢出。

### 11.4 更新时间准确性验收

使用临时测试用户和至少 3 条测试便签验证：

1. 记录 A/B/C 三条便签的 `updatedAt` 初始值和排序。
2. 打开 A，不输入、不切换任何状态，等待 autosave 周期后刷新列表，A 的 `updatedAt` 不变，排序不变。
3. 搜索并打开 B，不编辑，B 的 `updatedAt` 不变。
4. 聚焦 C 标题和正文后失焦，不输入，C 的 `updatedAt` 不变。
5. 修改 A 正文一个字符，A 的 `updatedAt` 更新，A 排到最新。
6. 修改待办勾选状态，`updatedAt` 更新。
7. 发送与当前内容完全相同的 PATCH，接口返回成功但 `updatedAt` 不变。
8. 归档/取消归档、置顶/取消置顶等真实状态变化会更新 `updatedAt`。
9. 附件上传/删除会更新 `updatedAt`。
10. 生产验收不能用真实内测用户做破坏性排序测试。

### 11.5 反馈工单验收

1. 账号菜单显示“反馈问题”入口。
2. 普通 active 用户可提交 bug / feature / other。
3. 标题为空、描述为空、超长内容会被拒绝。
4. disabled 用户不能提交。
5. 提交成功后管理员后台能看到。
6. 管理员可按状态和类型筛选。
7. 管理员可修改状态为 reviewing / resolved / closed。
8. 管理员可填写备注。
9. 非管理员访问反馈管理 API 返回 403。
10. 320px 宽度下反馈弹窗不横向溢出。

### 11.6 回归验收

1. 6 个内测用户仍可登录。
2. admin 仍可登录。
3. 邀请制注册正常。
4. 忘记密码人工说明页正常。
5. 管理员重置密码正常。
6. 用户列表正常。
7. 普通便签新建、编辑、删除、恢复正常。
8. 图片附件上传、查看、删除正常。
9. 存储额度显示正常。
10. 打开旧便签查看不会改变排序。
11. `npm run build` 通过。

## 14. 回退方案

### 14.1 页面/API 异常

1. 回退代码到 M10.7。
2. `npm run build`。
3. 重启服务。
4. 复查登录、注册、首页、管理员后台。

### 14.2 schema 或数据异常

1. 停止服务。
2. 恢复部署前数据库备份。
3. 回退代码。
4. build + restart。
5. 复查 6 个内测用户数据。

### 14.3 头像文件异常

1. 停止服务。
2. 恢复头像目录备份或删除本轮新增测试头像。
3. 恢复数据库备份。
4. 重启服务。

### 14.4 更新时间异常

如果发现打开便签仍会刷新排序：

1. 回退 Note PATCH / autosave 相关代码。
2. 恢复部署前备份。
3. 重新验证旧便签排序。
4. 暂停 M10.8 上线。
