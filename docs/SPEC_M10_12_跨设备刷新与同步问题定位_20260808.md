# M10.12 问题定位：跨设备刷新与同步可见性

日期：2026-08-08

## 一、用户反馈

同一账号在两台电脑同时登录时，出现以下问题：

1. 在一台电脑上编辑原有便签并新增内容，另一台电脑打开同一便签后没有同步显示。
2. 在网页端新建便签并输入内容，桌面端/另一台电脑的列表里没有出现，即使等待后仍不可见。
3. 桌面壳没有浏览器那样的刷新入口，只能关闭应用再打开，体验成本高。
4. 顶部显示「已同步」容易被理解为“已经拉到服务器最新内容”，但当前实际含义更接近“本机保存/推送状态”。
5. 应用闲置一段时间后偶发“抽搐一下”，需要排查是否由同步状态、布局观察器或自动任务触发。

## 二、初步定位结论

这不是用户操作问题，是当前同步模型的产品缺口。

当前实现是“服务端存储 + 本地离线推送队列”，不是完整的多端实时同步：

- `src/hooks/useNotes.ts` 只在页面首次加载、页面从隐藏变为可见、搜索/删除等本地操作后调用 `fetchNotes()` 拉取服务器列表。
- `src/hooks/useSyncStatus.ts` 每 30 秒触发的 `runSync()` 只处理本机 IndexedDB 里的 pending create/update/delete，把本机离线改动推到服务器。
- `src/lib/offline/sync.ts` 是 push-only，同步成功后不会主动从服务器 pull 其他设备的新数据。
- 桌面 WebView 长时间保持可见时，不一定触发浏览器的 `visibilitychange`，因此另一台设备产生的新便签/新内容不会自然进入当前内存列表。
- `src/components/NoteEditor.tsx` 当前编辑器重置本地编辑状态的 effect 只依赖 `note?.id`。即使列表重新拉到了同一条便签的新 `updatedAt`、`title`、`content`，只要便签 ID 没变，编辑器内容也不会自动替换为服务器新版。

因此用户看到的两个现象都能解释：

- “新建便签另一端列表不出现”：当前端没有主动 pull 最新列表。
- “原有便签新增内容另一端不显示”：即使触发了列表刷新，正在编辑的同一条便签也可能因为 `note?.id` 未变而不更新编辑器内容。

## 三、不要误判的点

「已同步」不是“多端数据已经最新”的证明。

当前 `SaveStatus` 基于本机保存状态、离线 pending 状态和 `runSync()` 状态展示。它只能表达“本机改动是否保存/是否等待推送”，不能表达“是否已经拉取了其他设备的最新修改”。建议文案或交互上把这两个概念分开：

- 本机保存状态：保存中 / 已保存 / 等待同步 / 同步失败。
- 远端刷新动作：手动刷新 / 刷新中 / 刚刚刷新 / 刷新失败。

## 四、建议优先级

### P0：补手动刷新入口

目标：用户在桌面壳里不用关闭应用，也能主动拉服务器最新数据。

建议位置：

- 主编辑区顶部工具栏，在现有 `SaveStatus` 附近增加圆形刷新图标按钮。
- 侧边栏底部或搜索区附近也建议保留一个刷新图标，解决“新建便签列表不出现”且当前无选中便签时也能刷新。

交互要求：

- 图标按钮使用圆形箭头，tooltip/aria-label 为“刷新便签”。
- 点击后进入 `刷新中` 状态，按钮禁用并显示旋转态，避免重复请求。
- 刷新失败时给出轻量提示，不清空当前内容。
- 不建议直接把「已同步」整体替换掉；更合理是保留本机保存状态，再增加刷新按钮。若产品坚持极简，可以把文字弱化，只让图标承担刷新动作。

### P0：刷新前保护本机未保存输入

刷新不能覆盖本机正在输入但还没保存成功的内容。

要求：

- 若当前编辑器存在 debounce pending updates，点击刷新前必须先 flush 当前待保存内容。
- 若上一次保存失败且有 `lastFailedPayload`，先重试保存；仍失败则停止刷新，并提示用户保存失败。
- 若本机存在 `pendingCreate` / `pendingUpdate` / `syncError`，刷新列表时不得用服务器旧快照覆盖本机本地队列。现有 `mirrorNote()` 已有“不覆盖非 synced 本地记录”的保护，改动时必须保留。

### P0：同一便签远端版本更新后编辑器要能更新

目标：另一台设备改了当前正在看的同一条便签，点击刷新后当前编辑器能显示新版。

技术点：

- `NoteEditor` 不能只在 `note?.id` 变化时重置内容。
- 需要额外监听 `note.updatedAt` 或显式的 `refreshVersion`。
- 仅在安全状态下应用远端新版：当前 `saveStatus === "saved"`、无 debounce pending、无 `lastFailedPayload`、无本地恢复草稿。
- 不安全时不要静默覆盖，建议提示：“本机有未保存内容，先保存后再刷新”。

### P1：增加低频自动拉取，但必须静默且保守

手动刷新先上线。自动拉取可以作为下一阶段，避免再次引入“抽搐”。

建议策略：

- 页面可见、在线、无 pending 本地修改、当前编辑器非 saving/error 时才自动 pull。
- 间隔建议 60-120 秒，不要 5-10 秒高频轮询。
- 后台 pull 必须 silent，不触发全局 loading 骨架屏，不改变滚动位置，不抢焦点。
- 如果当前正在编辑同一条便签且远端有新版，不要自动覆盖，可显示轻提示“有远端更新，点击刷新”。

暂不建议第一版引入 WebSocket/SSE。当前产品规模下，手动刷新 + 保守轮询足够，实时协同编辑不是本轮目标。

## 五、“抽搐一下”的排查方向

需要技术部复现并记录时间点，重点查三类来源：

1. `useSyncStatus.ts` 的 30 秒 `setInterval(runSync)`：即使没有待同步内容，也可能触发 `isSyncing` 或订阅状态变化，带动 `SaveStatus`/`OfflineBar` 重渲染。
2. `NoteEditor.tsx` 的 `ResizeObserver`：编辑器宽度轻微变化时会切换 `toolbarMode`，可能导致工具栏图标/状态位宽变化，看起来像抖动。
3. `SaveStatus` 文案宽度变化：`已同步`、`同步中`、`等待同步`、隐藏/显示文字在窄宽度下可能推动右侧按钮或触发一帧布局变化。

排查方式：

- 在桌面壳中打开同一便签静置 3-5 分钟，录屏并记录抖动周期是否接近 30 秒。
- 临时加日志观察 `runSync()` 开始/结束、`toolbarMode` 变化、`SaveStatus` label 变化。
- 如果抖动与 30 秒一致，优先处理同步状态更新的无意义重渲染。
- 如果抖动发生在窗口宽度临界值附近，优先处理 `ResizeObserver` 阈值和工具栏固定宽度。

## 六、改动文件建议

预计涉及：

- `src/hooks/useNotes.ts`
  - `fetchNotes(q, options)` 支持 `silent` 刷新。
  - 返回拉取到的 `Note[]`，便于父组件判断当前选中便签是否仍存在。
  - 后台/手动刷新不触发主列表 loading 闪烁。

- `src/app/(protected)/page.tsx`
  - 增加 `refreshing` 状态。
  - 增加统一 `handleRefresh()`。
  - 将刷新能力传给 `Sidebar` 和 `NoteEditor`。

- `src/components/Sidebar.tsx`
  - 增加刷新图标按钮，用于刷新便签列表。

- `src/components/NoteEditor.tsx`
  - 增加刷新按钮。
  - 刷新前 flush 当前 pending save。
  - 同一便签 `updatedAt` 变化时，在安全状态下应用远端新版。

- `src/components/SaveStatus.tsx`
  - 可选：文案调整，避免把本机保存状态误读为多端最新状态。

- `src/hooks/useSyncStatus.ts`
  - 可选：排查并减少无 pending 时的状态抖动。

## 七、验收标准

### 基础手动刷新

1. A 电脑登录账号，打开首页列表。
2. B 电脑同账号新建一条便签。
3. A 电脑不关闭应用，点击刷新按钮。
4. A 电脑列表出现 B 新建的便签。

### 同一便签内容刷新

1. A、B 两台设备打开同一条已存在便签。
2. B 修改标题和正文，等待保存完成。
3. A 不关闭应用，点击刷新按钮。
4. A 当前编辑器显示 B 修改后的标题和正文，底部最后编辑时间更新。

### 不覆盖本机未保存内容

1. A 正在输入内容，保存状态处于保存中或人为断网制造 pending。
2. A 点击刷新。
3. 系统先保存/提示保存失败，不得直接用服务器旧内容覆盖 A 当前输入。

### 新便签和搜索状态

1. 当前有搜索词时点击刷新，只刷新当前搜索结果。
2. 清空搜索后点击刷新，完整列表与服务器一致。
3. 其他设备删除当前选中便签后，本机刷新应退出当前编辑态或显示便签已删除，不应继续编辑幽灵数据。

### 桌面壳

1. Windows/macOS 桌面壳内可见刷新按钮。
2. 不依赖关闭应用重开。
3. 刷新按钮在 320px 窄窗口下不挤压标题、保存状态和更多菜单。

### 抽搐验证

1. 修复前录屏确认抖动周期和触发条件。
2. 修复后桌面壳静置 5 分钟，工具栏、列表、编辑器不出现可见横跳。
3. 若仍抖动，记录是 `runSync`、`ResizeObserver` 还是状态文案导致，作为独立缺陷继续处理。

## 八、上线注意

- 本轮只改前端同步可见性，不做数据库迁移。
- 不改账号体系，不做设备管理。
- 不做多人实时协同编辑和冲突合并。
- 生产构建仍必须使用 webpack：`npm run build -- --webpack`，不要在共享 VM 上使用 Next 16 默认 Turbopack 构建。
- 上线前先在本地或测试环境用两个浏览器会话/两台设备复验，再推生产。
