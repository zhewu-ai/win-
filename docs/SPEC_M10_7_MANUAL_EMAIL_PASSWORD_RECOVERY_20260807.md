# PinNote M10.7 人工邮箱验证找回密码 + 用户修改密码

日期：2026-08-07

## 1. 背景

M10.4 已完成管理员最小用户管理，管理员可以在 `/admin/users` 手动重置用户密码。

M10.5 已完成邀请制注册，新用户有绑定邮箱。

M10.6 已完成自动邮件重置密码能力，但生产暂未配置 SMTP 凭据。当前阶段不接付费邮件服务，也不自建邮件服务器。

本轮做一个免费、可立即执行的找回密码方案：用户必须使用自己账号绑定的邮箱，主动发送邮件给管理员；管理员核验发件邮箱后，在后台人工重置密码。

同时补上“已登录用户修改密码”能力。这样管理员发临时密码后，用户登录即可自行改成自己的新密码，人工找回闭环才完整。

## 2. 产品决策

### 2.1 用绑定邮箱证明身份

用户忘记密码时，系统不主动发邮件。

用户需要用账号绑定邮箱发邮件给管理员：

```text
yan251@foxmail.com
```

管理员收到邮件后，在后台查找该邮箱对应用户。只有当发件邮箱与用户账号绑定邮箱一致时，才允许重置密码。

### 2.2 保留 M10.6 技术能力，但本轮不启用自动发信

M10.6 的 reset token、SMTP、自动邮件链路可以保留在代码中，作为未来接入 SMTP 后的自动化能力。

但在 SMTP 未配置前，用户侧 `/forgot-password` 不应继续呈现“提交邮箱后系统会发送邮件”的承诺，避免误导用户。

本轮用户侧入口改为人工找回说明。

### 2.3 管理员人工兜底优先

当前产品仍是邀请制、小规模私有产品。人工重置的优势是：

1. 免费。
2. 不依赖 SMTP、短信、OAuth。
3. 身份证明逻辑清楚：用户必须控制绑定邮箱。
4. 可立即上线，不影响现有账号、便签、附件数据。

### 2.4 用户必须能自行修改密码

管理员人工重置只能生成临时密码，不应成为用户长期密码。

因此本轮必须新增已登录用户的“修改密码”功能：

1. 用户输入当前密码。
2. 用户输入新密码和确认新密码。
3. 后端校验当前密码正确后，bcrypt 重哈希保存新密码。
4. 修改成功后当前会话保持登录。

## 3. 本轮目标

M10.7 做六件事：

1. 修改 `/forgot-password` 页面为“人工邮箱验证找回密码”说明页。
2. 页面明确管理员邮箱 `yan251@foxmail.com`，并提供邮件内容模板。
3. 管理员操作规范写入交付报告：核验发件邮箱，再用 M10.4 重置密码。
4. 新增已登录用户“修改密码”入口、页面/弹窗和 API。
5. 修改密码成功后，用户可用新密码登录，旧密码立即失效。
6. 保留 M10.6 自动重置代码，但生产默认不承诺自动发信。

## 4. 本轮不做

明确不做：

1. 不接 SMTP 服务商。
2. 不自建邮件服务器。
3. 不做短信找回。
4. 不做微信/OAuth 找回。
5. 不做自动发临时密码。
6. 不做用户自行改绑定邮箱。
7. 不删除 M10.6 代码。
8. 不新增数据库表。
9. 不做其它设备/session 全量下线。
10. 不做密码历史记录。
11. 不做密码强度评分器。

## 5. 用户流程

### 5.1 用户忘记密码

用户点击登录页“忘记密码？”后进入：

```text
/forgot-password
```

页面显示：

```text
请使用你账号绑定的邮箱发送邮件给管理员申请重置密码。

管理员邮箱：
yan251@foxmail.com

邮件标题：
PinNote 密码重置申请

邮件内容：
我的 PinNote 账号邮箱是：
我确认需要重置密码。
```

页面应提供：

1. 管理员邮箱展示。
2. 邮件标题展示。
3. 邮件模板展示。
4. “复制邮箱”按钮。
5. “复制邮件模板”按钮。
6. “返回登录”按钮。

### 5.2 用户发信要求

用户必须从账号绑定邮箱发出邮件。

例如用户账号邮箱是：

```text
user@example.com
```

则必须用 `user@example.com` 给 `yan251@foxmail.com` 发邮件。

如果用户用其他邮箱发信，管理员不能仅凭文字说明重置密码。

### 5.3 管理员处理流程

管理员收到邮件后：

1. 登录 PinNote 管理后台 `/admin/users`。
2. 搜索或查找邮件中的邮箱。
3. 确认发件邮箱与用户绑定邮箱完全一致。
4. 确认用户状态：
   - `active`：可以重置。
   - `disabled`：默认不重置，除非管理员先明确启用。
5. 使用 M10.4 的“重置密码”功能设置临时密码。
6. 回复用户邮件，告知临时密码。
7. 提醒用户登录后尽快修改密码。

### 5.4 用户修改密码

用户用临时密码或原密码登录后，可以从账号菜单进入：

```text
修改密码
```

修改密码表单包含：

1. 当前密码。
2. 新密码。
3. 确认新密码。

用户提交后：

1. 前端校验新密码至少 8 位。
2. 前端校验两次新密码一致。
3. 后端校验当前密码正确。
4. 后端 bcrypt 保存新密码。
5. 返回成功文案。
6. 用户保持当前登录状态。

成功后：

1. 旧密码登录失败。
2. 新密码登录成功。
3. 用户现有便签、附件、额度、角色、状态不变。

## 6. 安全规则

### 6.1 必须校验发件邮箱

管理员只能接受“发件邮箱 = 账号绑定邮箱”的请求。

不得接受以下情况：

1. 发件邮箱不是绑定邮箱，但正文声称是本人。
2. 用户只提供昵称、用户名、截图。
3. 朋友、同事、家人代发。
4. 未绑定邮箱的老账号自行申请。

### 6.2 临时密码要求

管理员设置的临时密码必须：

1. 至少 12 位。
2. 包含大小写字母和数字。
3. 不使用简单词、生日、手机号。
4. 不复用历史临时密码。

示例格式：

```text
Pn-202608-7KQm29xA
```

不要在文档或交付报告中记录真实临时密码。

### 6.3 老 admin 账号处理

如果老 `admin` 账号没有绑定邮箱，不走本流程。

`admin` 账号密码找回仍由服务器/数据库管理员线下处理，或后续单独做“管理员绑定邮箱”能力。

### 6.4 disabled 用户

disabled 用户默认不允许通过人工找回恢复密码。

如果确实要恢复，需要管理员先判断是否应启用该用户，再执行密码重置。

### 6.5 修改密码安全规则

修改密码必须满足：

1. 必须已登录。
2. disabled 用户即使持有旧 session，也不能修改密码。
3. 必须提供当前密码。
4. 当前密码错误返回 400/401，不能修改。
5. 新密码至少 8 位。
6. 新密码和确认新密码必须一致。
7. 成功后旧密码立即失效。
8. 响应不能返回 passwordHash。
9. 服务端日志不能记录明文密码。

## 8. API 与后端

本轮新增一个已登录用户修改密码 API。

### 8.1 新增 API

```text
POST /api/auth/change-password
```

请求：

```json
{
  "currentPassword": "old-password",
  "newPassword": "new-password"
}
```

响应成功：

```json
{
  "ok": true,
  "message": "密码已修改"
}
```

错误：

| 场景 | HTTP | error |
|---|---:|---|
| 未登录 | 401 | `UNAUTHORIZED` |
| disabled 用户 | 403 | `ACCOUNT_DISABLED` |
| 当前密码错误 | 400 或 401 | `INVALID_CURRENT_PASSWORD` |
| 新密码少于 8 位 | 400 | `PASSWORD_TOO_SHORT` |
| 请求体非法 | 400 | `INVALID_REQUEST` |

后端要求：

1. 使用当前 session 获取用户。
2. 必须重新查数据库用户状态，不能只信 session。
3. 使用 bcrypt compare 校验当前密码。
4. 使用 bcrypt hash 保存新密码。
5. 不返回 passwordHash。
6. 不写明文密码日志。
7. 修改成功后当前 session 保持有效。

### 8.2 保留 M10.6 API

建议：

1. `POST /api/auth/forgot-password` 可以保留，供未来 SMTP 配置后启用。
2. `/forgot-password` 页面本轮不调用该接口。
3. `POST /api/auth/reset-password` 保留，供未来自动 token 链路使用。
4. 不新增 schema，不迁移数据。

如果技术部认为保留接口会造成误调用风险，可以在交付报告里说明当前用户侧没有入口调用该接口。

## 10. 验收标准

### 10.1 UI 验收

1. 登录页“忘记密码？”入口存在。
2. 点击后进入 `/forgot-password`。
3. `/forgot-password` 显示管理员邮箱 `yan251@foxmail.com`。
4. 页面显示邮件标题和邮件正文模板。
5. “复制邮箱”可复制 `yan251@foxmail.com`。
6. “复制邮件模板”可复制完整模板。
7. “返回登录”可回到 `/login`。
8. 账号菜单存在“修改密码”入口。
9. 修改密码弹窗/页面包含当前密码、新密码、确认新密码。
10. 320px 宽度下 `/forgot-password` 和修改密码弹窗/页面均不横向溢出。

### 10.2 行为验收

1. `/forgot-password` 页面不再调用 `POST /api/auth/forgot-password`。
2. 页面不再承诺“系统会发送密码重置邮件”。
3. M10.6 的 `/api/auth/reset-password` 不受破坏。
4. 管理员仍可在 `/admin/users` 重置用户密码。
5. disabled 用户仍不能登录。
6. 旧 admin 用户名登录不受影响。
7. `/api/auth/change-password` 未登录返回 401。
8. disabled 用户调用 `/api/auth/change-password` 返回 403。

### 10.3 人工流程验收

用一个临时测试用户验证：

1. 创建或使用测试邮箱用户。
2. 管理员在 `/admin/users` 查到该邮箱。
3. 管理员重置临时密码。
4. 旧密码登录失败。
5. 临时密码登录成功。
6. 用户登录后修改为自己的新密码。
7. 临时密码再次登录失败。
8. 新密码登录成功。
9. 测试数据清理后 User / Note / Attachment / InviteCode / PasswordResetToken 数量回到基线。

### 10.4 修改密码验收

1. 当前密码正确 + 新密码合法 -> 200 `ok:true`。
2. 当前密码错误 -> `INVALID_CURRENT_PASSWORD`，密码不变。
3. 新密码少于 8 位 -> `PASSWORD_TOO_SHORT`。
4. 两次新密码不一致 -> 前端拦截，不发请求。
5. 修改成功后旧密码登录失败。
6. 修改成功后新密码登录成功。
7. 修改成功后当前页面不被强制登出。
8. 响应体不包含 passwordHash。
9. 用户 Note / Attachment / storageQuota / storageUsed / role / status 不变。

### 10.5 回归验收

1. 登录页正常。
2. 注册页正常。
3. 管理员用户列表正常。
4. 管理员重置密码正常。
5. 普通用户便签列表正常。
6. 邀请制注册不退化。
7. 忘记密码页面移动端正常。

## 13. 回退方案

本轮不改 schema，回退简单。

如页面异常：

1. 回退前端代码到 M10.6。
2. `npm run build`。
3. 重启服务。
4. 确认 `/login`、`/forgot-password`、`/admin/users` 正常。
