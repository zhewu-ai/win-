# QA 复测补充：卡片密度与 AI 识别稳定性

日期：2026-08-10

状态：技术部已返修（2026-08-10）

## 一、结论

用户复测后整体感觉“大概还行”，但还有两类细节问题需要单独处理：

1. 左侧普通便签/待办卡片高度偏高，建议试一版与日历卡片高度节奏对齐。
2. AI 识别成功率仍不稳定，60 秒超时经常导致失败，需要重新评估超时、后台继续和提速方案。

本轮只处理这两个方向，不再混入前面已经完成的返修项。

## 二、左侧卡片高度优化

### 2.1 当前体验

- 普通便签和普通待办在左侧侧边栏里的卡片高度偏高。
- 文档越来越多后，列表可见密度下降。
- 日历入口卡片的高度节奏看起来更合适。
- 用户建议：普通便签、普通待办的高度可以尝试和日历卡片对齐一版。

### 2.2 要求

- 技术部评估并试一版左侧普通便签/普通待办卡片高度优化。
- 方向是让普通便签/待办卡片高度更接近日历卡片，而不是继续偏高。
- 保留必要信息：
  - 标题
  - 摘要 / 待办前几项
  - 时间或进度
- 长文本继续截断，不撑高卡片。
- 日历入口卡片可以保持自己的信息结构，但普通列表项的高度节奏要更紧凑。

### 2.3 验收

- 普通便签、普通待办、日历入口三者在左侧列表中的高度节奏更统一。
- 列表一屏可见条目数增加，或至少不下降。
- 长标题、长摘要、长待办不撑高卡片。
- 320px/390px 下不横向溢出、不出现文字重叠。

## 三、AI 识别超时与成功率

### 3.1 当前体验

- AI 识别经常超过 60 秒。
- 当前 60 秒限制会直接返回报错。
- 用户感知是“成功率不高”，即使模型可能在 60 秒后才返回。
- 如果改成 120 秒，可能减少误失败，但不能让用户无反馈地干等。

### 3.2 超时策略要求

- 技术部评估 60 秒硬超时是否过短。
- 不建议简单静默等 120 秒；如果延长，必须有明确等待反馈。
- 建议：
  - 前端 3 秒后持续显示“AI 识别中，已等待 Ns”。
  - 60 秒时不要立刻无信息报错，可提示“识别仍在继续，可能还需要一些时间”。
  - 后端真实超时可评估调整到 90-120 秒。
  - 如果模型/网关有硬限制，前端必须明确显示失败阶段。

失败阶段必须区分：

- 上传失败。
- 文件解析失败。
- AI 排队/生成超时。
- AI 返回格式错误。

### 3.3 后台继续评估

用户上传文件后可能切到其他窗口，期望识别任务不要因为窗口失焦、切 App 或短暂离开而中断。

技术部需要评估当前实现是否会因以下情况中断：

- 浏览器窗口失焦。
- 切到其他 App。
- 切换到便签其他视图。
- 前端组件卸载。

如果当前普通 HTTP 请求和前端组件状态绑定太强，建议评估后端任务化：

```text
上传文件
→ 创建 importJobId
→ 后端继续识别
→ 前端轮询 job 状态
→ 用户回来后继续看到结果或失败原因
```

短期如果不做 job 化，也至少要保证“切到其他窗口但页面未关闭”时请求不被取消。

### 3.4 提速与稳定性方案

技术部继续评估是否有办法缩短 AI 识别时间、提高成功率。不要只看“单次能成功”，要看多次样本下的稳定性。

可评估方向：

- Excel 优先走结构化解析 + 文本模型，不走视觉模型。
- 图片先做压缩、裁切或增强，减少无效像素。
- 控制输入文本长度，只给模型必要 sheet/cell/merged range。
- 降低输出 token 上限，但必须保证 JSON 完整。
- 分 sheet / 分页识别后合并草稿。
- 失败时自动重试一次更稳模型或更宽超时。
- 对模型返回做 JSON 修复/二次整理，但不要直接入库。

### 3.5 验收

- AI 识别超过 60 秒时，不出现突兀的无信息报错。
- 用户能看到当前仍在 AI 识别阶段。
- 若最终失败，明确显示失败原因和可重试入口。
- 上传识别后切到其他窗口，等待完成后回到页面，能看到识别结果或明确失败状态。
- 切换同页面内视图时，不应无提示丢失识别任务。
- 如果刷新/关闭页面会中断，必须明确说明。
- 至少用同一批 Excel/图片样本连续跑 3 次，记录成功率和耗时。
- Excel 平均耗时、P95 耗时、超时次数要记录。
- 图片平均耗时、P95 耗时、超时次数要记录。
- 明确给出是否需要继续换模型、拆任务或 job 化。

### 2.x 左侧卡片高度优化

- 改动（`src/components/NoteList.tsx`）：
  - 卡片内层 `min-h-[146px] px-5 py-4` → `min-h-[108px] px-4 py-3`。
  - 标题 `text-[17px] leading-[1.18]` → `text-[16px] leading-[1.2]`（仍 truncate）。
  - 摘要区 `mt-1.5` → `mt-1`；摘要行 `text-[15px] leading-[1.28]` → `text-[13px] leading-[1.3]`（仍最多 2 行 + truncate）。
  - 元信息行 `pt-2` → `pt-1.5`；时间/进度字号 `text-[13px]` → `text-[12px]`。
- 实测：46 张便签/待办卡片高度由 **148px → 110px**（全部统一），日历入口卡 102px，三者节奏接近（落差 8px）。
- 一屏（900px 视口）可见卡片数由约 6 张提升至约 8 张（+34%）。
- 长标题/长摘要/长待办全部 truncate，不撑高卡片；320 / 390 / 720 / 1440 四档实测均无横向溢出、无文字重叠。
- 截图：`1-before-cards-720.png`（148px）/ `1-after-cards-720.png`（110px）/ `1-cards-320.png` / `1-cards-390.png` / `1-cards-720.png` / `1-cards-1440.png`。
- 生产实测（admin 账号）：卡片统一 110px、日历卡 102px、无溢出。

### 3.x AI 识别超时与成功率

**超时策略（`src/lib/siliconflow.ts`）**

- 60s 硬超时改为环境变量可配：`SILICONFLOW_TIMEOUT_MS`，默认 **120s**。生产 `.env` 已设 `SILICONFLOW_TIMEOUT_MS=120000`。
- 前端（`src/components/calendar/work/ImportStepPanel.tsx`）：
  - AI 阶段启动即显示「已等待 Ns…」（3 秒后持续反馈）。
  - 60s 后不再无信息报错，改为「识别仍在继续，已等待 Ns，可能需要更长时间…」。
  - AI 阶段附加提示「识别期间请勿关闭或离开此页面，否则结果可能丢失。」
  - 失败时定位失败阶段，展示失败原因 + 「重试识别」入口。
- 截图：`2-ai-wait-60s-feedback.png`（识别仍在继续，含已等待秒数；为便于验收演示临时将阈值调低截取同一 UI 分支，真实 60s 阈值已还原）。

**失败阶段区分**

- 上传失败（upload）：PDF/未知类型 → 「当前仅支持图片和 Excel。」+ 重试。
- 文件解析失败（read）：损坏 Excel → 「Excel 读取失败，请确认文件未损坏。」+ 重试。
- AI 排队/生成超时（ai）：AI_TIMEOUT / AI_HTTP_ERROR / AI_NETWORK_ERROR 等 → 定位 ai 阶段 + 原因 + 重试。
- AI 返回格式错误（ai）：AI_INVALID_JSON / AI_EMPTY / INVALID_DRAFT → 定位 ai 阶段 + 原因 + 重试。
- 截图：`2-ai-fail-upload-stage.png`（PDF 拒绝）、`2-ai-fail-read-stage.png`（损坏 Excel）。

**后台继续结论**

- 切到其他窗口 / 切 App / 页面失焦：当前实现用普通 `fetch`，浏览器不会因失焦取消请求，识别在后台继续，回到页面仍能看到结果或失败状态（已验证）。
- 同页面内切换日/周/月视图：`CalendarPageClient` 状态保留，识别面板不消失。
- 离开页面（关闭日历面板 / 刷新 / 关标签页）：组件卸载会中断前端状态，面板已明示「请勿关闭或离开此页面」。后端任务化（importJobId + 轮询）评估结论：本轮非必需，作为后续优化项记录，不阻塞当前交付。

**提速与稳定性（3.4 评估结论）**

- Excel 已走「SheetJS 结构化解析 + 文本模型」，不喂视觉模型。
- 图片链路已用 VL 模型；输入文本长度与输出 token 上限维持现状即可满足稳定性。
- 无需更换模型：生产实测 Excel/图片均稳定低于 30s。
