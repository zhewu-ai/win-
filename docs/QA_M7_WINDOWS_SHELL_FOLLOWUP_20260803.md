# M7 Windows 壳复验问题单：置顶、极小模式、图片删除

日期：2026-08-03

结论：不通过，需要继续修复。

当前 Windows App 已能通过 GitHub 封装运行，说明“壳能启动”已经跑通。但 M7 的核心价值是桌面置顶悬浮便签，目前仍有关键缺口。

## 1. QA-M7-F01：应用无法置顶

严重级别：P0

用户现象：

- Windows App 可以打开。
- 但窗口无法保持在其他软件前方。
- 这直接阻断 M7 的核心目标：把便签贴在桌面上处理反馈。

当前代码线索：

- Tauri 侧已有命令：
  - `src-tauri/src/lib.rs`
  - `open_floating_note`
  - `toggle_always_on_top`
  - `get_always_on_top`
- 前端封装：
  - `src/lib/tauri.ts`
  - `toggleAlwaysOnTop`
  - `getAlwaysOnTop`
- 悬浮页按钮：
  - `src/app/notes/[id]/floating/FloatingNoteClient.tsx`
  - 只在 `isTauri()` 为真时显示窗口置顶按钮。

需要技术部重点排查：

1. Windows 打包后的环境中，`isTauri()` 是否真的返回 `true`。
2. 悬浮页的“窗口置顶”按钮是否可见。
3. 点击置顶按钮时，`toggle_always_on_top` 是否被成功 invoke。
4. invoke 失败时不能静默吞掉，需要至少在开发/调试环境输出错误。
5. Tauri 权限/capability 是否允许前端调用自定义 command。
6. `set_always_on_top(true)` 是否作用在正确窗口上，而不是主窗口/错误窗口。
7. 悬浮窗口打开时 `.always_on_top(true)` 是否在 Windows 环境实际生效。

产品要求：

- 悬浮便签窗口默认置顶。
- 用户可以手动取消置顶。
- 用户可以再次打开置顶。
- 主窗口可以不默认置顶，但至少悬浮便签必须可置顶。

验收标准：

1. 打开 Windows App。
2. 从某条便签打开悬浮窗口。
3. 打开 AE/C4D/浏览器/资源管理器等其他软件。
4. 悬浮便签仍停留在最前。
5. 点击“取消置顶”后，悬浮便签可以被其他窗口遮挡。
6. 再点击“置顶”后，悬浮便签重新保持最前。
7. 关闭悬浮窗口并重新打开，置顶状态按上次设置恢复。

## 2. QA-M7-F02：缺少极小模式/侧边栏隐藏模式

严重级别：P0

用户现象：

- 当前 App 更像完整网页窗口。
- 没有一个非常小、适合长期挂在桌面上的模式。
- 用户希望有“侧边栏隐藏”的极小模式。

产品判断：

M7 不能只做“Web 套壳打开主站”。如果没有极小模式，即使 App 能运行，也不像桌面便签。

需要实现的模式：

### 2.1 主窗口完整模式

用于管理便签：

- 有列表侧边栏。
- 有搜索。
- 有回收站/归档等管理入口。

### 2.2 极小/悬浮模式

用于工作时贴在桌面上：

- 不显示侧边栏。
- 只显示当前单条便签。
- 宽度 320px 到 420px 可用。
- 顶部工具栏保持一行，不换行、不竖排。
- 保留核心操作：
  - 编辑标题/正文或待办
  - 切换便签/待办
  - 图片上传
  - 图片删除
  - 置顶开关
  - 返回主窗口或打开主窗口

建议实现方向：

1. 优先使用现有 `/notes/:id/floating` 作为极小模式页面。
2. 主编辑页需要有明确按钮：`以悬浮窗打开` 或 `极小模式`。
3. 如果用户在主窗口内点击极小模式：
   - Tauri 环境：打开独立悬浮窗口。
   - 普通 Web 环境：跳转或新开 `/notes/:id/floating`。
4. 不要让用户靠手动缩小主窗口来模拟极小模式。

验收标准：

1. 在主窗口选中一条便签。
2. 点击“极小模式/悬浮窗”。
3. 出现一个无侧边栏的小窗口，只显示单条便签。
4. 小窗口宽度调到 320px 后仍可编辑。
5. 小窗口中待办、图片、置顶等核心操作可用。
6. 主窗口和小窗口不能互相抢焦点到不可操作。

## 3. QA-M7-F03：图片无法单独删除

严重级别：P0

用户现象：

- 图片可以附加到便签里。
- 但无法对某一张图片单独删除，或删除入口不可见/不可用。

当前代码线索：

- 图片展示组件：
  - `src/components/ImageAttachments.tsx`
- 删除接口：
  - `DELETE /api/notes/:id/attachments/:attachmentId`
  - `src/app/api/notes/[id]/attachments/[attachmentId]/route.ts`
- M3 规格已经明确要求“支持删除图片附件”。

需要技术部重点排查：

1. 删除按钮是否只在 hover 时出现，导致 Windows 小窗口/触控板/窄窗口下用户看不到。
2. 图片预览层里是否缺少删除入口。
3. 悬浮页 `/notes/:id/floating` 是否也正确传入 `noteId` 和 `attachments`。
4. 删除接口是否返回 401/404/500，但前端只弹“删除图片失败”，没有足够调试信息。
5. 删除后前端状态是否更新。
6. 删除后刷新页面，图片是否真的消失。
7. 本地文件路径 `UPLOAD_DIR + storagePath` 是否正确，避免 DB 删除了但文件还在，或接口报错。

产品要求：

- 每张图片必须有明确、可发现的删除入口。
- 删除某张图片不能删除整条便签。
- 删除后该图片应立即从当前便签消失。
- 刷新后仍然消失。
- 主编辑页和悬浮极小页都要支持单图删除。

验收标准：

1. 上传 3 张图片到同一条便签。
2. 删除第 2 张图片。
3. 第 1、3 张仍保留，第 2 张立即消失。
4. 刷新页面后，第 2 张仍不存在。
5. 在 `/notes/:id/floating` 极小模式中重复以上流程，也必须通过。
6. 删除失败时给出明确错误提示，技术调试环境要能看到 HTTP 状态码和接口错误。

## 4. 本轮修复边界

本轮只修这三个问题：

1. 置顶能力真正可用。
2. 极小/悬浮模式真正可用。
3. 图片可单独删除。

本轮不要扩展：

1. 不做邮箱注册/登录。
2. 不做多用户权限重构。
3. 不做图片排序。
4. 不做图片标注/OCR。
5. 不做 Mac 壳。
6. 不做离线同步。

## 5. 技术部交付时必须提供的证据

1. Windows App 安装包或可执行包。
2. Windows 实机录屏或截图，证明悬浮窗口置顶在其他软件前方。
3. 置顶开关打开/关闭的录屏或说明。
4. 极小模式入口截图。
5. 320px 左右小窗口截图。
6. 上传 3 张图、删除其中 1 张、刷新后仍删除的录屏或接口日志。
7. `npm run build` 通过。
8. Tauri 打包命令通过。

## 6. 通过标准

这轮通过标准很简单：

> Windows 上可以把一条便签以极小窗口置顶在桌面上，同时该窗口里能正常编辑文字/待办并单独删除图片。

如果这句话不能完整成立，M7 就还没有通过。
