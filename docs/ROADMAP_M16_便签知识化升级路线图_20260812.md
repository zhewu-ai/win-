# ROADMAP M16：便签知识化升级路线图

日期：2026-08-12

状态：产品路线图草案，供技术部拆阶段评估

## 一、背景

当前产品已经从最初的轻便签，逐步加入了待办、图片附件、内部便签链接、工作日历、AI 排期导入和桌面壳能力。

下一阶段需要回答一个核心问题：

```text
便签未来只是一个简单记录工具，还是要逐步成为个人/团队资料库与工作助手？
```

产品判断：可以往资料库和 AI 助手方向演进，但不能直接跳到完整语雀、Notion 或 Obsidian。下一阶段应先把“记录”和“整理”的基础能力打稳。

## 二、总体方向

建议把后续方向定义为：

```text
苹果备忘录式轻编辑 + Obsidian 式组织关系 + 工作日历/AI 助手
```

含义：

1. 普通用户不需要学习 Markdown。
2. 编辑体验像苹果备忘录，提供少量必要按钮：标题、加粗、列表、待办、图片、引用、分割线。
3. 熟悉 Markdown 的用户可以使用快捷输入，但 Markdown 只是底层兼容能力，不是唯一使用方式。
4. 便签和待办不再强行分成两种互斥内容类型，待办应成为便签正文里的 checklist block。
5. 保留并强化现有内部便签链接，未来支持标签、反向链接、关系图。
6. 工作日历和 AI 不独立发展，而是利用便签资料库：从资料、排期、节点、项目关系里理解用户工作。

## 三、产品形态演进

### 阶段 0：当前基础

已经具备：

- 便签 CRUD。
- 待办模式。
- 图片附件。
- 内部便签链接。
- 工作日历。
- AI 排期导入。
- Web + Windows/macOS 桌面壳基础。

当前限制：

- 便签和待办是两套编辑体验，切换会遇到图片、排版、结构化内容如何转换的问题。
- 图片主要是附件，不是正文里的内容。
- 内链已有基础，但还不是完整知识关系系统。
- 标签、反向链接、知识图谱还没有。
- AI 主要服务于排期导入，还没有深入理解便签资料库。

### 阶段 1：统一“便签/待办”为文档内容

目标：解决便签模式和待办模式割裂的问题。

建议定义：

```text
一条内容 = 一篇便签文档
待办 = 文档中的 checklist block
```

用户仍可以看到“新建便签 / 新建待办”两个入口，但它们只是不同创建模板：

- 新建便签：创建空文档。
- 新建待办：创建一篇默认带 checklist block 的文档。

不再做“便签转待办 / 待办转便签”的硬切换。旧待办迁移为一篇带 checklist 的便签；旧普通便签迁移为普通文本块。

### 阶段 2：轻富文本编辑

目标：让便签不再显得简陋，但不做完整重型文档系统。

P0 能力：

- 标题 / 正文样式。
- 加粗 / 斜体。
- 无序列表 / 有序列表。
- checklist block。
- 引用。
- 分割线。
- 内部便签链接。
- 外部 URL。
- 图片插入正文。

P1 能力：

- 简单表格，必须按钮式操作，不要求用户写 Markdown 表格。
- 图片基础缩放或查看大图。
- 只读网页粘贴卡片或干净文本粘贴。

暂不做：

- 多人协同编辑。
- 完整 Notion/语雀 block 系统。
- 任意字体、字号、颜色、复杂样式。
- 复杂表格合并单元格、公式、筛选。
- 网页剪藏器。

### 阶段 3：标签与轻量收纳

目标：当便签数量变多后，用户可以主动整理。

建议同时保留两种组织方式，但分阶段上线：

1. 文件夹/分组：一条便签最多属于一个文件夹，适合“工作 / 生活 / 客户项目”等稳定分类。
2. 标签：一条便签可多个标签，适合“#单针 / #美术 / #客户A / #待交付”等灵活状态。

优先级建议：

- 先做单层文件夹，降低学习成本。
- 再做标签，支持 `#标签` 输入识别和标签筛选。
- 颜色只作为视觉标记，不作为唯一分组方式。

### 阶段 4：互链、反向链接、关系视图

目标：学习 Obsidian 的组织能力，但不要复制它的复杂度。

建议能力：

- `[[便签名]]` 搜索并插入内部链接。
- 当前便签底部显示“被这些便签引用”。
- 坏链扫描：目标便签被删除后提示。
- 链接建议：输入时根据标题、标签、最近使用推荐。
- 关系图视图：展示便签、标签、项目、排期之间的连接。

关系图不要第一阶段做。必须先保证数据关系真实可靠，否则只会是视觉特效。

### 阶段 5：资料库驱动的 AI 助手

目标：AI 不只是帮忙识别排期，而是能基于用户自己的资料回答问题、整理内容、生成计划。

建议能力：

- 对选中便签做总结。
- 从多条便签生成待办。
- 从项目资料生成排期草稿。
- 根据工作日历和便签内容提示节点风险。
- 支持“这个项目今天提前交一版”这类自然语言修改排期。
- 基于标签/文件夹/项目限定 AI 读取范围。

前提：

- 便签正文结构稳定。
- 图片和附件存储方案明确。
- 权限、分享、日志脱敏成熟。
- AI 请求不泄漏全文、key、base64、隐私内容到日志。

### 阶段 6：分享与外部访问

目标：用户能把便签、排期或资料页分享给别人。

建议从只读分享开始：

- 分享单条便签。
- 分享一个项目页。
- 分享一个排期摘要。
- 支持取消分享。
- 后续再加密码、有效期、访问次数限制。

暂不做：

- 多人共同编辑。
- 评论协作。
- 团队权限矩阵。

### 阶段 7：存储与成本优化

如果未来支持大量图片、文件、富文本资料库，不能长期依赖小服务器本机磁盘和带宽。

建议优先路线：

1. 对象存储：Cloudflare R2、腾讯 COS、阿里 OSS、S3、Backblaze B2。
2. 本机服务器只保存数据库、权限、索引和签名 URL。
3. 图片走压缩、缩略图、懒加载。
4. 分享文件走对象存储 CDN 或限时签名 URL。

暂不建议第一阶段做：

- P2P / 类种子传输。
- IPFS。
- 用户之间互传文件。
- 直接把某台 Mac 当默认服务器。

原因：隐私、安全、在线率、权限控制和排障成本太高。Mac 常开访问可以作为高级个人模式，但不应作为默认产品路线。

## 四、推荐版本节奏

### M15 收尾：桌面壳下载与入口

目标：让已经做出来的 Windows/macOS 壳有正式下载路径。

范围：

- 下载页支持 Windows 和 macOS。
- 下载链接不要固定历史版本。
- 桌面壳内增加“打开网页版 / 官网”入口。
- 版本号、Release、下载页一致。

### M16R1：统一文档块模型

目标：便签和待办不再强行分裂。

范围：

- 新建便签 / 新建待办仍保留。
- 底层逐步统一为文档。
- 待办成为正文 checklist block。
- 旧数据迁移方案先设计清楚。
- 不急着做完整图片正文、表格、知识图谱。

### M16R2：轻富文本编辑

目标：让普通用户不懂 Markdown 也能排版。

范围：

- 基础格式工具栏。
- Markdown 快捷输入可选。
- 图片插入正文。
- 旧便签渲染兼容。
- 320px / 390px 工具栏收纳。

### M16R3：文件夹和标签

目标：便签数量增长后可整理。

范围：

- 单层文件夹。
- `#标签` 识别。
- 标签筛选。
- 左侧列表新增组织视角。

### M16R4：互链增强和反向链接

目标：让便签之间形成资料关系。

范围：

- `[[便签名]]` 插入体验升级。
- 反向链接。
- 坏链提示。
- 链接建议。

### M17：知识图谱和 AI 深化

目标：基于稳定关系数据做可视化和 AI 助手。

范围：

- 关系图。
- 项目/便签/排期联动。
- AI 问答和整理。
- 自然语言调整排期。

## 五、关键原则

1. 不让用户必须学习 Markdown。
2. 不再强依赖“便签/待办二选一”的内容类型。
3. 新入口可以保留，底层模型逐步统一。
4. 图片一定要纳入长期规划，但不要在没有存储方案时盲目放开大文件。
5. 标签、互链、图谱必须建立在稳定数据关系上。
6. AI 深化必须先有可靠资料库，否则只会变成普通聊天入口。
7. 每一阶段都要能独立交付、独立回滚。

## 六、暂不做清单

下一阶段不要一次性做：

- 完整 Obsidian。
- 完整 Notion/语雀。
- 多人协同文档。
- P2P 文件传输。
- 自建网盘。
- 复杂权限系统。
- 全文 RAG 问答。
- 知识图谱动画。

这些可以作为远期方向，但 M16 第一阶段必须先解决内容模型和编辑体验。

## 七、给技术部的总要求

技术部在正式开工前，需要先给出：

1. 当前便签/待办数据模型审计。
2. 旧便签、旧待办、图片附件、内部链接的迁移方案。
3. 轻富文本编辑器技术方案，优先评估继续扩展现有 Tiptap。
4. 搜索、同步、离线、桌面壳兼容影响说明。
5. 回滚方案，确保失败时旧数据不丢。
6. P0 验收清单和截图要求。
