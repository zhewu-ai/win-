# M16R1 设计方案：统一便签/待办与轻富文本基础

日期：2026-08-13
来源：`docs/SPEC_M16R1_统一便签待办与轻富文本基础_20260812.md`
状态：技术评估稿（待拍板后进入实现）

## 〇、结论摘要

当前「text 便签」与「checklist 待办」是**两套互斥存储 + 两个互斥编辑器**，切换时 `textToChecklist`/`checklistToText` 做数据转换，这就是 SPEC 要消除的结构问题。

建议走 **方案 B-lite**：新增 `note.documentJson` 作为**唯一权威结构**（Tiptap JSON，多块：段落 + checklist 块 + 后续 heading/引用/分割线），`content`（纯文本投影）与 `checklistItems`（扁平投影）在保存时**同步生成**，因此搜索、左侧列表预览、离线层、桌面壳、旧数据打开**全部零改动**。旧数据（`documentJson` 为空）打开时按需从 `content`/`checklistItems` 生成，保存即升级；回滚 = 忽略 `documentJson` 回旧编辑器，数据字段始终完整。

编辑器从「单 noteText 块」升级为「多块文档」，checklist 块复用现有 `ChecklistRow` 的行渲染逻辑（每行本就是 singleLine `LinkEditor`，天然支持内链/URL/`[[` 搜索），不重写编辑器内核。

## 一、现状梳理（侦察结论）

### 1.1 数据模型（`prisma/schema.prisma:98-127`，`src/types/index.ts:41-64`）

| 字段 | 含义 | 现状 |
|---|---|---|
| `content` | 纯文本正文 | text 模式唯一正文源；`\n`=换行，内链 `[[note:id\|title]]`，URL 为纯文本 |
| `mode` | `"text" \| "checklist"` | 编辑器互斥渲染开关 |
| `checklistItems` | JSON 数组（扁平行） | checklist 模式唯一正文源；行 `{kind:todo\|heading, text, checked, sortOrder, ...}` |
| `checklistGroups` | JSON 数组（旧分组） | 已由 `normalizeChecklist` 扁平化迁移，空数组为主 |
| `attachments` | 独立 Attachment 表 | 图片在正文**下方**独立区块，不在正文里 |

### 1.2 两套编辑器

- **text**：`LinkEditor`（`src/lib/note-text-schema.ts`）——Tiptap **单块** `Document{content:"noteText"}`，内联 = text/hardBreak/noteLink 原子节点；URL 用装饰插件画蓝；`serialize(parse(text))===text` 恒等 round-trip。
- **checklist**：`ChecklistEditor`（`src/components/ChecklistEditor.tsx`）——React 行列表（active + completed 两区），**每行 = singleLine `LinkEditor`**（已支持内链/URL/`[[` 搜索/多行粘贴拆行/回车新增/拖拽排序/小标题行）。

**关键复用点**：两种编辑器的内联层是**同一个** `LinkEditor` + `note-text-schema`。checklist 行与正文段落共享内链芯片、URL 装饰、`[[` 建议浮层。

### 1.3 模式切换 = 数据转换（问题根源）

`NoteEditor.tsx:535-552`：text→checklist 用 `textToChecklist(content)` 拆行；checklist→text 用 `checklistToText(...)` 拼行。未来加入图片/表格/复杂块后这种双向转换必然丢数据。SPEC 明确要求消除。

### 1.4 创建入口（`Sidebar.tsx:178-187` → `useNotes.ts` → `persist.ts`）

只有「新建便签」一个按钮，POST 不带 mode → 默认 `mode:"text"`、空 content。**没有「新建待办」入口**（SPEC 要求保留双入口）。

### 1.5 搜索与列表预览

- 服务端搜索（`src/app/api/notes/route.ts:37-43`）：`q` 对 `title`/`content`/`checklistItems`(JSON 字符串) `contains`，**已覆盖 checklist**。
- 列表预览（`NoteList.tsx` `getAutoTitle`/`getSummaryLines`）：text 取前 2 行，checklist 取前 2 项加 ✓/○。
- **不一致点**：`InsertNoteLinkDialog`/`InlineNoteLinkSuggest` 只搜 `title` 或 `mode!==checklist && content`——checklist 便签按 items 文本搜不到，需在 M16R1 修齐。

### 1.6 离线层（`src/lib/offline/{db,persist,sync,draft}.ts`）

`LocalNote` 已含 `content/mode/checklistItems/checklistGroups` 全字段；`sync.ts` `PATCH_FIELDS` 覆盖这四字段。新增 `documentJson` 只需照此扩展。

### 1.7 桌面壳（`src-tauri/src/*`）

纯 WebView 壳（URL 白名单、外链、窗口置顶/几何），对 `content/checklistItems` **零读写**，只做 HTTP 代理。**M16R1 无壳侧改动**，壳内表现 = 浏览器表现。

## 二、目标数据模型（方案 B-lite）

### 2.1 新增字段

```prisma
model Note {
  ...
  content        String   @default("")   // 纯文本投影（保留，语义 = 全部可见文本行）
  mode           String   @default("text") // 仅作旧数据兼容与降级展示，不再驱动编辑器互斥
  checklistItems String   @default("[]") // 扁平投影（保留）：全部 checklist 块的行
  checklistGroups String  @default("[]") // 保留空数组
  documentJson   String?                  // 新增：Tiptap JSONContent，权威结构
}
```

### 2.2 块 schema（`note-text-schema.ts` 升级）

```
doc
 ├─ paragraph  = 现有 noteText（group:block, inline*: text|hardBreak|noteLink）——复用不改
 ├─ checklistBlock（block，attrs.rows: ChecklistItem[] JSON；ReactNodeView 渲染 ChecklistRow 列表）
 ├─ heading    （P1：小标题块，attrs.text，block）
 ├─ divider    （P1：分割线，leaf block）
 └─ quote      （P1：引用，block，inline*）
```

- `checklistBlock` 的行存 **attrs.rows**（JSON），不建子节点——复用现有 `ChecklistItem`/`normalizeChecklist`/排序/勾选逻辑，行内编辑仍走 singleLine `LinkEditor`（内链/URL/`[[` 免费获得）。
- 编辑器从 `Document.extend({content:"noteText"})` 改为 `content: "block+"`（段落 / checklist 块混排），`Enter` 在段落内 → hardBreak（保持现行为），在块间 → 新建段落。

### 2.3 投影定义（保存时同步生成）

- `content` = 各块文本行拼接：段落行 + checklist 行（todo 前缀 `[ ]`/`[x]`，heading 行前缀 `# `）；块之间用空行分隔。旧单块正文无空行边界 → 解析仍为一个段落。
- `checklistItems` = 全部 checklist 块的 `rows` 扁平合并（保持现有行形状）。
- **权威性**：编辑一律基于 `documentJson`；`content`/`checklistItems` 是**派生投影**，仅供搜索/列表/AI/旧端展示，永不反向重建新文档。

### 2.4 不变式变化

旧不变式 `serialize(parse(content))===content` 仅对**旧文档**（documentJson 为空）成立。新文档投影允许丢装饰（加粗/斜体等 mark 不投影），因为编辑回读走 documentJson 而非投影——投影只保证「文本可读、可搜、可预览」。

## 三、编辑体验设计（对应 SPEC P0 验收）

### 3.1 统一创建入口语义

- 「新建便签」→ 创建 `doc{paragraph(空)}`。
- 「新建待办」→ 创建 `doc{checklistBlock(1 空行)}`。
- 两入口都在 `Sidebar` 提供（沿用「新建」按钮旁或下拉），底层都走统一 POST（`documentJson` 初始化），`mode` 字段按旧兼容填（待办填 `"checklist"`，保留列表旧展示逻辑）。

### 3.2 checklist 块交互（全部沿用 ChecklistEditor 现有能力）

- 插入 checklist 块（工具栏按钮 / `/` 命令可选）；块内新增行、勾选/取消、删行、回车新增、多行粘贴拆行、已完成折叠区、拖拽排序。
- 段落 ↔ checklist 块相邻可连续输入；在块内最后一行按 Enter 在空行上 → 退出块插入新段落。
- 已完成项显示清晰但不占过多空间（沿用折叠区）。

### 3.3 内链 / 外链 round-trip（不回归）

- `[[note:id|title]]` 语法、`escapeLinkTitle` 转义、`NoteLinkView` 芯片、`[[` 搜索浮层、URL 装饰、壳内 `openExternal`——全部复用，不受多块化影响（checklist 行编辑器未变）。
- **修一致性**：`InsertNoteLinkDialog`/`InlineNoteLinkSuggest` 的搜索范围改为与主搜索一致（title + content 投影，即自然覆盖 checklist 文本）。

### 3.4 P1 工具栏雏形（最小集）

- 块级：段落、小标题、引用、分割线、待办（插入 checklist 块）、插入内链。
- 字符级（mark，仅 documentJson 存、不投影）：加粗、斜体。
- 320/390px：沿用三档 toolbarMode 收纳；新增按钮进「更多」菜单。

## 四、迁移与回滚策略

### 4.1 迁移（懒迁移 + dry-run）

1. **懒迁移**：打开旧文档（`documentJson == null`）时前端按 `mode` 生成：
   - text → `doc{paragraph(parseNoteText(content))}`
   - checklist → `doc{checklistBlock(normalizeChecklist(items, groups))}`
   生成后随下次保存写 `documentJson`（一次写入，不批量）。
2. **dry-run 脚本**（可选用，`scripts/m16-migrate-dryrun.ts` 或临时 route）：遍历 DB 统计「无 documentJson 的 text/checklist 各多少、能否解析、预计生成块数」，不写库。
3. **备份**：任何涉及 `documentJson` 的批量操作前 `cp data/prod.db backups/prod_M16R1_<ts>.db`。

### 4.2 回滚

- 前端 feature 开关：关闭即回旧双模式编辑器，读 `content`/`checklistItems`（**两字段始终完整，是投影的主战场**），`documentJson` 被忽略。
- 由于投影字段始终同步写，回滚不会丢任何旧功能可见的数据；仅新块的格式（如引用/分割线）在回滚后按投影显示为普通文本行，不丢失文字。

## 五、搜索 / 自动保存 / 离线 / 桌面壳影响

| 面 | 影响 | 动作 |
|---|---|---|
| 服务端搜索 | `content` 投影已含全部文本 | 无需改；`checklistItems` 字符串 contains 保留 |
| 列表预览 | `getAutoTitle`/`getSummaryLines` 读投影 | 无需改（投影保持现有格式） |
| 自动保存 | PATCH 增加 `documentJson` | `allowedFields` + `validate`（JSON 大小上限） |
| 离线层 | `LocalNote` 增 `documentJson`；`PATCH_FIELDS` 补字段 | 照现有字段扩展，双向映射 |
| 草稿镜像 | `draft.ts` 增字段 | 照现有扩展 |
| 桌面壳 | 纯 WebView | 无改动；壳内=浏览器行为 |

安全/合规：`UserActivityLog` 禁止记录标题/正文/待办文字（现有限制不变）；`documentJson` 不写入日志、不 base64、不记录密钥。

## 六、风险与决策点

### 风险

- **多块化重构面**：`parseNoteText`/`serializeNoteText`/`LinkEditor` 的单块假设要放宽（`doc.firstChild`、Enter 插 hardBreak、粘贴解析）。已识别具体改动点，属可控局部重构（评分 ~6）。
- **投影格式定义**：`content` 引入空行=块边界，需与旧数据（无空行=单块）兼容，解析器按「documentJson 为空才走旧路径」分流。
- **mark 不投影**：加粗/斜体只在 documentJson，投影剥 mark——需明确这是设计而非缺陷（编辑回读走 documentJson）。

### 决策点（需用户拍板）

1. **数据模型**：方案 B-lite（新增 `documentJson`，推荐）vs 方案 A 兼容层（不新增字段，只改 `content` 序列化容纳块）vs 本轮纯设计。
2. **落地范围**：M16R1 完整落地（多块编辑器 + 新建待办 + checklist 块 + P1 工具栏雏形，推荐）vs M16R1 只做设计 + 新建待办入口（checklist 块留 M16R2）。
3. **`mode` 字段**：保留仅作兼容（推荐）vs 彻底移除（需额外迁移）。
4. **P1 工具栏**：段落/小标题/引用/分割线/待办/内链 + 加粗斜体（推荐）vs 不含 mark。

## 七、实现顺序（确认决策后）

1. **第一阶段（行为不变重构）**：schema 升级为多块 + `documentJson` 读写管线，投影同步，旧文档懒迁移；验证旧 text/checklist 打开/保存/刷新/离线全回归。
2. **第二阶段（新功能）**：新建待办入口 + checklist 块插入/渲染 + 段落↔块连续输入 + P1 工具栏 + 链接搜索一致性修复。
3. **第三阶段（验证）**：`npx tsc --noEmit` + `npm run build -- --webpack`；dev 浏览器（1440/720/390/320）+ 响应式；macOS 壳实机；Windows 壳待实机。
4. **第四阶段（部署）**：备份 DB → rsync → rebuild → 重启 → 健康检查 → 更新交付报告 + commit/push。
