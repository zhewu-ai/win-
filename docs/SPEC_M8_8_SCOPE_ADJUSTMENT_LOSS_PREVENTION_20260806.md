# PinNote M8.8 范围调整：离线安全降级与断网防丢保护

日期：2026-08-06

## 1. 背景

M8.8 原始目标是“离线可用 MVP”：断网可打开、可新建、可编辑、关闭重开不丢、联网后自动同步。

用户在 Windows App 实测后发现：当前实现主要解决了“断网冷启动不显示浏览器/WebView 错误页”，但没有真正进入可用的 PinNote 主界面。断网冷启动后页面停留在“重新连接”类提示页，无法正常进入列表和编辑器，也无法完成离线新建/编辑。

进一步测试：

1. 在线打开 App。
2. 进入便签后断网。
3. 继续输入测试内容，例如 `123123`。
4. 关闭 App。
5. 再次打开。
6. 断网期间输入内容丢失。

这个结果说明：当前实现不满足“离线写入本地持久化”，也不能宣称“离线写入会保存”。

## 2. 产品判断

产品侧重新评估后，决定不继续把 M8.8 做成完整离线编辑系统。

原因：

1. 当前核心使用场景大多数时候有网络。
2. 完整离线编辑会引入较高复杂度：
   - App shell 缓存。
   - IndexedDB 本地数据库。
   - 同步队列。
   - 创建/更新/删除状态合并。
   - 待办排序与勾选同步。
   - 冲突处理。
   - 图片离线降级。
   - Windows 实机断网回归。
3. 相比投入，当前阶段完整离线系统的收益不够高。
4. PinNote 当前更重要的是桌面壳稳定、置顶体验、便签/待办输入顺手、数据不丢。

因此，M8.8 从“完整离线可用”调整为：

```text
离线安全降级 + 在线使用中断网后的防丢保护
```

## 3. 最新范围

### 3.1 本轮继续保留

1. 断网冷启动不显示浏览器/WebView 默认错误页。
2. 断网冷启动可以显示产品内离线页。
3. 离线页文案必须诚实，不能暗示当前无法做到的能力。
4. 在线使用过程中如果突然断网或保存失败，后续输入必须有防丢保护。
5. 用户关闭 App 前，如果存在未同步且未确认本地保存的内容，必须保护。
6. App 重开后，如果存在本地未同步草稿，必须恢复或提示用户处理。
7. 恢复联网后，未同步草稿应自动同步或提供明确重试入口。

### 3.2 本轮不再要求

以下内容从 M8.8 必做范围中移出，进入后续 Backlog：

1. 断网冷启动进入完整 PinNote 主界面。
2. 断网冷启动后新建便签。
3. 断网冷启动后新建待办。
4. 离线浏览完整历史便签列表。
5. 归档页/回收站页离线可用。
6. 图片离线上传。
7. 完整离线同步队列。
8. 多端复杂冲突合并。

## 4. 当前体验问题

### 4.1 问题 A：离线页文案不准确

当前离线页会表达类似：

```text
离线写入会保存
```

但用户实际无法进入编辑器，也无法验证写入保存。

要求：

- 如果当前做不到离线编辑，就不要写“离线写入会保存”。
- 离线冷启动页应明确：

```text
当前离线，PinNote 需要网络同步。
请连接网络后继续。
```

可选补充：

```text
如果你已经打开过便签，断网期间的未同步输入会被保护。
```

前提是防丢保护已经实现。

### 4.2 问题 B：在线编辑中断网后继续输入会丢

这是本轮必须解决的最高优先级问题。

真实场景：

1. 用户在线打开一条便签。
2. 正在写一大段内容。
3. 网络中断，但用户不一定立刻知道。
4. 用户继续写。
5. 用户关闭 App。
6. 之后恢复网络再打开，发现断网期间输入丢失。

这个体验不可接受。便签工具最核心的信任是“我写进去的东西不能静默丢”。

## 5. 必做能力：断网防丢保护

### 5.1 目标

不要求断网冷启动完整可用，但要求：

```text
用户已经打开 App 后，中途断网或保存失败，继续输入的内容不能静默丢失。
```

### 5.2 触发条件

以下任意情况都应进入防丢保护：

1. `navigator.onLine === false`。
2. `PATCH /api/notes/:id` 保存失败。
3. `POST /api/notes` 创建失败。
4. 请求超时。
5. 服务器返回 5xx。
6. Windows App 网络短暂断开。

### 5.3 本地草稿保存

当进入防丢保护后：

1. 用户后续输入仍允许继续。
2. 输入内容必须保存到本地持久化存储。
3. 本地存储建议使用 IndexedDB；如果技术部认为实现成本高，MVP 可先用 localStorage 存“当前打开便签的未同步草稿”，但必须说明容量和风险。
4. 本地草稿必须至少包含：
   - noteId。
   - title。
   - content。
   - mode。
   - checklistItems。
   - checklistGroups，如当前结构需要。
   - updatedAt。
   - localDraftUpdatedAt。
   - syncStatus。

建议状态：

```ts
syncStatus: "synced" | "saving" | "localDraft" | "syncFailed"
```

### 5.4 UI 状态

保存状态必须准确，不允许误导。

在线保存成功：

```text
已同步
```

断网或服务器保存失败，但本地草稿保存成功：

```text
已保存到本地，等待联网同步
```

本地草稿保存失败：

```text
保存失败，请不要关闭窗口
```

同步失败：

```text
同步失败，内容已保存在本地
```

要求：

- 不能在服务器未保存成功时显示“已同步”。
- 不能只显示“保存失败”而不保护用户输入。
- 文案要让用户知道当前内容在哪里：服务器，还是本地。

### 5.5 关闭保护

当存在未同步草稿时，关闭 App/刷新页面/离开页面必须保护。

如果本地草稿已经保存成功：

- 可以允许关闭。
- 下次打开必须恢复草稿。

如果本地草稿还没有确认保存成功：

- 必须拦截关闭或弹出确认。
- 文案建议：

```text
当前内容还没有保存完成，关闭可能导致丢失。请稍等或重试保存。
```

### 5.6 重开恢复

App 启动后：

1. 检查是否存在未同步本地草稿。
2. 如果存在，必须恢复到对应便签。
3. 如果对应服务器便签也存在，优先展示本地草稿，并提示：

```text
发现未同步内容，已从本地恢复
```

4. 恢复联网后自动尝试同步。
5. 同步成功后清理本地草稿。

## 6. 断网冷启动策略

M8.8 不再强制要求断网冷启动进入完整 App。

允许当前策略：

```text
断网冷启动 -> 产品内离线页 -> 提示连接网络
```

但必须满足：

1. 不显示浏览器/WebView 默认错误页。
2. 不显示虚假的“离线可写”文案。
3. 如果有未同步草稿，应在离线页提供“查看/恢复本地草稿”的入口，或在联网后自动恢复。

可接受文案：

```text
当前离线，PinNote 需要网络同步。
请连接网络后继续。
```

如果本地有未同步草稿：

```text
检测到未同步草稿。连接网络后将尝试恢复并同步。
```

更优方案是提供：

```text
查看本地草稿
```

但这不是本轮硬要求；硬要求是不能丢。

## 7. 同步策略

M8.8 调整后不要求完整离线队列，但要求对“已打开便签的本地草稿”做同步。

同步触发：

1. 网络恢复。
2. App 启动时检测到在线。
3. 用户点击“重试同步”。
4. 保存失败后的定时轻量重试。

同步规则：

1. 本地草稿优先。
2. 同步成功后显示“已同步”。
3. 同步失败后保留本地草稿，不得删除。
4. 如果服务器版本与本地草稿冲突，MVP 先采用本机草稿覆盖。

说明：

- 当前单用户场景为主，可以先不做复杂冲突合并 UI。
- 但不得因为冲突或失败丢掉本地草稿。

## 8. 验收标准

### 8.1 冷启动离线页

步骤：

1. 关闭网络。
2. 完全退出 Windows App。
3. 重新打开 Windows App。

通过标准：

1. 不出现浏览器/WebView 默认错误页。
2. 出现 PinNote 产品内离线页。
3. 文案不承诺“离线可写会保存”这类当前未实现能力。
4. 页面提示用户连接网络后继续。

### 8.2 在线编辑中断网防丢

步骤：

1. 打开 Windows App，保持在线。
2. 打开一条已有普通便签。
3. 输入第一段：`online saved text`。
4. 等待显示“已同步”。
5. 关闭网络。
6. 继续输入第二段：`offline draft text 123123`。
7. 确认 UI 显示“已保存到本地，等待联网同步”或等价状态。
8. 完全退出 Windows App。
9. 保持断网重新打开，或恢复网络后重新打开。

通过标准：

1. 第二段内容不能丢。
2. App 必须恢复本地草稿，或联网后自动恢复并同步。
3. 不能显示“已同步”但服务器实际没有保存。

### 8.3 待办中断网防丢

步骤：

1. 在线打开一条待办便签。
2. 新增一条待办：`online todo`。
3. 等待同步。
4. 断网。
5. 新增一条待办：`offline todo 123123`。
6. 勾选或取消勾选另一条待办。
7. 完全退出 App。
8. 重开 App。

通过标准：

1. `offline todo 123123` 不丢。
2. 勾选状态不丢。
3. 恢复联网后能同步。

### 8.4 保存失败防丢

步骤：

1. 保持网络连接。
2. 临时让服务器保存接口失败，或模拟 `PATCH /api/notes/:id` 返回 500。
3. 在便签里继续输入。
4. 关闭 App。
5. 重开 App。

通过标准：

1. 保存失败期间输入内容不丢。
2. UI 显示本地保护状态。
3. 服务器恢复后可同步。

### 8.5 关闭保护

步骤：

1. 在线打开 App。
2. 断网。
3. 输入内容。
4. 立刻关闭窗口。

通过标准：

1. 如果本地草稿已保存成功，允许关闭，重开后内容恢复。
2. 如果本地草稿未保存完成，必须提示用户不要关闭或等待保存。
3. 不能静默关闭后丢失内容。

## 9. 不通过条件

出现以下任意一项，本轮不通过：

1. 断网冷启动显示浏览器/WebView 默认错误页。
2. 离线页文案承诺离线可写，但实际不能编辑或不能保存。
3. 在线编辑过程中断网后继续输入，关闭重开内容丢失。
4. 保存接口失败时用户输入丢失。
5. 未同步内容未保存到本地，却允许用户无提示关闭。
6. UI 显示“已同步”，但服务器实际未保存。
7. 本地草稿同步失败后被清理。

## 10. 交付物

技术部交付时必须提供：

1. 实现说明：
   - 防丢保护触发条件。
   - 本地草稿存储位置。
   - 本地草稿数据结构。
   - 恢复策略。
   - 同步策略。
2. Windows 实机录屏：
   - 断网冷启动显示产品内离线页。
   - 在线编辑中断网继续输入，关闭重开不丢。
   - 待办中断网继续编辑，关闭重开不丢。
   - 恢复联网后同步成功。
3. 构建与部署：
   - `npm run build` 通过。
   - Windows App 实机验证通过。
   - 生产部署前创建数据库备份。

## 11. 后续 Backlog

完整离线系统暂不进入当前轮次，但保留为后续方向：

1. 断网冷启动进入完整 App。
2. 离线新建便签和待办。
3. 离线浏览完整缓存列表。
4. 完整 IndexedDB note mirror。
5. 完整 pendingCreate/pendingUpdate/pendingDelete 队列。
6. 图片离线缓存与上传队列。
7. 多端冲突提示与合并。

触发重新评估的条件：

1. 用户开始频繁在无网环境工作。
2. Windows App 用户增长，需要更原生的离线体验。
3. 后续做移动端/PWA，需要系统性 offline-first 能力。

## 12. 结论

M8.8 最新目标：

```text
不追求完整离线编辑，但必须防止用户已打开 App 后因断网或保存失败导致输入内容静默丢失。
```

本轮最高优先级不是“离线能不能从零开始用”，而是：

```text
用户已经写进去的东西，不能因为断网、保存失败、关闭 App 而丢。
```
