# QA：M11.1.2 链接编辑态一致性与待办覆盖审计

日期：2026-08-09

## 一、结论

M11.1.1 比 M11.1 明显进步：去掉了手动「阅读模式」，普通文本便签失焦后能显示蓝色外链和内部便签芯片，也补了 `[[` 搜索和返回栈。

但当前仍不能算“链接体验闭环”，原因有两个：

1. 链接渲染只覆盖普通文本便签，待办清单模式没有覆盖。
2. 普通文本便签一进入编辑态，链接又变回裸文本/裸语法，用户在链接后继续新增内容时体验割裂。

用户预期是：链接一旦形成，就应该在正文里长期保持链接外观。编辑后面的普通文字时，前面的链接不应该突然变成一长串 `[[note:id|title]]`。

本轮建议定义为 **M11.1.2 链接编辑态一致性修正**。

## 二、当前问题定位

### P0-1：待办清单模式未覆盖链接渲染

当前普通文本便签走 `LinkedText` 渲染层，但待办清单仍由 `ChecklistEditor` 内部的 `AutoGrowTextarea` 直接显示 `row.text`。

结果：

- 普通便签里的 URL/内部便签链接能变蓝。
- 待办项里的 URL/内部便签链接仍是普通文本。
- 同一个产品里，“正文可点击、待办不可点击”，用户理解成本高。

修正方向：

- `ChecklistEditor` 也要接入链接渲染能力。
- 每个待办项/小标题在非聚焦时显示 `LinkedText`。
- 聚焦该行时进入编辑。
- 点击链接时打开外部链接或内部便签，不切入编辑态。

### P0-2：编辑态暴露底层链接语法

当前普通文本便签的实现是：

- 失焦：显示 `LinkedText` 渲染层。
- 聚焦：切回 textarea，显示原始 `note.content`。

由于底层保存的是：

```text
[[note:NOTE_ID|显示标题]]
```

所以用户只要点击正文准备继续写字，链接就会从“芯片/蓝色链接”变成一串代码。这是体验问题，不是数据问题。

问题影响：

- 用户在链接后追加文字时，前面的链接突然变长，视觉跳动明显。
- 内部便签链接暴露 ID，破坏“便签互链”的直觉。
- 这会让用户觉得链接功能不稳定。

修正方向：

- 编辑态也不能直接暴露裸语法。
- 需要引入“可编辑链接表面”，至少保证已形成的链接在编辑时仍显示为蓝色链接/芯片。

## 三、推荐修正路线

### 推荐路线：从 textarea 升级为轻量 token editor

textarea 本身不能在同一段文字里把部分内容渲染成蓝色链接/芯片。继续用单一 textarea，就必然会在编辑态看到原始语法。

要达到“编辑时链接仍保持样子”，需要把正文编辑器升级为轻量 token editor：

- 底层仍保存纯文本 `note.content`。
- 渲染层把文本解析成 segments：
  - 普通文本
  - 外部 URL token
  - 内部 note token
- 页面上显示 token 化内容：
  - 普通文本可编辑。
  - 外部 URL 是蓝色链接 token。
  - 内部便签是芯片 token。
- 用户在 token 后继续输入时，token 不展开成原始语法。

这不是完整富文本，也不是 Markdown 编辑器，只是“链接 token 化编辑器”。

### 可接受的过渡路线

如果完整 token editor 成本较高，可以先做过渡版，但必须比现在更自然：

1. 当前行聚焦编辑时，仅当前行切 textarea。
2. 其他行/其他段仍保持链接渲染。
3. 光标离开当前行后立刻恢复链接渲染。
4. 对内部链接 token，尽量用短占位显示，例如 `客户反馈记录`，不要显示完整 `[[note:id|title]]`。

但要明确：过渡版仍不是最终体验。最终还是应做 token editor。

## 四、具体产品要求

### 4.1 普通文本便签

目标：

- 已识别的链接在编辑态和非编辑态都保持链接外观。
- 用户在链接前后输入文字时，链接不展开。

验收例子：

原文：

```text
参考 https://example.com
修改依据 [[note:abc123|客户反馈]]
今天继续补充：
```

用户点击“今天继续补充”后输入内容时：

- `https://example.com` 仍显示为蓝色链接。
- `客户反馈` 仍显示为内部便签芯片。
- 不应显示 `[[note:abc123|客户反馈]]`。

### 4.2 待办清单

目标：

- 待办项文本也支持外部 URL 和内部便签链接。
- 小标题是否支持可作为 P1，但待办项必须支持。

验收例子：

待办项：

```text
检查客户反馈 [[note:abc123|客户反馈]]
```

非聚焦时：

- 显示“检查客户反馈 客户反馈（芯片）”
- 点击芯片打开对应便签。

聚焦编辑该待办项时：

- 不建议展开完整 `[[note:abc123|客户反馈]]`。
- 若短期实现只能展开，也必须作为已知缺陷，不可宣称“链接体验闭环”。

### 4.3 `[[` 搜索

`[[` 搜索不能只在普通正文可用，至少待办项也应支持：

- 在普通便签正文输入 `[[`：弹便签搜索。
- 在待办项输入 `[[`：弹便签搜索。
- 选择后插入内部链接 token。

底层仍保存 `[[note:id|title]]`，但表面不要暴露。

### 4.4 返回栈

M11.1.1 的返回栈方向正确，继续保留。

需要补充：

- 从待办项内部链接跳转，也要压入返回栈。
- 返回后应回到来源便签；是否恢复到具体待办项位置可后续增强。

## 五、技术建议

### 5.1 新增统一链接编辑组件

建议新增：

```text
src/components/TokenizedTextEditor.tsx
```

职责：

- 输入 `value: string`
- 输出 `onChange(next: string)`
- 接收 `onOpenNote(noteId)`
- 接收 `linkableNotes`
- 支持外部 URL token、内部 note token、普通文本编辑、`[[` 搜索。

普通文本便签和待办项都复用它，避免两套逻辑分叉。

### 5.2 不建议继续堆叠 textarea + 渲染层

当前方案的问题根源是 textarea 和渲染层互斥：

- textarea 可编辑，但不能局部渲染链接。
- LinkedText 可显示链接，但不可编辑。

再继续补丁式切换，会不断出现“聚焦变代码、失焦变链接”的体验问题。

建议把 M11.1.2 作为技术分水岭：链接能力要进入“可编辑渲染表面”，而不是只读预览表面。

### 5.3 可选实现方向

技术部可选：

1. `contenteditable` + 自研 token 渲染
   - 适合轻量链接 token。
   - 需要认真处理光标、粘贴、撤销、输入法。

2. 引入轻量编辑器内核
   - 例如 ProseMirror/Tiptap/Lexical 这类编辑器。
   - 成本更高，但长期更稳。

3. 过渡版行级编辑
   - 短期成本低。
   - 只能缓解，不能完全解决。

产品建议：

- 如果只是 URL + 内部便签 token，先做自研轻量 token editor。
- 不要现在上完整 Markdown/富文本。
- 如果后续确定要 Markdown/富文本，再评估 Tiptap/Lexical。

## 六、验收标准

### 普通文本便签

1. 外部 URL 在非编辑态显示为蓝色链接。
2. 外部 URL 在继续编辑其他文字时仍保持蓝色链接，不展开成普通长文本。
3. 内部便签链接在非编辑态显示为标题芯片。
4. 内部便签链接在继续编辑其他文字时仍显示为标题芯片，不展开 `[[note:id|title]]`。
5. 点击外部链接不进入编辑态。
6. 点击内部链接打开目标便签并压入返回栈。

### 待办清单

1. 待办项中的 `https://...` 非聚焦时显示为蓝色链接。
2. 待办项中的内部便签链接显示为芯片。
3. 点击待办项链接可打开外部链接/内部便签。
4. 待办项输入 `[[` 可唤起便签搜索。
5. 选择便签后插入链接，并保持可读显示。
6. 勾选、回车新增、删除、拖拽排序不受影响。

### 编辑体验

1. 用户点击链接后方继续输入，链接不变成长代码。
2. 用户在链接前方插入文字，链接仍保持外观。
3. 复制/粘贴普通文本不破坏链接结构。
4. autosave debounce 正常。
5. 离线 pending 正常。
6. 跨设备刷新后链接显示一致。

### 窄窗口

1. 320px 下普通正文链接 token 不溢出。
2. 320px 下待办项链接 token 不遮挡勾选框、拖拽柄、删除按钮。
3. `[[` 搜索浮层在 320px 下不越界。

## 七、优先级

### P0 必须修

1. 待办项也支持链接渲染。
2. 普通便签编辑时不展开内部链接裸语法。
3. 在链接后新增内容时，链接外观保持稳定。

### P1 应该补

1. 待办项也支持 `[[` 搜索插入。
2. 小标题支持链接渲染。
3. 列表卡片预览支持外链/内链弱渲染。

### 暂不做

1. 完整 Markdown。
2. 完整富文本。
3. 反向链接页。
4. 日历挂载。

## 八、给技术部的结论

M11.1.1 解决了“阅读模式入口”和“返回栈”问题，但还没有解决“链接作为正文的一等内容”问题。

现在的实现仍是“失焦看链接、聚焦看原文”。这不是最终体验。

下一步 M11.1.2 要把目标改成：

> 链接在查看和编辑时都保持链接样子；普通便签和待办清单都一致支持。

在这个目标达成前，不建议把链接功能视为完全验收通过。
