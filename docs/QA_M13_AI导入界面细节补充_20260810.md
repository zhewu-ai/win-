## 二、AI 上传按钮优化

### 当前问题

- “上传给 AI”按钮现在偏小。
- 视觉上又黑又弱，不像主要入口。
- 用户不容易一眼看出这里是 AI 导入的主操作。

### 要求

- 上传按钮应做得更明显、更容易点击。
- 建议作为右侧面板里的主要按钮，而不是普通小按钮。
- 文案可使用：

```text
上传给 AI
```

或：

```text
上传排期文件
```

- 按钮需要明确支持 Excel / 图片，但不要拆成两个按钮。
- 可以在按钮下方用很轻的辅助文字提示：

```text
支持 Excel、图片
```

不要写大段说明。

### 验收

- 进入 AI 导入区域后，上传入口一眼可见。
- 按钮点击区域足够大。
- 视觉上不再是又黑又小的次要按钮。
- 320px/390px 下按钮不挤压、不溢出。

## 三、识别后草稿输入列过长

### 当前问题

- AI 识别完成后，草稿里需要编辑的时间/标题输入项很多。
- 输入列纵向过长。
- 用户需要一直滑到最底下，才能看到后续操作或打开/确认。
- 当识别条目较多时，预览区负担偏重。

### 要求

技术部评估能否优化草稿预览布局。目标是减少“必须滑到底”的操作成本。

可选方案：

1. 顶部或底部固定操作栏  
   - “确认导入 / 取消 / 批量改年份”等关键操作固定在可见区域。
   - 用户不需要滚到最底部才能继续。

2. 项目分组折叠  
   - 每个项目分组可折叠。
   - 默认展开第一个项目，其他项目可收起。

3. 表格紧凑化  
   - 标题、开始日期、结束日期压缩为更紧凑的一行。
   - 日期输入不要占过高行高。

4. 批量操作  
   - 年份错误、日期偏移等高频修改提供批量入口。
   - 不要让用户逐条改。

5. 虚拟列表或分页  
   - 如果条目很多，评估是否需要虚拟滚动。
   - 短期可先不做，除非性能明显卡顿。

如果技术部认为短期不好做，需要说明原因，而不是只说“不好做”。

### 验收

- 识别出 20 条以上排期时，用户不需要滑到最底部才能确认导入。
- 关键操作按钮始终容易找到。
- 草稿仍可编辑项目名、标题、开始日期、结束日期。
- 320px/390px 下输入项不重叠、不溢出。

## 四、排期表日期视觉识别优化

### 当前问题

- 排期表日期区域颜色太单调。
- 月视图/周视图中日期和排期的识别性不够高。
- 用户扫一眼时，不容易快速区分日期、今天、选中日期、排期强弱。

### 要求

在不做花哨视觉的前提下，提高日期区域识别性。

可考虑：

- 今天使用更明确的边框或底色。
- 选中日期使用轻量高亮。
- 周末用更弱的背景或文字色区分。
- 当前月日期和非当前月日期对比更清楚。
- 排期条颜色与项目色保持一致，但避免整页颜色过杂。
- 日期数字、项目色点、排期条之间层级更清楚。

不要：

- 不要大面积高饱和色块。
- 不要让颜色抢过排期内容。
- 不要用过多同色系深浅导致仍然单调。

### 验收

- 用户能快速看出今天是哪一天。
- 用户能快速看出当前选中日期。
- 周末/非当前月日期有清楚但克制的区分。
- 排期条与日期数字不互相干扰。
- 320px/390px 下仍保持可读。

## 五、日历封面显示关键节点信息

### 当前问题

- 现在左侧日历封面/卡片展示的信息意义不够强。
- 用户真正关心的是接下来有什么关键交付节点。
- 只展示过程性排期时，用户很难判断“马上要交什么”。

### 要求

在日历封面上优先显示节点性信息，而不是只显示普通过程。

示例：

```text
3 天后交单帧
5 天后交 A call
明天交美术
今天交 DCO
```

节点识别可先基于关键词，不必一开始做复杂 AI：

- 交
- 提交
- 反馈
- 确认
- call / A call / B call / ACO / BCO / DCO
- 单帧
- 美术
- layout
- cutdown
- 最终交付

排序优先级：

1. 今天到未来 7 天内的节点。
2. 越近越优先。
3. 明确“交付/提交/确认/call”的节点优先于普通“制作/修改”。
4. 如果没有节点，再显示普通最近排期。

### 验收

- 左侧日历封面能显示未来关键节点。
- 有关键节点时，不只显示普通制作过程。
- 节点文案短，不撑高封面。
- 无节点时有合理 fallback，不空白。

## 六、日历简介缩略信息未更新 Bug

### 当前问题

- 日历内容已经更新。
- 但日历封面底下缩略显示日期的两个部分仍然是之前的内容。
- 用户看到的封面信息与实际日历内容不一致。

### 要求

- 技术部定位封面缩略信息的数据来源。
- 当排期新增、编辑、删除、AI 导入确认后，封面缩略信息必须同步更新。
- 不允许主日历内容已变、封面摘要仍显示旧数据。

可能原因方向：

- 日历封面使用了旧缓存。
- 工作日历数据更新后没有透传到左侧 CalendarCard。
- AI 导入确认后只刷新了日历主体，没有刷新左侧列表/封面摘要。
- memo / useMemo 依赖缺失。

### 验收

- 手动新增排期后，左侧日历封面摘要立即更新。
- 编辑排期日期/标题后，封面摘要同步更新。
- 删除排期后，封面摘要不再显示已删除内容。
- AI 导入确认后，封面摘要显示新导入内容。
- 刷新页面后封面摘要与日历主体一致。

## 八、连续滚动月历断格与重复数据 Bug

### 当前问题

- 现在的滚动月历并不是真正连续。
- 每个月仍按独立月视图网格渲染，通常会补齐完整周。
- 这样会导致相邻月份之间出现重复日期。
- 例如 8 月视图的表头/首周可能包含 7 月 30 日、7 月 31 日等补位日期。
- 同一条排期如果落在这些补位日期上，可能会在 7 月月历里出现一次，又在 8 月月历里重复出现一次。

用户真实遇到的问题：

- 某个 1 号的排期，例如 `A call`，在上一个月的补位区域出现。
- 到当前月又出现一份。
- 用户会以为数据重复，或者误判该排期被创建了两次。

### 问题本质

连续滚动月历不能简单把多个“完整月网格”上下拼接。

如果每个月都包含前后月份的补位日期，就会产生：

- 日期重复。
- 排期重复。
- 月份边界断裂。
- 用户无法判断某条排期到底属于哪个月份。

### 要求

技术部必须修复连续月历的日期去重和月份边界问题。

可选方案：

1. 真连续时间流
   - 按周作为连续单位渲染。
   - 每一周只出现一次。
   - 月份标题只是插入在对应周前，不重新生成完整月网格。

2. 月份独立网格但隐藏跨月排期
   - 每个月仍显示补位日期，但补位日期不显示排期条目。
   - 排期只在其真实所属月份显示。
   - 补位日期视觉弱化，只用于保持网格结构。

3. 月份独立网格但去重
   - 同一日期在连续滚动容器中只能有一个主渲染位置。
   - 如果该日期已在前一个月显示过，下一个月的补位格不再显示排期或交互。

推荐优先评估方案 1 或方案 2。核心要求是：同一日期、同一排期在连续滚动月历里不能重复出现。

### 验收

- 7 月底 / 8 月初这类跨月边界滚动时，同一日期不重复显示排期。
- 同一条 `A call` / `交单帧` / `交美术` 等排期不在两个相邻月份重复出现。
- 补位日期如果保留，必须视觉弱化，并且不能造成重复数据误判。
- 点击补位日期时行为明确：要么不响应，要么跳转到该日期真实所属月份/日视图。
- 320px/390px 下连续滚动不出现断格、错位、重复排期。

### 10.5 QA⑦ 连续月历去重（生产验证）

- 7 月网格（data-month=2026-6）仅渲染 7 月真实日期内的排期：创意确认(7/15)、模型优化(7/16-19)、layout制作 材质测试(7/20-25)、layout V1提交&反馈(7/26)、layout制作(7/27-28)、layout V2提交&反馈(7/29)、layout制作 单帧制作 作曲制作(7/30-31)。

- 8/3-8/4「单帧制作 作曲制作」仅出现在 8 月网格，不出现在 7 月补位区。
- 结论：同一条排期只在真实所属月份出现一次，跨月边界无重复渲染，QA⑦ 修复生效。

### 10.6 验证说明（排查过程）

- 排查「7 月缺单帧制作/作曲制作条」时，通过 React fiber 读取生产环境 WorkMonthView 实际收到的 `items` props（31 条、全部属于项目 cmsmb2yzx002），确认渲染结果与数据一致。
- 生产库 WorkProject 中其余 9 个同名项目均为软删除（deletedAt 非空），日历按可见项目过滤，因此其余项目的排期（含 7/29-8/15 单帧制作/作曲制作）正确不显示。该现象属数据归属过滤，非渲染 Bug。
- 附带发现（未在本轮处理）：`/api/work-schedule-items` 未按项目 deletedAt 过滤，会返回已删除项目的排期；客户端日历通过 visibleProjectIds 正确过滤，不影响展示。建议后续在 API 层补充项目级 deletedAt 过滤。
