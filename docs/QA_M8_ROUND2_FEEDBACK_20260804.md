# M8 第二轮复验反馈：置顶通过，收敛极小模式，优化待办密度与小窗口布局

日期：2026-08-04

结论：部分通过，继续修复。

本轮最大进展：Windows 桌面壳的窗口置顶问题已经解决，可以置顶。这一项可以先视为通过。

但当前仍有几个体验问题需要继续处理。本轮方向要收敛：既然主窗口本身已经可以缩得很小，就不要继续强推“极小模式独立按钮/独立窗口”。先把缩小后的主窗口体验打磨好。

## 1. 已通过项

### M8-R2-PASS-01：Windows 壳置顶能力已可用

用户反馈：

- 新一轮修改后，置顶问题已解决。
- Windows App 可以置顶。

后续要求：

- 保持当前置顶能力。
- 不要因为移除极小模式按钮影响置顶功能。
- 仍需保留一个清晰的“窗口置顶/取消置顶”入口。

## 2. 不通过问题

### M8-R2-F01：极小模式按钮点击后崩溃，建议直接移除

严重级别：P0

用户现象：

- 点击“极小模式”按钮后 App 会崩溃。
- 但现在主窗口本身已经可以缩得很小，所以独立极小模式不再是必要路径。

产品决策：

- 本轮先删除“极小模式/打开悬浮窗”按钮。
- 不继续修这个按钮的崩溃问题。
- 桌面小窗体验统一通过“主窗口缩小 + 置顶”实现。

原因：

1. 当前用户核心需求是桌面置顶，不是一定要独立子窗口。
2. 独立悬浮窗涉及 Tauri 多窗口、远程页面、权限、状态同步，复杂度较高。
3. 主窗口可缩小后，已经能覆盖当前主要使用场景。

验收标准：

1. Windows App 顶部/工具栏不再出现“极小模式/悬浮窗”按钮。
2. 点击任何剩余按钮不会触发 `open_floating_note`。
3. App 不再因极小模式按钮崩溃。
4. 主窗口缩小到小尺寸后仍可编辑、置顶。

### M8-R2-F02：待办模式行距/间距过大，信息密度太低

严重级别：P1

用户现象：

- 待办模式下，每条待办之间的空隙太大。
- 导致小窗口里能显示的内容很少，信息密度低。
- 对反馈清单来说不够高效。

产品要求：

- 待办列表需要更紧凑。
- 小窗口里应能一次看到更多待办项。
- 但不能挤到难以点击勾选框或拖拽手柄。

建议方向：

- 降低待办项垂直 padding。
- 降低行间 gap。
- 长文本多行时保留合理行高。
- 普通单行待办建议高度接近 30px 到 36px。
- 已完成区也要保持紧凑。

验收标准：

1. 260px 到 360px 宽的小窗口中，连续 8 到 10 条短待办能较高效显示。
2. 单行待办之间没有明显过大空白。
3. 长待办换行后仍清楚可读。
4. 勾选框、拖拽手柄仍容易点击。

### M8-R2-F03：拖拽排序在网页端可用，但 Windows App 壳里不好拖/拖不动

严重级别：P1

用户现象：

- 网页端可以拖拽排序。
- 封装成 Windows App 后，拖拽手柄不好触发，感觉拖不动。

产品判断：

这很可能是 WebView 内 pointer/mouse 事件、拖拽库传感器、拖拽手柄命中区域或右键/窗口拖动区域冲突导致。不能只用浏览器端验证。

产品要求：

- Windows App 壳内拖拽排序必须可用。
- 拖拽手柄需要更容易命中。
- 小窗口里也能拖。

建议方向：

1. 增大拖拽手柄点击区域，不只显示一个很小图标。
2. 使用 pointer events 兼容 WebView2。
3. 如果使用拖拽库，确认启用了 mouse/pointer sensor，而不是只在浏览器环境表现正常。
4. 拖拽手柄不要和文本输入选择、勾选框、窗口拖动区域冲突。
5. Windows 壳内需要实机验证，不允许只用 Mac 浏览器验证。

验收标准：

1. Windows App 内创建 5 条待办。
2. 用拖拽手柄把第 5 条拖到第 2 条。
3. 操作成功，顺序立即变化。
4. 刷新/重开后顺序保持。
5. 小窗口尺寸下仍可拖动。

### M8-R2-F04：小窗口下顶部栏占空间，“我的/新建”等入口碍事

严重级别：P1

用户现象：

- 窗口缩小时，顶部那一行包含“我的”“新建”等入口，占用头部空间。
- 小窗口里顶部显得拥挤，视觉上很奇怪。
- 用户希望把这些入口挪走，把顶部空间让给便签内容。

产品方向：

- 小窗口状态下弱化顶部全局栏。
- 可以把“我的/账户”“新建”等全局操作移到左下角或底部工具区。
- 主编辑内容的顶部尽量干净。

建议方案：

### 方案 A：响应式隐藏顶部全局栏，改用底部迷你工具条

当窗口宽度小于某个阈值，例如 420px：

- 顶部全局栏隐藏或极简化。
- 底部左侧显示账户/我的入口。
- 底部显示新建入口。
- 置顶按钮保留在容易点击的位置。

### 方案 B：标题区下方左侧放迷你入口

将“我的/新建”等入口移动到便签标题附近的左下角，弱化成小图标。

注意：

- 不要遮挡正文输入。
- 不要让底部工具条挡住最后一行文字。
- 小窗口下必须优先保证编辑区域。

验收标准：

1. 窗口缩到 320px 宽时，顶部不再被“我的/新建”等入口占满。
2. 用户仍能找到新建入口。
3. 用户仍能找到账户/我的入口。
4. 正文编辑空间明显增加。
5. 布局不跳、不遮挡、不裁切。

## 3. 本轮建议优先级

P0：

1. 移除极小模式/悬浮窗按钮，避免崩溃。

P1：

1. 压缩待办模式行距和间距。
2. 修复 Windows App 壳内拖拽排序手柄不好触发。
3. 小窗口下重排顶部栏，把“我的/新建”等入口移到底部或弱化。

P2：

1. 图片变灰、图片绑定待办项继续后置。
2. 图片压缩/缩略图如未测试，本轮先保留待验。

## 4. 明确不做

1. 本轮不继续修独立极小模式多窗口。
2. 不做 Mac 壳。
3. 不做邮箱注册/多用户。
4. 不做复杂富文本。
5. 不做图片绑定待办项。

## 6. 本轮通过标准

这一轮通过标准：

> Windows App 保留置顶能力，去掉会崩溃的极小模式按钮；主窗口缩小后，待办列表紧凑、可拖拽排序，顶部不再挤占核心编辑空间。

如果 Windows App 内拖拽仍不好用，或顶部栏在小窗口下仍明显碍事，本轮不通过。
