# 全平台便签 M8 启动文档：桌面壳体验、编辑排版、待办组织与图片策略

日期：2026-08-04

## 1. 背景

Windows 桌面壳已经可以运行，但真实使用中暴露出一批体验问题。当前阶段不要急着做账号体系，多用户/邮箱登录优先级低。M8 的目标是先把“作为一个桌面便签工具”的基础体验打磨到可长期使用。

本轮核心判断：

> 便签产品最重要的是顺手、稳定、像一个真正的桌面工具。现在优先修窗口、排版、待办输入组织和图片性能，不扩展账号体系。

## 2. 本轮总目标

M8 要解决四类问题：

1. Windows 壳不能穿帮：置顶/悬浮窗命令必须在桌面壳里可用，右键不能出现浏览器菜单。
2. 小窗口排版要像便签：文字不能提前裁切，窗口缩小时内容应连续自适应换行。
3. 待办要可整理：支持拖拽调整待办顺序，支持轻量小标题/分隔段落。
4. 图片要降成本：上传压缩、缩略图加载，评估图片是否继续保留或先降级。

## 3. P0 必须修复

### M8-P0-01：Windows 壳内仍提示“请确认在桌面壳中运行”

用户现象：

- 在 Windows App 里点击“窗口置顶”，提示：

```text
窗口置顶操作失败，请确认在桌面壳中运行
```

- 在 Windows App 里点击“打开悬浮窗/极小模式”，提示：

```text
打开悬浮窗失败，请确认在桌面壳中运行
```

产品判断：

这是 P0。用户确实是在桌面壳里运行，却被系统判断成非桌面壳，说明 Tauri 环境检测或 command invoke 链路仍有问题。

技术排查方向：

1. 不要只依赖 `__TAURI_INTERNALS__ in window` 判断壳环境，需验证生产 Windows 包中该标记是否存在。
2. 在 Windows 包里实际打印/暴露诊断信息：
   - `isTauri()` 返回值
   - `window.__TAURI_INTERNALS__` 是否存在
   - `invoke("toggle_always_on_top")` 是否可用
   - invoke 失败的原始错误
3. 检查 Tauri v2 capability 是否允许 `main` 和 `floating_*` 调用自定义 command。
4. 检查线上 Web 页面跑在 Tauri WebView 中时，`@tauri-apps/api/core` 是否能正常注入和调用。
5. 如果线上远程页面无法直接调用 Tauri API，需要按 Tauri 官方远程页面能力要求配置权限/allowlist，或改为壳加载本地 bridge 页面再嵌入线上应用。

验收标准：

1. Windows App 内点击“窗口置顶”不再出现“请确认在桌面壳中运行”。
2. Windows App 内点击“极小模式”能打开悬浮窗。
3. 置顶开关能实际改变窗口置顶状态。
4. 若失败，弹窗必须显示可定位的错误码/错误文本，不允许只给通用提示。

### M8-P0-02：小窗口文字提前裁切，底部/边缘留白但内容被截断

用户现象：

- Windows App 缩小到一定程度后，文字明明还没到边框，距离边框还有大约一指宽，却已经被裁切。
- 在普通便签模式，纵向空间明明还很大，内容还没到底部也被截掉。

产品判断：

这是布局容器问题，不是单纯字体问题。很可能存在固定宽高、固定 max-width、overflow hidden、内层容器高度计算错误、`min-h-screen` 与窗口高度冲突、或 WebView 缩放后滚动容器没有正确撑开。

技术排查方向：

1. 检查主编辑页和 `/notes/:id/floating` 的外层容器是否使用了固定宽度/固定最大宽度，例如 `max-w-[320px]` 一类限制。
2. 检查编辑区是否存在 `overflow-hidden`、固定 `height`、固定 `min-height` 导致内容区域提前裁切。
3. 普通文本编辑区不要用固定 `min-h` 后让父容器裁切，应让 textarea/editor 在可视区域内自然滚动。
4. 小窗口下正文容器的 padding 要随窗口宽度收缩，不能保留桌面大窗口的左右留白。
5. 需要分别验证：
   - 主窗口 320px 宽
   - 悬浮窗 260px 宽
   - 普通便签长文本
   - 待办长文本

验收标准：

1. 小窗口下文字不会在距离边缘仍有明显空白时被裁切。
2. 纵向空间足够时，正文不会提前被底部裁切。
3. 内容超出可视区时，滚动行为正常。
4. 260px 悬浮窗和 320px 主窗口都通过。

### M8-P0-03：响应式换行不连续，像固定档位切换

用户现象：

- Windows 自带便签在窗口缩小时，靠近边界的文字会自然换到下一行。
- 当前应用像只有几个固定断点，到某个尺寸才突然变布局，响应不够连续。

产品要求：

- 便签正文、待办文本、小标题、工具栏都要连续响应窗口宽度。
- 用户拖动窗口边缘时，文本应随可用宽度实时换行，而不是到固定档位才突变。

技术要求：

1. 正文区域宽度应使用容器宽度 `width: 100%`，避免固定 `max-width` 在悬浮窗中造成假边界。
2. 文本输入控件必须允许自然换行：
   - 普通便签：textarea 或富文本编辑器要 `white-space: pre-wrap` / 自然换行。
   - 待办项：如继续使用单行 input，会天然不支持多行换行；需要改为 textarea/autosize textarea，或至少让长文本不裁切。
3. 窄窗口下工具栏按钮文字隐藏为图标，不能挤压正文区域。

验收标准：

1. 拖动窗口从 520px 到 260px，正文行宽连续变化。
2. 长句靠近边界时自动换行。
3. 待办项长文本不横向裁切。
4. 工具栏不把正文挤到不可用。

### M8-P0-04：Windows App 右键出现浏览器菜单，产品穿帮

用户现象：

- 在 Windows App 中右键，出现浏览器默认菜单：
  - 返回
  - 刷新
  - 另存为
  - 打印
  - 共享

产品判断：

这会明显暴露“只是浏览器套壳”，需要修。

产品要求：

优先方案：

- 禁用 WebView 默认右键菜单。

更好方案：

- 自定义右键菜单，只保留便签相关动作：
  - 复制
  - 粘贴
  - 剪切
  - 全选
  - 删除所选

本轮最低要求：

- 不能出现浏览器默认菜单。

验收标准：

1. Windows App 中右键不会出现浏览器默认菜单。
2. 文本输入区域右键至少不影响正常复制粘贴。
3. 如果实现自定义菜单，菜单项必须是产品内动作，不出现“打印/另存为/刷新网页”。

## 4. P1 应优先做

### M8-P1-01：待办项支持拖拽排序

用户场景：

- 反馈 1 下面有 A/B/C。
- 反馈 2 下面也有 A/B/C。
- 用户想调整待办顺序，例如把第 2 条拖到第 1 条前面。

产品要求：

- 待办项左侧提供拖拽手柄。
- 用户可以拖拽调整未完成待办的顺序。
- 调整后立即保存。
- 刷新后顺序保持。
- 已完成区可以暂不支持拖拽，或只支持在已完成区内部拖拽。

交互建议：

- 鼠标悬停待办项时显示拖拽手柄。
- 小窗口下手柄仍可点击/拖动。
- 拖动时显示插入位置。

验收标准：

1. 创建 5 条待办。
2. 将第 5 条拖到第 2 条位置。
3. 刷新后顺序保持。
4. 勾选完成后，该项仍进入已完成区。

### M8-P1-02：待办中支持轻量小标题/分段

用户场景：

- 用户不想做复杂分组。
- 但需要在一堆待办中插入小标题，例如：

```text
C4D
○ 模型比例调整
○ 材质太亮

AE
○ 字幕错位
○ 输出预览
```

产品判断：

这可以理解为“轻量组标题”，但不能做成复杂项目管理。

产品要求：

- 待办列表中允许插入“小标题行”。
- 小标题行没有勾选圆圈。
- 小标题行可编辑、可删除、可拖拽排序。
- 小标题下面的待办视觉上属于这一段。
- 勾选完成后，完成项仍统一进入底部“已完成”，不要每个小标题下面都生成一个完成区。

实现建议：

- 数据结构可新增 item 类型：

```ts
type: "todo" | "heading"
```

- 或在现有 checklist item 中增加字段：

```ts
kind: "todo" | "heading"
```

- 不建议恢复重型“添加分组”按钮。

验收标准：

1. 可在任意位置插入小标题。
2. 小标题没有勾选按钮。
3. 小标题可参与拖拽排序。
4. 小标题下方待办完成后进入统一已完成区。

### M8-P1-03：图片上传自动压缩与缩略图

用户问题：

- 当前图片上传默认全量大小，增加服务器压力。
- 加载时也可能直接加载原图，影响速度。

产品要求：

上传时：

- 前端优先压缩图片。
- 长边建议压到 1600px 或 2000px。
- JPEG/WebP 质量建议 0.75 到 0.85。
- 超过限制的 GIF 可先不压缩，但要限制大小。

展示时：

- 便签中默认显示缩略图。
- 只有用户主动点击“查看全图”时才加载原图。

存储建议：

- 保存两份：
  - `thumbnailUrl`
  - `originalUrl`
- 如果短期不改数据库，可先让 `url` 指向压缩图，原图暂不保存。

产品取舍：

- 如果图片压缩/缩略图短期做不好，可以先降级图片功能：
  - 保留上传入口但限制更严格；
  - 或在悬浮小窗中暂时隐藏图片上传；
  - 不建议直接永久删除图片功能，因为三维/设计反馈场景仍可能需要截图。

验收标准：

1. 上传一张 5MB 以上截图后，服务端实际保存体积明显下降。
2. 列表/编辑区默认加载缩略图。
3. 点击预览时才加载大图或清晰图。
4. 上传失败提示清楚。

## 5. P2 后续增强

### M8-P2-01：图片绑定到具体待办项

用户设想：

- 图片可以拖到某一条待办下面。
- 勾选该待办后，文字划掉，图片也变灰。

产品判断：

这是有价值的设计反馈场景，但实现复杂度高于“便签级图片附件”。涉及：

- 图片和 checklist item 的关联关系。
- 图片拖拽移动。
- 待办完成状态联动图片样式。
- 删除/恢复/排序的一致性。

建议：

- 不放入本轮 P0。
- 先完成图片压缩和缩略图。
- 下一轮再设计“附件绑定到待办项”。

### M8-P2-02：时间戳位置调整

用户反馈：

- 顶部时间戳从排版上看不够合理。
- 可以考虑放到文档最末尾。

产品建议：

- 主编辑页顶部不再强显示大时间戳。
- 可改为底部弱信息：

```text
最后编辑于 2026年8月4日 14:30
```

- 悬浮窗中尤其要弱化时间戳，避免占用顶部空间。

验收标准：

1. 顶部不再被时间戳占据主要视觉。
2. 底部能看到最后编辑时间。
3. 小窗口下时间戳不挤占编辑空间。

### M8-P2-03：基础文字格式

用户需求：

- 加粗
- 斜体
- 下划线

产品判断：

这是富文本能力，不建议临时在 textarea 上硬拼。需要先决定编辑器方案。

建议方案：

- 如果只做轻量格式：Markdown 快捷语法 + 简单预览。
- 如果做真正富文本：引入成熟编辑器，例如 TipTap/ProseMirror。

本轮建议：

- 先不做完整富文本。
- 可以先评估编辑器迁移成本。
- 不要在现有纯文本模型里临时塞 HTML，避免污染搜索、待办转换和同步。

### M8-P2-04：多用户/账号体系

用户反馈：

- 多用户、账号体系需要，但优先级低。

产品结论：

- M8 不做。
- 等桌面便签体验稳定后，再启动 M9/M10 账号体系：
  - 邮箱登录
  - 用户隔离
  - 邀请同事
  - 权限校验

## 6. 本轮不做

1. 不做邮箱注册/登录。
2. 不做多人协作。
3. 不做离线同步。
4. 不做 Mac 壳。
5. 不做完整富文本编辑器落地。
6. 不做图片标注/OCR。
7. 不做复杂项目管理字段，如负责人、截止日期、优先级。

## 7. 推荐排期

### 第 1 批：桌面壳与排版阻塞

必须先完成：

1. 修复 Tauri 环境识别和 invoke。
2. 修复置顶/极小模式调用失败。
3. 禁用或替换浏览器右键菜单。
4. 修复小窗口文字提前裁切。
5. 修复连续响应式换行。

这一批完成后先发一个 Windows 包验收。

### 第 2 批：待办整理能力

1. 待办拖拽排序。
2. 小标题/分段行。
3. 小窗口下待办长文本换行。

### 第 3 批：图片策略

1. 上传压缩。
2. 缩略图展示。
3. 评估是否做“图片绑定待办项”。

## 8. 技术部交付证据

每批交付都要提供：

1. `npm run build` 结果。
2. Tauri Windows 打包结果。
3. Windows 实机录屏。
4. 小窗口尺寸截图：
   - 260px 悬浮窗
   - 320px 主窗口
5. 问题修复前后对比说明。

桌面壳问题必须提供：

1. Windows App 中 `isTauri()` 或等价环境检测结果。
2. 置顶 command 成功调用证据。
3. 右键菜单不再出现浏览器默认菜单的录屏。

图片问题必须提供：

1. 上传前后文件体积对比。
2. 缩略图和原图加载路径说明。
3. 删除/刷新后仍删除的验证。

## 9. M8 通过标准

M8 通过不是看功能数量，而是看这句话是否成立：

> Windows 上的便签像一个真正的桌面便签工具：窗口能置顶，极小窗口能自然排版，文字不会被裁切，待办能整理顺序，图片不会拖垮加载和服务器。

如果置顶仍失败、右键仍穿帮、文字仍提前裁切，M8 不通过。
