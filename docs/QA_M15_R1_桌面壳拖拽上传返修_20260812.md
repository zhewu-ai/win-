# QA M15 R1：桌面壳拖拽上传返修

日期：2026-08-12

状态：新增返修，Web 已通过，桌面壳未通过

## 一、问题结论

M15 R1 已完成 Web 页面里的拖拽上传：

- AI 排期导入区支持拖拽 Excel / 图片。
- 便签编辑区支持拖拽 / 粘贴图片。

但用户补充发现：**在桌面壳里不能拖拽文件上传**。

这不是用户误用，而是验收范围缺口。浏览器里的 HTML5 drop 事件通过，不代表 Tauri Windows/Mac 壳也通过。

当前交付报告 `docs/交付报告-M15_下一阶段R1_拖拽上传_20260811.md` 主要验证了：

- localhost Web。
- 生产 Web。
- 320px 窄窗。

但没有覆盖：

- Windows Tauri 壳。
- Mac Tauri 壳。
- 主窗口 / 悬浮窗内拖拽。

因此 M15 R1 需要补桌面壳返修验收。

## 二、原因判断

当前前端实现主要依赖浏览器 DOM 事件：

- `onDropCapture`
- `onPasteCapture`
- `dragenter / dragover / dragleave / drop`

这些在普通浏览器可用。

但 Tauri v2 桌面壳中，系统文件拖放默认会由 Tauri / WebView 层处理。尤其 Windows WebView2 下，Tauri 官方说明：如果要使用前端 HTML5 drag/drop，需要禁用 Tauri 内部 drag drop handler；否则应监听 Tauri 的文件拖放事件。

当前仓库检查结果：

- `src/components/NoteEditor.tsx` 已加 Web drop/paste。
- `src/components/calendar/work/WorkRightPanel.tsx` 已加 Web drop zone。
- `src-tauri/src/lib.rs` 没有文件拖放事件桥接。
- `src-tauri/tauri.conf.json` 没有 `dragDropEnabled` 相关配置。
- `src/lib/tauri.ts` 没有封装桌面文件拖放监听。

所以壳里无法拖拽是合理结果。

## 三、修复方向

技术部需要二选一，建议优先方案 A。

### 方案 A：禁用 Tauri 内部拖放处理，让前端 HTML5 drop 生效

在 Tauri WebView 配置里关闭内部 drag drop handler。

目标：

- Windows/Mac 壳中，文件拖入 WebView 后仍触发前端 DOM `drop`。
- 继续复用现有 Web 逻辑：
  - AI 导入：`onParseFile(file)`
  - 便签图片：`imageUploadRef.uploadFiles(files)`

需要确认 Tauri v2 配置项或 builder API 写法。官方文档中对应概念为：

```text
dragDropEnabled: false
```

或 Rust builder 中等价的 disable drag drop handler。

注意：

- 主窗口 `main` 要配置。
- 悬浮窗 `floating_*` 也要配置，因为便签图片拖拽可能发生在悬浮窗。
- 修改后必须在 Windows 实机验证，不能只在浏览器验证。

### 方案 B：监听 Tauri 文件拖放事件，再桥接到前端上传流程

使用 Tauri v2 的 `onDragDropEvent` 监听壳层文件拖放：

- drag enter / over：通知前端显示高亮。
- drop：拿到文件路径。
- 前端根据路径请求 Rust command 读取文件，转换成可上传内容。
- 再走现有上传接口。

该方案更可控，但复杂度更高。

需要新增：

- Tauri JS 事件监听封装。
- 读取文件内容的 Rust command。
- 权限配置。
- 路径安全校验。
- 文件大小限制。
- 文件名 / MIME 推断。

除非方案 A 在 Windows WebView2 下不可用，否则不建议第一轮走方案 B。

## 四、验收要求

### 4.1 Windows 壳主窗口

必须用 Windows 安装包或 `tauri dev` 验收：

1. 打开主窗口。
2. 进入工作日历右侧导入区。
3. 从资源管理器拖入 `.xlsx`。
4. drop zone 高亮，松开后进入现有 AI / 程序解析流程。
5. 从资源管理器拖入 `.png/.jpg/.webp`。
6. 能进入图片识别流程。
7. 拖入 PDF，提示“当前仅支持 Excel 和图片”，不调 AI。
8. 拖入多个文件，提示“一次仅支持导入 1 个文件”，不调 AI。

### 4.2 Windows 壳便签编辑区

1. 打开一条便签。
2. 从资源管理器拖入图片。
3. 图片上传并出现在附件区。
4. 拖入 `.txt/.pdf`，提示“仅支持上传图片”，不上传。
5. 纯文本粘贴仍正常。

### 4.3 Windows 悬浮窗

1. 打开一条便签悬浮窗。
2. 从资源管理器拖入图片。
3. 图片上传并出现在该便签附件区。
4. 离线时提示“离线模式下暂不支持上传图片”。

### 4.4 Mac 壳

如果本轮没有 Mac 实机，至少要明确写：

```text
Mac 壳未验收，待 Mac 实机补测。
```

如果有 Mac 实机，按 Windows 主窗口和便签编辑区同样验收。

## 五、回归要求

修复后必须保证：

- Web 浏览器拖拽仍可用。
- Web 浏览器纯文本拖拽/粘贴不被错误拦截。
- 待办行内拖拽排序不受影响。
- Tiptap 内部文字编辑不受影响。
- Windows 壳窗口拖动、缩放、置顶、悬浮窗打开不受影响。
- `cargo check` 通过。
- `npx tsc --noEmit` 通过。
- `npm run build -- --webpack` 通过。
- `npm run tauri build` 或 GitHub Actions Windows 包构建通过。

- Windows 壳主窗口 AI 导入拖拽录屏或截图。
- Windows 壳便签图片拖拽录屏或截图。

## 七、当前发布判断

M15 R1 Web 端可以保留。

但如果产品宣传“支持拖拽上传”，需要补一句：

```text
当前仅 Web 浏览器支持，桌面壳待返修。
```

在桌面壳返修通过前，不应把“拖拽上传”作为 Windows/Mac 壳已完成能力对外说明。
