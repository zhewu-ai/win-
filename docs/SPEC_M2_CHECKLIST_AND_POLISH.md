# 全平台便签 M2 产品规格：待办模式与体验完善

## 1. 本轮目标

M2 的目标是把现有 Web MVP 从“可记录便签”提升到“可日常使用的便签 + 待办工具”。

本轮重点：

1. 新增待办模式。
2. 优化便签列表视觉和信息密度。
3. 优化编辑输入体验和保存失败处理。
4. 新增回收站。
5. 增强搜索。
6. 预留未来桌面壳的单条便签视图。

本轮不做：

1. 图片上传和附件管理。
2. 富文本编辑器。
3. Markdown 预览。
4. 多人共享。
5. 实时协同。
6. Windows/Mac 原生壳。

图片能力作为 M3 候选范围，见本文第 12 节。

## 2. 范围优先级

### 2.1 P0：必须完成

1. 便签模式 / 待办模式切换。
2. 待办项新增、编辑、勾选、删除。
3. 待办项自动保存。
4. 列表显示待办完成进度。
5. 便签卡片视觉优化。
6. 新建后自动聚焦。
7. 保存失败支持重试。
8. 回收站：删除、恢复、永久删除。
9. 搜索增强：清空按钮、结果高亮。

### 2.2 P1：尽量完成

1. `Cmd/Ctrl + Enter` 新建下一条便签。
2. 输入区域高度优化。
3. 离开页面前保存中保护。
4. 搜索移动端体验优化。
5. 单条便签小窗口页面 `/notes/:id/floating`。
6. 桌面窗口字段 API 验证。

### 2.3 P2：本轮可延期

1. 置顶便签手动拖拽排序。
2. 普通便签自定义排序。
3. 隐藏已完成待办。
4. 图片附件。

## 3. 数据模型

### 3.1 Note 新增字段

在现有 `Note` 上新增：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `mode` | string | 是 | `text` | 便签模式，取值 `text` 或 `checklist` |
| `checklistItems` | json/string | 是 | `[]` | 待办项列表 |

如果当前数据库不方便使用 JSON 类型，可以用 string 存储 JSON，但 API 返回给前端时必须是数组。

### 3.2 ChecklistItem

`checklistItems` 数组元素结构：

```json
{
  "id": "item_id",
  "text": "买牛奶",
  "checked": false,
  "sortOrder": 1000,
  "createdAt": "2026-07-23T00:00:00.000Z",
  "updatedAt": "2026-07-23T00:00:00.000Z"
}
```

字段规则：

- `id`：客户端或服务端生成均可，但同一便签内必须唯一。
- `text`：允许为空字符串，空项在用户离开编辑区时可以保留或清理，由实现固定。
- `checked`：勾选状态。
- `sortOrder`：排序字段，第一版按创建顺序即可。
- `createdAt`、`updatedAt`：建议保留，便于未来扩展。

### 3.3 删除模型调整

现有 `deletedAt` 继续作为软删除字段。本轮新增回收站，因此删除行为变更为：

- 普通删除：设置 `deletedAt`，便签进入回收站。
- 恢复：清空 `deletedAt`。
- 永久删除：从数据库删除，或设置无法恢复的永久删除状态。推荐直接硬删除。

## 4. API 规格

### 4.1 Note 返回结构

所有返回 `Note` 的接口必须包含：

- `mode`
- `checklistItems`

当 `mode=text` 时：

- `content` 是主要正文。
- `checklistItems` 返回空数组。

当 `mode=checklist` 时：

- `checklistItems` 是主要内容。
- `content` 可以为空，也可以保留从旧文本迁移来的内容，但列表展示和编辑以 `checklistItems` 为准。

### 4.2 新建便签

`POST /api/notes`

新增请求字段：

```json
{
  "title": "",
  "content": "",
  "color": "yellow",
  "mode": "text",
  "checklistItems": []
}
```

规则：

- `mode` 不传时为 `text`。
- `mode=checklist` 时，`checklistItems` 不传则为空数组。
- 非法 `mode` 返回 400。

### 4.3 更新便签

`PATCH /api/notes/:id`

新增允许更新字段：

- `mode`
- `checklistItems`

规则：

- `mode` 只能是 `text` 或 `checklist`。
- `checklistItems` 必须是数组。
- 每个 item 必须有 `id`、`text`、`checked`。
- 非法结构返回 400。
- 更新 `checklistItems` 后必须刷新 `updatedAt`。

### 4.4 回收站列表

`GET /api/notes/trash?q=keyword`

返回：

```json
{
  "notes": []
}
```

规则：

- 只返回 `deletedAt` 非空的便签。
- 支持搜索标题、正文、待办项文字。
- 按 `deletedAt` 倒序。

### 4.5 恢复便签

`POST /api/notes/:id/restore`

规则：

- 只能恢复当前用户自己的便签。
- 便签不存在或不属于当前用户时返回 404。
- 恢复后 `deletedAt=null`。
- 恢复后的便签回到主页或归档页，取决于 `isArchived`。

### 4.6 永久删除

`DELETE /api/notes/:id/permanent`

规则：

- 只能永久删除当前用户自己的回收站便签。
- 未进入回收站的便签不允许永久删除，返回 400。
- 删除后无法恢复。

## 5. 待办模式

### 5.1 模式切换

编辑区需要提供模式切换入口：

- 普通便签
- 待办清单

交互要求：

- 新建便签默认是普通便签。
- 用户可以把普通便签切换成待办清单。
- 用户可以把待办清单切回普通便签。

切换规则：

- `text -> checklist`：如果 `content` 非空，系统可以把每一行转换为一条待办项。
- `checklist -> text`：系统可以把待办项转换为文本行，已完成项建议加上 `[x]` 前缀，未完成项建议加上 `[ ]` 前缀。
- 切换前必须保存当前内容。
- 切换后必须自动保存 `mode` 和转换后的内容。

### 5.2 待办项编辑

待办编辑区行为：

- 每条待办左侧显示 checkbox。
- 点击 checkbox 切换 `checked`。
- 待办文字可以直接编辑。
- 按 Enter 新增下一条待办。
- 当前项为空且按 Backspace 时，可以删除该项并聚焦上一项。
- 至少保留一条可编辑空项，避免用户进入空白死状态。

### 5.3 待办项视觉

未完成项：

- 正常文字。
- checkbox 未勾选。

已完成项：

- checkbox 已勾选。
- 文字颜色变浅。
- 文字加删除线。

### 5.4 自动保存

待办模式下这些操作必须自动保存：

- 新增待办项。
- 修改待办文字。
- 勾选/取消勾选。
- 删除待办项。
- 模式切换。

保存策略：

- 文字输入使用 debounce。
- checkbox 勾选可以立即保存，或合并到短 debounce 中。
- 保存失败时不能回滚用户当前输入。
- 保存失败时显示“保存失败”和“重试”。

## 6. 便签列表优化

### 6.1 卡片视觉

便签列表项从普通列表改为卡片式：

- 卡片背景使用便签颜色的浅色版本。
- 保留清晰边框或阴影，但不要过度装饰。
- 选中态必须明显。
- 置顶便签和普通便签分区显示。

颜色建议：

- `yellow`：浅黄背景。
- `blue`：浅蓝背景。
- `green`：浅绿背景。
- `pink`：浅粉背景。
- `gray`：浅灰背景。

### 6.2 列表内容

每张卡片显示：

- 标题或自动标题。
- 正文摘要或待办摘要。
- 更新时间。
- 置顶标识。
- 待办完成进度。

自动标题规则：

1. 如果 `title` 非空，显示 `title`。
2. 如果 `title` 为空且 `mode=text`，显示 `content` 第一行。
3. 如果 `title` 为空且 `mode=checklist`，显示第一条非空待办文字。
4. 如果仍为空，显示“无标题便签”。

摘要规则：

- 普通便签显示正文前 1-2 行。
- 待办清单显示前 2-3 条待办。
- 已完成待办可以显示勾选状态。

完成进度：

- 当 `mode=checklist` 时显示 `已完成数/总数`。
- 如果没有任何非空待办项，显示 `0/0` 或不显示，由实现固定。

### 6.3 分区

主页列表：

- 置顶区标题：“置顶”。
- 普通区标题：“便签”。
- 搜索状态下仍保留置顶/普通分区。

归档页：

- 可以保留置顶/普通分区。
- 不要求支持编辑，只需查看、取消归档、删除。

回收站：

- 不要求置顶/普通分区。
- 按删除时间倒序。

## 7. 编辑体验优化

### 7.1 新建自动聚焦

新建便签后：

- 默认聚焦标题输入框。
- 如果用户用快捷键新建，行为相同。

可接受替代：

- 默认聚焦正文，但必须在产品中保持一致。

### 7.2 快捷键

支持：

- `Cmd/Ctrl + Enter`：新建下一条便签。

规则：

- 在标题、正文、待办项输入时都生效。
- 快捷键触发前，当前便签如有待保存内容，需要先触发保存或 flush。
- 新建后自动选中新便签并聚焦输入。

### 7.3 输入区域

普通便签：

- 正文输入区域高度应随可用空间增长。
- 桌面端不应只有很矮的 textarea。
- 移动端键盘弹出后，主要输入区仍应可滚动。

待办清单：

- 待办项列表应占用主要编辑空间。
- 长清单可滚动。

### 7.4 保存失败重试

保存失败时：

- 显示“保存失败”。
- 提供“重试”入口。
- 点击重试后重新发送最近一次失败的内容。
- 重试成功后显示“已保存”。
- 用户继续编辑后，应继续尝试自动保存。

### 7.5 离开保护

当存在未保存内容或保存中状态时：

- 浏览器刷新/关闭 tab 前，应尽量触发保存。
- 如果无法确认保存完成，可以显示浏览器离开确认。
- 切换便签、返回列表、归档、删除前，应先 flush 当前待保存内容。

## 8. 回收站

### 8.1 入口

需要新增回收站入口：

- 可以放在顶部栏菜单。
- 可以和归档入口并列。
- 移动端也必须可访问。

### 8.2 回收站页

页面路径建议：

- `/trash`

页面能力：

- 查看已删除便签。
- 搜索已删除便签。
- 恢复便签。
- 永久删除便签。

空状态：

- 无删除便签时显示空状态。
- 搜索无结果时显示搜索空状态。

### 8.3 删除确认

普通删除：

- 从主页或归档页删除时，需要确认。
- 确认文案需要说明“删除后可在回收站恢复”。

永久删除：

- 必须二次确认。
- 文案需要说明“永久删除后无法恢复”。

## 9. 搜索增强

### 9.1 搜索范围

主页搜索：

- 标题。
- 正文。
- 待办项文字。

归档搜索：

- 标题。
- 正文。
- 待办项文字。

回收站搜索：

- 标题。
- 正文。
- 待办项文字。

### 9.2 高亮

搜索结果中匹配文字需要高亮。

要求：

- 标题匹配时高亮标题中的关键词。
- 摘要匹配时高亮摘要中的关键词。
- 待办项匹配时高亮待办文字中的关键词。
- 高亮不能破坏原有文字。
- 搜索关键词为空时不显示高亮。

### 9.3 清空搜索

搜索框输入非空时显示清空按钮。

点击清空：

- 清空搜索词。
- 列表恢复默认内容。
- 移动端不应造成布局跳动。

## 10. 排序

### 10.1 本轮排序规则

本轮必须保持：

1. 置顶便签在普通便签前。
2. 同一区内按 `updatedAt` 倒序。
3. 归档页不影响主页排序。
4. 回收站按 `deletedAt` 倒序。

### 10.2 手动拖拽排序

手动拖拽排序本轮不作为必须项。

如果研发成本可控，可以只支持置顶区拖拽排序：

- 拖拽只影响置顶便签。
- 更新 `sortOrder`。
- 普通便签仍按 `updatedAt`。

如果实现拖拽会影响本轮交付，则延期。

## 11. 未来桌面壳预留

### 11.1 单条便签视图

建议新增页面：

- `/notes/:id/floating`

目标：

- 模拟未来 Windows/Mac 悬浮窗中的单条便签体验。
- 不等于实现桌面 App。

页面要求：

- 无侧边栏。
- 无完整顶部导航。
- 只显示当前便签编辑能力。
- 保留标题、正文或待办清单、颜色、置顶、删除。
- 宽度 320px 下可正常编辑。
- 高度较小时内容区可滚动。

权限：

- 未登录访问时跳转登录页。
- 只能访问当前用户自己的便签。

### 11.2 桌面窗口字段验证

以下字段已有或需要继续保留：

- `windowX`
- `windowY`
- `windowWidth`
- `windowHeight`
- `alwaysOnTop`

本轮要求：

- API 仍允许读写这些字段。
- 前端主界面不需要展示这些字段。
- 技术部需要提供至少一组接口验证，证明 PATCH 后能再次 GET 到这些值。

## 12. 图片能力预研和 M3 候选

图片支持有价值，但本轮不建议强塞进 M2。

原因：

- 涉及上传接口。
- 涉及服务器文件存储。
- 涉及图片大小限制和压缩。
- 涉及删除图片后的文件清理。
- 涉及备份和迁移。
- 手机浏览器上传兼容需要额外测试。

M3 候选范围：

1. 每条便签支持添加图片附件。
2. 图片显示在正文或待办清单下方。
3. 支持点击预览。
4. 支持删除图片。
5. 限制单张图片大小。
6. 限制每条便签图片数量。

建议数据模型：

```text
Attachment
- id
- userId
- noteId
- type: image
- url
- filename
- mimeType
- size
- createdAt
```

建议存储策略：

- 第一版可以使用服务器本地磁盘。
- 路径示例：`/uploads/notes/{noteId}/{imageId}.jpg`
- 后续如有需要再迁移对象存储。

## 14. 完成定义

M2 视为完成，当且仅当：

- P0 项全部完成。
- P1 中除拖拽排序以外的项目尽量完成，未完成项需明确列出原因。
- 测试清单中与已交付范围相关的项目全部通过。
- 原 MVP 功能不能回退。
- 技术部提供迁移说明，说明旧便签如何获得默认 `mode=text` 和空 `checklistItems`。
- 技术部提供部署说明，包含数据库 schema 更新步骤。
