## 3. 多选删除

### 3.1 交互
- 左侧列表顶部「选择」进入多选模式：每条便签左侧显示圆形 checkbox，顶部显示「已选 X 条 / 全选 / 取消全选 / 取消 / 删除」。
- 删除前弹确认框：`确定将选中的 X 条便签移入回收站？`
- 确认后批量软删，删除成功退出多选模式并刷新列表。
- 当前正在编辑的便签被选中删除后，编辑区清空。
- 全选只作用于当前列表/搜索结果可见便签。
- 搜索状态下只删除已选中项。

### 3.2 API
`POST /api/notes/bulk-delete`，请求 `{ "ids": [...] }`，响应 `{ ok, deletedIds, notFoundIds }`。

限制：ids 非空数组（空 → 400 `INVALID_REQUEST`）、单次 ≤100（超限 → 400）、重复 id 去重、只删当前用户拥有且未删除的便签；`notFoundIds` 含不存在/非本人/已在回收站的 id。删除为软删（仅置 `deletedAt=now`），不进物理删除。`deletedIds` 为空但请求合法仍返回 200。

### 3.3 离线
离线时「删除」按钮禁用，title 提示「离线时暂不支持批量删除，请联网后再试。」；不因批量删除失败丢本地内容。

## 4. 自定义头像

### 4.1 数据模型
`User` 新增（`prisma db push` 非破坏性加列）：
```prisma
avatarUrl         String?
avatarStoragePath String?
avatarMimeType    String?
avatarSize        Int      @default(0)
```

### 4.2 API
- `POST /api/auth/avatar`：multipart 上传。校验登录与 active；MIME ∈ {image/jpeg, image/png, image/webp}（否则 400 `UNSUPPORTED_AVATAR_TYPE`）；≤1MB（否则 413 `AVATAR_TOO_LARGE`）；sharp 元数据校验拦截伪装可执行文件（400 `UNSUPPORTED_AVATAR_TYPE`）；计入存储额度（超限 413 `STORAGE_QUOTA_EXCEEDED`）。写盘 `uploads/avatars/{随机}.{ext}` → 更新 User 字段与 `storageUsedBytes` → 替换时删除旧文件；写库失败回滚删新文件，不留孤儿。返回最新 `user`。
- `DELETE /api/auth/avatar`：删当前用户头像文件、清空字段、扣减额度，返回最新 `user`。
- `GET /api/auth/me` 返回头像字段；管理员用户列表返回头像字段。

### 4.3 额度
- 上传前检查 `storageUsed - 旧头像size + 新头像size <= quota`。
- 替换头像先释放旧头像占用再放新头像。
- 移除头像释放占用。

### 4.4 文件访问安全（技术方案：**鉴权读取**）
经 `/api/files/[...path]` 读取 `avatars/*`：文件名随机不可猜；只允许读 `avatars/` 目录下文件（禁止路径穿越）；**登录鉴权**——本人或管理员可读，他人 403，未登录 401；`Cache-Control: private, no-store` 使删除后旧 URL 立即失效（404）。选鉴权读取而非受控公开 URL，保证头像属于用户私密展示且删除即时生效。

## 5. 更新时间准确性

- 根因：Prisma `@updatedAt` 在**每次** `prisma.note.update()` 调用时自动刷新，前端防抖/打开便签触发的"保存"即便内容未变也会更新时间。
- 修复：后端 PATCH 规范化（title/content 空串归一、checklist JSON 字符串化比对）后**逐字段比较**；无任何真实变化 → **跳过 `prisma.note.update()`**，直接返回序列化结果。
- 效果：打开/查看/切换选中/聚焦不输入均不改 `updatedAt`；只有真实编辑（正文/标题/待办勾选/归档/置顶/附件增删）才更新。

## 6. 更新说明弹窗

- 登录后（受保护布局）首屏展示一次，`localStorage["seenReleaseNote_M10_8"]="true"` 记录已读，点「知道了」关闭，刷新/重开不再弹。

### 7.2 部署中发现的服务器既有问题（重要，已修复）
服务器项目根存在**陈旧的 `./schema.prisma`**（与 `prisma/schema.prisma` 并存），Prisma CLI 解析到根文件，导致 `db push` 报告「already in sync」却未新增列。处置：将 `prisma/schema.prisma` 内容同步到根 `schema.prisma` 后 `db push` 成功加列，客户端重新生成包含头像字段。**后续每次 schema 改动，必须同时同步两个 schema 文件**（或删除根文件并固定 Prisma 配置）。已在本次部署完成验证。

> 注：过程中曾误用 `--force-reset` 触发一次生产库清空，已立即从部署前备份恢复（users/notes/attachments 计数恢复与基线一致），无数据丢失。已记录教训：生产库绝不使用 `--force-reset`。
