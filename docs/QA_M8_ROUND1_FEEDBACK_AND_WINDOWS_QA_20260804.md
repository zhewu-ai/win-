# M8 第一轮复验反馈与 Windows 实机调试流程改造

日期：2026-08-04

结论：部分通过，仍不通过。普通便签文本响应式换行已有改善，但待办模式、小标题、桌面壳 command 权限、时间戳、图片联动等问题仍未解决。

## 1. 本轮已改善项

### M8-R1-PASS-01：普通便签模式文字已能随窗口宽度自适应换行

用户反馈：

- 便签模式下，文字可以跟随窗口缩放无级换行。
- 这一项方向正确。

后续要求：

- 保持该行为。
- 不要为了修待办模式回退普通便签模式的响应式效果。

## 2. 仍未通过问题

### M8-R1-F01：待办模式文字仍被裁切，不能自然换行

严重级别：P0

用户现象：

- 普通便签模式已经能换行。
- 但待办模式中，待办文字输入/操作区域仍会被裁切。
- 长待办无法像普通文本一样随窗口宽度自然换到下一行。

产品要求：

- 待办项长文本必须能在小窗口中自然换行。
- 不能因为左侧勾选圆圈、拖拽手柄、删除按钮等固定元素，把正文输入区域压到裁切。
- 260px 悬浮窗、320px 主窗口都要可用。

技术建议：

- 如果当前待办项使用单行 `input`，应改为 autosize textarea 或支持换行的编辑控件。
- 待办项布局建议使用：
  - 左侧固定宽度：勾选圆圈/拖拽手柄
  - 右侧 `min-width: 0; flex: 1;`
  - 文本控件 `width: 100%`
  - 长词/长句允许 `overflow-wrap: anywhere` 或等价策略
- 不允许用横向滚动解决。

验收标准：

1. 在待办模式输入一条 80 字以上的中文长句。
2. 将悬浮窗缩到 260px 宽。
3. 待办文字自然换成多行，不裁切，不横向滚动。
4. 勾选按钮、拖拽手柄、删除按钮不遮挡文字。

### M8-R1-F02：待办小标题/分段仍未改对

严重级别：P1

用户现象：

- “待办标题/小标题”目前还没有达到预期。
- 用户需要的是在待办中插入一个轻量分隔标题，而不是复杂分组。

产品要求：

- 小标题是待办列表里的一个特殊行。
- 小标题没有勾选按钮。
- 小标题可以编辑、删除、拖拽排序。
- 小标题下方的待办视觉上属于这一段。
- 已完成项仍统一进入底部“已完成”，不要每个小标题下面都有一个已完成区。

推荐数据结构：

```ts
type ChecklistRow =
  | { kind: "heading"; id: string; text: string; sortOrder: number }
  | { kind: "todo"; id: string; text: string; checked: boolean; sortOrder: number }
```

验收标准：

1. 可以在任意两个待办之间插入小标题。
2. 小标题没有圆形勾选框。
3. 小标题可拖拽排序。
4. 小标题下面的待办勾选后进入统一已完成区。

### M8-R1-F03：Tauri ACL 不允许调用 `open_floating_note`，置顶/悬浮窗仍不可用

严重级别：P0

用户现象：

- Windows App 内点击相关操作时，出现类似错误：

```text
ACL 不允许使用命令 open_floating_note
```

或：

```text
打开悬浮窗失败，请确认在桌面壳中运行
窗口置顶操作失败，请确认在桌面壳中运行
```

产品判断：

这不是产品交互问题，是 Tauri v2 权限/capability 配置或远程页面调用 command 的链路问题。必须先修通，否则 Windows 壳的核心价值不存在。

技术排查方向：

1. Tauri v2 的前端 command 调用受 ACL/capability 控制。需要在 capability 中明确授权前端窗口/远程页面可调用这些 command。
2. 需要验证以下窗口都被授权：
   - `main`
   - `floating_*`
3. 需要验证以下 command 都被授权：
   - `open_floating_note`
   - `toggle_always_on_top`
   - `get_always_on_top`
4. 如果 command 名称在权限系统里被映射为 `allow-open-floating-note` 等格式，需要按 Tauri 生成/要求的权限名配置，不要只写窗口名。
5. 如果线上远程页面 `https://notes.hello-mylife.online` 调用 Tauri command，还需要确认远程 URL 是否在安全配置/能力范围内允许。
6. 技术部交付时必须贴出：
   - `src-tauri/capabilities/*.json`
   - `src-tauri/tauri.conf.json`
   - Windows 控制台或 DevTools 中的完整 ACL 报错

验收标准：

1. Windows App 内点击“极小模式”，能打开悬浮窗。
2. Windows App 内点击“窗口置顶”，不再出现 ACL 错误。
3. 悬浮窗可以置顶在浏览器/AE/C4D/资源管理器上方。
4. 技术部提供 Windows 实机录屏证明。

### M8-R1-F04：时间戳仍在顶部，未按产品方向弱化

严重级别：P2

用户现象：

- 时间戳仍在顶部。
- 顶部视觉占位不合理，尤其在小窗口中浪费空间。

产品要求：

- 顶部不再强显示大时间戳。
- 改到底部弱显示：

```text
最后编辑于 2026年8月4日 14:30
```

验收标准：

1. 主编辑页顶部不再显示大时间戳。
2. 悬浮窗顶部不显示大时间戳。
3. 底部弱显示最后编辑时间。

### M8-R1-F05：图片与待办完成状态联动未实现

严重级别：P2

用户期望：

- 图片可以放到某条待办下面。
- 勾选该待办后，文字划掉，图片也变灰。

产品判断：

这不是本轮 P0，但需要作为后续独立设计，不要临时硬拼。

建议：

- 先完成图片压缩/缩略图。
- 再单独设计“附件绑定到待办项”：
  - `attachment.checklistItemId`
  - 图片可拖到某条待办下
  - 待办完成后关联图片变灰
  - 取消完成后恢复正常

### M8-R1-F06：右键菜单虽不再穿帮，但出现闪烁

严重级别：P1

用户现象：

- 右键菜单已从浏览器默认菜单变成复制/粘贴等产品内菜单。
- 但右键时菜单会在上一帧位置闪一下，再移动到正确位置。
- 体验不够稳定。

产品要求：

- 右键菜单出现位置必须稳定。
- 不能先出现在旧位置，再跳到新位置。

技术建议：

- 打开菜单前先计算位置，再渲染菜单。
- 避免复用上一次坐标渲染一帧。
- 可在 state 中一次性设置 `{x, y, visible: true}`。
- 或使用成熟 floating UI/portal 定位库，避免手写定位闪烁。

验收标准：

1. 连续在不同位置右键 10 次。
2. 菜单直接出现在鼠标位置附近。
3. 不出现旧位置闪烁。

## 3. 当前最大的流程问题：没有 Windows 实机调试闭环

当前协作方式：

```text
Mac 本地开发 -> 推到 GitHub -> GitHub Actions 打 Windows 包 -> 用户下载 Windows 包实测 -> 反馈问题
```

这个流程可以做发布验收，但不适合调试 Windows 桌面壳能力。置顶、窗口、右键、ACL 注入、WebView2 行为都必须在真实 Windows 图形桌面里测试。

## 4. 建议建立新的 Windows 调试闭环

### 方案 A：准备一台专用 Windows 测试机，安装远程控制和自托管 Runner

推荐优先级：最高。

做法：

1. 准备一台 Windows 电脑或 Windows 云桌面。
2. 安装：
   - Git
   - Node.js
   - Rust
   - Tauri 依赖
   - WebView2 Runtime
   - Chrome/Edge
   - GitHub self-hosted runner
   - 远程控制工具，例如 Tailscale + RDP、AnyDesk、ToDesk
3. 技术部可以直接在这台 Windows 上：
   - 拉代码
   - 本地运行 Tauri dev
   - 看 DevTools
   - 实时测置顶/右键/悬浮窗
   - 录屏交付

优点：

- 最接近真实用户环境。
- 能直接调试 ACL、WebView2、置顶。
- 不需要每次都等 GitHub 打包。

缺点：

- 需要维护一台 Windows 环境。

### 方案 B：租一台 Windows 云桌面/云主机做测试机

推荐优先级：高。

适合当前团队都在 Mac 上的情况。

要求：

- 必须是带 GUI 的 Windows，不是纯命令行服务器。
- 能安装 WebView2 和 Tauri 依赖。
- 能远程桌面登录。

优点：

- 不占用个人电脑。
- 环境稳定，可复现。

缺点：

- 有成本。
- 图形性能和置顶行为可能仍与本地 Windows 略有差异，但比 Mac 猜测强很多。

### 方案 C：继续 GitHub Actions 打包，但增加诊断面板和日志

推荐优先级：中。可以作为 A/B 的补充，不建议单独依赖。

需要新增一个桌面壳诊断入口，例如：

```text
/desktop-diagnostics
```

显示：

1. 是否检测到 Tauri 环境。
2. 当前窗口 label。
3. 是否能调用 `get_always_on_top`。
4. 是否能调用 `toggle_always_on_top`。
5. 是否能调用 `open_floating_note`。
6. 当前 app version / git commit / build time。
7. 最近一次 command 错误堆栈。

优点：

- 用户反馈时不只说“失败”，而是能给技术部错误证据。

缺点：

- 仍然不能替代实时调试。

## 5. 推荐决策

建议立刻采用：

```text
方案 A 或 B + 方案 C
```

也就是：

1. 搭一台 Windows 实机/云桌面作为固定调试机。
2. 同时在 App 里加桌面壳诊断面板。

这样之后 Windows 壳问题不再靠用户反复下载安装包验证。

## 6. 关于“记忆迁移到 Windows 电脑”的判断

不建议迁移 Codex/AI 记忆到 Windows 电脑。

原因：

1. 产品上下文和规格文档已经在仓库里。
2. Windows 机器只需要作为测试/构建/调试环境。
3. 技术决策和验收判断仍可以在当前 Mac 侧完成。

建议做法：

- 把所有重要上下文沉淀成仓库文档，而不是依赖某台机器上的 AI 记忆。
- Windows 测试机只需要：
  - 拉取代码
  - 运行项目
  - 生成日志
  - 录屏
  - 回传结果

## 7. 下一步给技术部的任务拆分

### 第一批：先修壳能力

1. 修复 Tauri ACL command 权限。
2. 增加 `/desktop-diagnostics` 或等价诊断面板。
3. 建立 Windows 实机调试环境。
4. 重新验证置顶和悬浮窗。

### 第二批：修待办布局

1. 待办长文本换行。
2. 小窗口下待办操作区不裁切。
3. 小标题/分段行按产品要求实现。

### 第三批：体验细节

1. 时间戳移到底部。
2. 右键菜单闪烁修复。
3. 图片压缩/缩略图。
4. 图片绑定待办项方案评估。

## 8. 本轮通过标准

这一轮不要用“功能写了”作为通过标准，要用实机体验判断：

1. Windows 壳内不再出现 ACL command 错误。
2. 极小模式能打开。
3. 悬浮窗能置顶。
4. 待办模式长文本能自然换行，不裁切。
5. 右键菜单不穿帮、不闪烁。
6. 普通便签和待办在小窗口里都像桌面便签，而不是网页被硬塞进小壳。
