# SPEC M16R1：统一便签/待办与轻富文本基础

日期：2026-08-12

状态：待技术部评估与排期

关联路线图：`docs/ROADMAP_M16_便签知识化升级路线图_20260812.md`

## 一、本阶段目标

M16R1 的目标不是立刻做完整富文本，也不是做完整知识库。

本阶段只解决一个核心结构问题：

```text
便签和待办不应继续作为两种互斥编辑模式。
```

产品目标：

1. 用户仍然可以点“新建便签”或“新建待办”。
2. 新建待办只是创建一篇默认带 checklist 的便签。
3. 一篇内容里可以同时存在文字、待办、内部链接、外部链接。
4. 为后续图片正文、标签、反向链接、知识图谱、AI 资料库打基础。

## 二、为什么要改

当前模式的问题：

- 如果便签升级为富文本，里面有图片、表格、链接，再切到待办模式会无法完整表达。
- 如果待办里也需要说明文字、图片或项目资料，独立待办模式会越来越不够用。
- “便签/待办切换”本质上是在转换数据类型，后续越复杂越容易丢数据。

推荐方向：

```text
内容统一为 Note Document
Checklist 是文档中的一种 block
```

这更接近用户直觉：正常写文字时，点一下待办按钮，就能在正文里出现几个待办项。

## 三、本轮范围

### P0：方案设计和底层兼容

技术部必须先完成设计，不允许直接改生产数据结构。

需要输出：

1. 当前 `note.content`、`checklistItems`、图片附件、内部链接的现状梳理。
2. 新文档模型草案。
3. 旧数据迁移策略。
4. 回滚策略。
5. 搜索、自动保存、离线、桌面壳影响说明。

### P0：统一创建入口语义

保留用户能理解的两个入口：

- 新建便签。
- 新建待办。

但底层语义调整为：

- 新建便签：创建空文档。
- 新建待办：创建默认包含 checklist block 的文档。

验收：

1. 用户点新建便签后，可以输入普通文字。
2. 用户点新建待办后，默认出现可编辑待办项。
3. 待办文档里也可以添加普通文字。
4. 普通便签里也可以插入 checklist。
5. 不再出现“切换模式后图片/链接/内容不知道怎么处理”的交互。

### P0：Checklist block

Checklist 应成为正文中的一种内容块。

基础能力：

- 插入 checklist。
- 新增待办项。
- 勾选 / 取消勾选。
- 删除待办项。
- 回车新增下一条。
- 多行粘贴拆成多条。
- 已完成项显示清楚，但不要占过多空间。

验收：

1. 一篇文档中可以有普通文字 + checklist。
2. checklist 前后可以继续输入文字。
3. 多行粘贴仍然自然可用。
4. 旧待办数据打开后不丢失。
5. 保存、刷新、切换便签后状态一致。

### P0：保留现有内部便签链接

现有内部链接能力不能丢：

- `[[便签]]` 或当前已有 `[[note:id|title]]` 底层表示要兼容。
- 编辑态仍显示为链接芯片。
- 外部 URL 仍显示为可点击链接。
- 旧内容 round-trip 不得被格式化破坏。

验收：

1. 旧便签里的内部链接刷新后仍正常显示。
2. checklist 里的内部链接仍正常显示。
3. 外部 URL 仍可打开。
4. 编辑保存后底层内容不出现链接丢失或裸代码退化。

### P1：轻量格式工具栏雏形

本轮可以只做最小工具栏，为 M16R2 打基础。

建议按钮：

- `Aa`：段落 / 标题。
- 加粗。
- 斜体。
- 列表。
- 待办。
- 引用。
- 分割线。
- 插入内部链接。

要求：

- 用户不需要输入 Markdown 语法。
- Markdown 快捷输入可以支持，但不能只靠快捷语法。
- 320px / 390px 下工具栏必须能收纳，不得挤压正文。

### P1：图片正文能力先设计，不一定本轮落地

图片是后续必须能力，但 M16R1 不要求直接完成正文图片混排。

技术部需要给出方案：

1. 正文图片是否复用现有附件上传接口。
2. 图片节点如何存储。
3. 图片删除是否删除真实文件。
4. 图片缩略图、原图、压缩策略。
5. 小服务器和带宽压力如何控制。
6. 桌面壳拖拽/粘贴图片是否复用 Web 能力。

M16R1 可以只输出方案，M16R2 再落地。

## 四、建议技术方案

### 4.1 优先继续扩展现有 Tiptap

当前项目已经在内部链接编辑中使用 Tiptap。建议优先沿用，不要直接换成另一套重型编辑器。

原因：

- 已有链接芯片、URL 装饰、`[[` 搜索基础。
- 可以逐步增加 checklist、heading、list、quote、image 等扩展。
- 风险比直接切 BlockNote/Notion 式编辑器小。

### 4.2 数据模型建议

需要技术部评估两种路线。

方案 A：短期兼容层

```text
旧字段继续保留
编辑器内部使用文档结构
保存时仍尽量序列化回现有字段
```

优点：迁移风险低。

缺点：后续图片、表格、复杂 block 会受限。

方案 B：新增文档字段

```text
note.documentJson 新增富文本文档结构
note.content 保留纯文本投影
checklistItems 保留旧数据兼容
```

优点：长期清晰，适合图片、表格、标签、AI。

缺点：需要迁移、回滚、搜索投影、接口兼容。

建议：M16R1 先做方案 B 的设计和小范围实现，但不要在没有回滚方案时全量迁移。

### 4.3 搜索与列表摘要

无论底层是否变成 JSON，都必须保留纯文本投影：

- 左侧列表摘要使用纯文本投影。
- 搜索使用纯文本投影。
- AI 可读取经过脱敏/裁剪的纯文本投影。
- 图片、表格、链接不应破坏列表预览。

### 4.4 桌面壳兼容

必须同时验证：

- Web 浏览器。
- macOS Tauri 壳。
- Windows Tauri 壳。

重点：

- 粘贴。
- 拖拽。
- 外链打开浏览器。
- 图片上传。
- 320px / 390px 窄宽工具栏。

## 五、不做范围

M16R1 不做：

- 完整 Obsidian。
- 完整 Notion/语雀 block editor。
- 知识图谱。
- 标签系统全量实现。
- 文件夹系统全量实现。
- 图片正文混排全量落地。
- 表格编辑器。
- 多人协同。
- 分享。
- AI 资料库问答。

这些进入路线图后续阶段，不要混进本轮。

## 六、验收清单

### 数据兼容

1. 旧普通便签打开正常。
2. 旧待办打开正常。
3. 旧内部链接打开正常。
4. 旧外部 URL 打开正常。
5. 旧图片附件仍显示。
6. 刷新页面后内容不丢。
7. 切换便签后自动保存不丢。

### 编辑体验

1. 新建便签可输入文字。
2. 新建待办默认出现 checklist。
3. 普通便签可插入 checklist。
4. checklist 前后可输入普通文字。
5. checklist 支持回车新增、多行粘贴、勾选、删除。
6. 内链芯片仍可插入和打开。
7. 外链仍可点击打开。

### 响应式和壳

1. 1440px 桌面浏览器工具栏清晰。
2. 720px 不拥挤。
3. 390px 不横向溢出。
4. 320px 不遮挡正文。
5. macOS 壳内可编辑、粘贴、拖拽不异常。
6. Windows 壳需实机验证后才能标记通过。

### 技术验证

1. `npm run build -- --webpack` 通过。
2. `npx tsc --noEmit` 通过。
3. 自动保存相关测试通过。
4. 旧数据迁移脚本有 dry-run。
5. 迁移前有数据库备份。
6. 日志不输出用户全文、图片 base64、密钥。

## 八、产品口径

对外或对内说明时，不建议说“我们要做 Markdown 编辑器”。

建议表述：

```text
便签将升级为轻量文档。用户可以像苹果备忘录一样用按钮排版、插入待办和图片；熟悉 Markdown 的用户也可以使用快捷输入。后续会逐步加入标签、互链、反向链接和关系图，让便签成为可整理、可检索、可被 AI 理解的资料库。
```
