# 全平台便签 M8.6：成熟响应式稳定方案与交付标准

日期：2026-08-06

## 1. 背景

M8.5 已经尝试修复横向缩放稳定性，但复测发现仍未达到成熟桌面 App 的体感：

- 700px 双栏下，“便签/待办”文字仍会竖排。
- 600/560/520px 从宽屏收窄时，侧边栏仍保留，右侧内容被裁切。
- 当前断点按 viewport 判断，而不是按编辑区实际可用宽度判断。
- 验收漏掉了 760/700/640/600/560 等真正容易出问题的临界宽度。

产品目标需要重新明确：

> 我们不是为了“简单”而简单，而是在效果尽可能好、体验尽可能好的前提下保持实现可控。如果某个方案特别复杂、收益有限，再权衡性价比。

M8.6 的目标是用成熟产品常见的响应式策略，替代当前“控件各自断点 + 双栏硬撑”的不稳定方案。

## 2. 本轮目标

M8.6 只解决一个核心问题：

> 横向缩放时，界面稳定、可预期、不过度跳变，不出现文字竖排、工具栏变高、右侧裁切、侧边栏突兀消失。

必须做到：

1. 明确定义布局模式，而不是让各组件各自响应。
2. 双栏必须有最小可用宽度，放不下就进入单栏。
3. 工具栏按编辑区容器宽度响应，不只看 viewport。
4. 工具栏整组切换，避免多个控件分散跳变。
5. 使用短过渡动画降低突兀感。
6. Windows 壳实机验收临界宽度。

## 3. 本轮不做

1. 不做账号系统。
2. 不做亮色模式。
3. 不做新图片功能。
4. 不做复杂富文本。
5. 不做 Mac 壳。
6. 不做离线同步。

## 4. 设计原则

### 4.1 体验优先，但实现要可控

不要为了代码最省事，牺牲用户体感。

也不要为了追求完美响应式，引入过度复杂的布局系统。

判断标准：

- 用户能明显感受到稳定性提升，值得做。
- 只是理论更优但用户感知不强，可以不做。
- 会引入大量风险的方案，需要降级。

### 4.2 布局模式优先于零散断点

当前问题来自多个控件各自响应：

- 模式文字自己断点。
- 色球自己断点。
- 保存状态自己断点。
- 侧边栏自己断点。
- 更多按钮位置被动变化。

M8.6 要改为整体模式：

```text
舒展模式
紧凑模式
单栏模式
```

组件只根据当前模式渲染，不再各自随意跳。

### 4.3 容器宽度优先于 viewport 宽度

编辑器工具栏的可用空间取决于右侧编辑区宽度，不是整个窗口宽度。

例如：

```text
总窗口 700px
侧边栏 350px
编辑区只剩约 350px
```

这时不能因为 viewport > 640px 就显示“便签/待办”文字和完整色球。

### 4.4 放不下就切模式，不硬撑

成熟产品不会让内容在窄空间里硬撑到裁切。空间不足时，应进入更适合的模式。

## 5. 推荐布局策略

### 5.1 三种布局模式

#### A. 舒展模式

适用：

```text
窗口宽度 >= 900px
或编辑区宽度 >= 520px
```

表现：

- 双栏。
- 侧边栏 320-350px。
- 编辑器工具栏可显示文字。
- 颜色色球完整显示。
- 保存状态显示文字。
- 更多菜单保留低频操作。

示意：

```text
侧边栏 350px | 编辑区 >= 520px
```

#### B. 紧凑模式

适用：

```text
窗口宽度约 720-900px
或编辑区宽度约 360-520px
```

表现：

- 优先仍可双栏，但侧边栏应缩窄。
- 侧边栏宽度建议 260-300px。
- 编辑器工具栏图标化。
- 模式切换不显示“便签/待办”文字。
- 颜色收进颜色按钮，不显示完整色球。
- 保存状态使用固定槽位，可显示点或极短状态。
- 删除/归档/便签置顶进入更多菜单。

示意：

```text
侧边栏 260px | 编辑区 >= 360px
```

#### C. 单栏模式

适用：

```text
窗口宽度 < 620px
或无法同时满足侧边栏最小宽度 + 编辑区最小宽度
```

表现：

- 列表/详情单栏切换。
- 编辑器宽度占满。
- 顶部有返回列表按钮。
- 工具栏极简图标化。
- 全局新建/账号入口继续在侧边栏/底部入口处理。

## 6. 双栏宽度规则

### 6.1 推荐简单版

优先推荐，性价比最高：

```text
>= 720px：双栏
< 720px：单栏
```

双栏时：

```text
侧边栏：clamp(260px, 32vw, 350px)
编辑区：剩余空间，但不得低于 360px
```

如果实现 clamp 后复杂度高，可以先：

```text
>= 900px：侧边栏 350px
720-899px：侧边栏 280px
< 720px：单栏
```

### 6.2 更优版

如果技术部有能力，使用 CSS grid：

```css
grid-template-columns: minmax(260px, 350px) minmax(360px, 1fr);
```

当窗口不足以满足两列最小值时，进入单栏。

### 6.3 不推荐

不推荐继续使用：

```text
<520px 进入单栏
>580px 退出单栏
```

原因：

- 520-700px 区间会双栏硬撑。
- 右侧编辑区不够用。
- 用户仍会看到裁切和跳变。

## 7. 工具栏响应规则

### 7.1 工具栏按编辑区容器宽度判断

不要再用全局 `sm` / `md` 直接控制编辑器工具栏内部。

可选实现：

1. CSS container query。
2. ResizeObserver 测量编辑器容器宽度。
3. 根据布局模式传入 `toolbarMode`。

推荐优先：

- 如果项目配置支持 container query，用 container query。
- 如果不方便，先用布局模式传参，最简单可控。

### 7.2 三种工具栏模式

#### Toolbar Spacious

条件：

```text
编辑区 >= 520px
```

显示：

```text
返回 | 便签/待办文字 | 颜色色球 | 保存文字 | 图片 | 窗口置顶 | 更多
```

#### Toolbar Compact

条件：

```text
360px <= 编辑区 < 520px
```

显示：

```text
返回 | 模式图标 | 颜色按钮 | 保存槽位 | 图片 | 窗口置顶 | 更多
```

要求：

- 不显示“便签/待办”文字。
- 不显示完整色球。
- 保存槽位固定宽度。
- 工具栏高度 56px。

#### Toolbar Minimal

条件：

```text
编辑区 < 360px
```

显示：

```text
返回 | 模式图标 | 图片 | 置顶 | 更多
```

颜色、删除、归档、便签置顶进入更多菜单。

### 7.3 禁止项

1. 禁止“便签/待办”文字竖排。
2. 禁止工具栏变两行。
3. 禁止删除按钮单独掉行。
4. 禁止色球在临界宽度反复展开/折叠。
5. 禁止保存状态变化推动右侧按钮。

## 8. 过渡动画策略

动画可以缓解突兀感，但不能掩盖布局错误。

### 8.1 可加动画

建议加：

1. 侧边栏宽度变化：

```text
duration: 120-180ms
easing: ease-out
```

2. 侧边栏折叠/展开：

```text
width + opacity
```

3. 工具栏控件显隐：

```text
opacity + scale 0.98 -> 1
```

4. 更多菜单：

```text
opacity + translateY
```

### 8.2 不建议加动画

不要给以下区域加明显动画：

1. 正文输入区宽度。
2. 光标所在文本区域。
3. 滚动内容。
4. 用户正在拖拽排序的待办项。

原因：

这些区域动画会影响输入和操作手感。

### 8.3 动画验收

动画应让变化更自然，而不是更花。

验收标准：

- 切换不突兀。
- 不拖泥带水。
- 不影响输入。
- 不造成新的跳动。

## 9. 滚动条与 gutter

M8.5 已做 `scrollbar-gutter: stable`，M8.6 继续保留并补实机验证。

要求：

1. 所有主要滚动容器都保持稳定 gutter。
2. 滚动条出现/消失不改变内容宽度。
3. 滚动条视觉低对比、细、圆角。
4. Windows WebView2 实机验收。

## 10. 验收宽度

M8.6 必须补测真实问题区间。

宽度：

```text
1200
900
760
720
700
640
600
560
520
500
360
260
```

测试路径：

1. 从 1200px 慢慢缩到 260px。
2. 从 260px 慢慢放大到 1200px。

不能只测固定四档截图。

原因：

- 横向拖动过程中的连续体感才是核心问题。
- 迟滞/断点问题只有在连续拖动中容易暴露。

## 11. 验收标准

### 11.1 双栏/单栏

必须满足：

1. 双栏下左右都有可用空间。
2. 不出现右侧内容被裁切。
3. 不出现状态相关的怪异行为：
   - 从宽屏缩到 560 是双栏裁切；
   - 从窄屏拉到 560 又是单栏。
4. 模式切换有清晰阈值，且用户能感受到合理。

### 11.2 工具栏

必须满足：

1. 所有验收宽度下，工具栏单行。
2. 工具栏高度稳定，建议 56px。
3. 模式文字不竖排。
4. 色球不颤动。
5. 保存状态固定槽位。
6. 更多按钮不横跳。

### 11.3 动画

必须满足：

1. 侧边栏折叠/模式切换有轻微过渡。
2. 过渡时不影响输入光标。
3. 不出现布局先错位再归位。

### 11.4 滚动条

必须满足：

1. 滚动条出现/消失不影响内容宽度。
2. 滚动条视觉不像浏览器默认厚重控件。
3. Windows 壳实机表现通过。

## 12. 技术部交付物

### 12.1 实现说明

技术部必须说明：

1. 使用了哪种布局方案：
   - 简单版 720 单栏阈值；
   - 侧边栏 clamp；
   - CSS grid minmax；
   - container query；
   - ResizeObserver。
2. 为什么选择该方案。
3. 与 M8.5 相比，减少了哪些断点。
4. 哪些控件按布局模式统一切换。

### 12.2 验收证据

必须提供：

1. Windows 壳录屏：
   - 1200 -> 260 -> 1200 连续横向缩放。
2. 宽度截图：
   - 900
   - 760
   - 720
   - 700
   - 640
   - 600
   - 560
   - 520
   - 500

3. 工具栏截图：

4. 滚动条出现/消失对比。
5. 置顶功能回归测试，确认未被改坏。

## 13. 性价比边界

### 必须做

1. 解决 700px 文字竖排。
2. 解决 600/560/520px 双栏裁切。
3. 解决工具栏多次跳变。
4. 补充临界宽度验收。

### 推荐做

1. 侧边栏轻微过渡动画。
2. 工具栏显隐轻微过渡。
3. 侧边栏 clamp 或 minmax。

### 可暂缓

1. 极致连续的像素级响应式。
2. 复杂可拖拽调整侧边栏宽度。
3. 多套主题。
4. 大规模重构布局系统。

如果技术部认为 container query 或 ResizeObserver 成本高，可以先采用：

```text
720px 以下单栏 + 720-900 紧凑双栏 + 工具栏图标化
```

这比当前 M8.5 更简单，也能解决主要体感问题。

## 14. 通过标准

M8.6 通过标准：

> 横向缩放时，产品不再像网页控件被挤压，而像成熟桌面 App：双栏只在放得下时出现，紧凑模式有明确规则，单栏切换自然，工具栏稳定，动画短而稳。

如果 700px 仍竖排，或 560px 仍双栏裁切，本轮不通过。
