# PinNote M10.3 存储额度与空间提示

日期：2026-08-07

## 1. 背景

M10.1 已确认账号地基完整：历史数据归属默认用户，API 按 `userId` 隔离。

M10.2 已完成账号入口与基础身份：登录态收口、昵称/文字头像、图片入口降级。

下一步应先建立多用户资源边界：

```text
每个用户有默认存储额度。
用户能看到已用空间。
超过额度时系统能阻止高风险写入，尤其是图片上传。
```

本轮不是做管理员后台，也不是开放注册或找回密码。M10.3 只做“额度地基 + 用户侧提示”。

## 2. 产品决策

### 2.1 默认额度

默认每个用户：

```text
10 MB
```

原因：

1. PinNote 主要存纯文本，10 MB 对文字已经非常够用。
2. 当前服务器资源有限，需要防止图片/附件滥用。
3. 额度系统先建立起来，后续管理员可以单独调大。

现有 `admin` 用户可以先给：

```text
10 MB
```

如果产品侧希望自己主账号更宽裕，也可以在部署时给 `admin` 设置：

```text
50 MB
```

技术部实现时不要写死到前端；额度必须来自后端 `User.storageQuotaBytes`。

### 2.2 额度口径

已用空间应包含：

1. 便签标题。
2. 便签正文。
3. 待办数据。
4. 小标题/分组数据。
5. 附件文件大小。

建议口径：

```text
文本数据按 UTF-8 字节数估算。
附件按 Attachment.size 统计。
```

不必追求数据库文件实际占用字节级完全一致。本轮要的是稳定、可解释、可限制。

### 2.3 超额策略

不要粗暴导致用户“写了一堆才发现保存失败”。

策略：

1. 超额后，禁止上传图片。
2. 超额后，禁止新建明显超大的便签。
3. 已打开便签的小幅文字编辑尽量允许保存，或在保存前给明确提示。
4. 保存失败必须有清楚文案，不能静默失败。

本轮优先把图片上传限制做好，因为图片最容易撑爆空间。

## 3. 本轮目标

M10.3 做四件事：

1. User 增加存储额度字段。
2. 统计并维护每个用户已用空间。
3. 账号菜单显示空间用量。
4. 图片上传前检查额度，超额时阻止上传并提示。

## 4. 本轮不做

明确不做：

1. 不做管理员后台。
2. 不做注册。
3. 不做找回密码。
4. 不做邮箱验证。
5. 不做微信登录。
6. 不做头像上传。
7. 不做复杂计费/套餐。
8. 不做用户自行购买扩容。
9. 不做内容审核。
10. 不重构附件存储目录。

管理员调额度放到 M10.4。

## 5. 数据模型

在 `User` 上增加：

```prisma
model User {
  storageQuotaBytes Int @default(10485760)
  storageUsedBytes  Int @default(0)
}
```

说明：

```text
10485760 = 10 * 1024 * 1024 = 10 MB
```

要求：

1. 字段必须有默认值。
2. 老用户 `admin` 执行后自动获得默认值。
3. `storageUsedBytes` 不应由前端直接写。
4. 后端负责统计和更新。

如果担心未来超过 2GB，技术部可用 BigInt。但当前 SQLite + 小服务器阶段，`Int` 足够。若采用 BigInt，API 返回时要转 number/string 并统一前端处理。

## 6. 统计规则

### 6.1 文本大小

建议统计字段：

```text
Note.title
Note.content
Note.checklistItems
Note.checklistGroups
```

使用 UTF-8 字节数：

```ts
new TextEncoder().encode(value).length
```

服务端 Node 可使用：

```ts
Buffer.byteLength(value ?? "", "utf8")
```

### 6.2 附件大小

附件大小使用：

```text
Attachment.size
```

要求：

1. 上传成功后增加用量。
2. 删除附件后减少用量。
3. 永久删除便签时，其附件用量也要减少。
4. 软删除到回收站不减少用量。
5. 从回收站恢复不增加用量。

### 6.3 回收站是否计入额度

产品决策：

```text
回收站内容仍计入额度。
```

原因：

1. 文件还在服务器上。
2. 便签仍可恢复。
3. 不计入会被用来绕过额度。

只有永久删除后才释放空间。

## 7. 维护方式

推荐做两层：

### 7.1 实时维护

在这些操作中更新 `storageUsedBytes`：

1. 新建便签。
2. 编辑便签。
3. 上传附件。
4. 删除附件。
5. 永久删除便签。
6. 回收站自动清理。

编辑便签时建议：

```text
newUsage = oldUserUsage - oldNoteSize + newNoteSize
```

不能简单只增加，否则用户删文字后用量不会下降。

### 7.2 兜底重算

新增一个后端工具函数或脚本：

```text
recalculateStorageUsage(userId)
```

用途：

1. M10.3 首次上线时统计历史数据。
2. 以后发现用量异常时可修复。
3. 管理员后台之前可用脚本人工校正。

初次部署后必须对 `admin` 执行一次重算。

## 8. API 设计

### 8.1 当前用户接口

扩展：

```text
GET /api/auth/me
```

返回：

```json
{
  "ok": true,
  "user": {
    "id": "xxx",
    "username": "admin",
    "displayName": null,
    "avatarColor": null,
    "storageQuotaBytes": 10485760,
    "storageUsedBytes": 12345
  }
}
```

### 8.2 上传附件额度检查

接口：

```text
POST /api/notes/:id/attachments
```

要求：

1. 上传前读取当前用户额度。
2. 计算本次上传文件总大小。
3. 如果 `storageUsedBytes + uploadSize > storageQuotaBytes`，拒绝上传。
4. 返回明确错误码。

建议错误：

```json
{
  "ok": false,
  "error": "STORAGE_QUOTA_EXCEEDED",
  "message": "存储空间不足，无法上传图片"
}
```

状态码建议：

```text
413 Payload Too Large
```

或：

```text
403 Forbidden
```

技术部二选一即可，但前端要统一处理。

### 8.3 便签保存额度检查

接口：

```text
POST /api/notes
PATCH /api/notes/:id
```

建议：

1. 新建便签如果会超额，返回 `STORAGE_QUOTA_EXCEEDED`。
2. 编辑便签如果超额，返回明确错误。
3. 前端收到后不能显示“已保存”。
4. 如果只是小幅编辑导致略超，产品允许技术部先采用宽松策略，但必须有记录。

本轮验收优先看图片上传限制；文本保存限制可先做基础版本。

## 9. UI 设计

### 9.1 显示位置

放在：

```text
左下角账号菜单 -> 账号与存储区域
```

不需要单独页面。本轮先做账号菜单里的轻量 UI。

用户点击左下角账号区域后，菜单里应包含：

```text
文字头像 + 昵称/username
账号信息
存储空间进度条
已用 / 总量
状态提示
修改昵称
外观切换
退出登录
```

建议结构：

```text
┌──────────────────────────────┐
│  A  admin                    │
│     @admin                   │
├──────────────────────────────┤
│ 存储空间                     │
│ ███████░░░  1.2 MB / 10 MB   │
│ 空间正常 / 空间快满 / 已满   │
├──────────────────────────────┤
│ 修改昵称                     │
│ 外观                         │
│ 退出登录                     │
└──────────────────────────────┘
```

显示内容：

```text
已用 1.2 MB / 10 MB
进度条
状态提示
```

### 9.2 提示阈值

建议：

```text
< 80%：正常
80% - 95%：空间快满
>= 95%：空间即将用尽
>= 100%：空间已满
```

文案建议：

```text
空间快满
空间即将用尽
空间已满，无法上传图片
```

视觉要求：

1. 不要做成很重的警告条。
2. 正常状态轻量展示。
3. 超过 80% 后再明显提醒。
4. 不破坏 M9 左侧视觉。
5. 进度条不能挤压昵称、菜单项和退出按钮。
6. 390px/320px 下菜单内容不能横向溢出。
7. 额度数字较长时要能换行或压缩，不要撑破菜单。

### 9.3 图片上传失败提示

当用户从更多菜单添加图片但空间不足：

```text
提示：存储空间不足，无法上传图片。请删除不需要的图片或便签后再试。
```

不能静默失败。

## 10. 数据安全执行顺序

生产执行顺序：

1. 备份生产数据库。
2. 记录 User / Note / Attachment 数量。
3. `PRAGMA integrity_check = ok`。
4. 部署 schema。
5. `prisma db push`。
6. 对 `admin` 执行历史用量重算。
7. 验证 `storageQuotaBytes` 和 `storageUsedBytes`。
8. build。
9. 重启服务。
10. 健康检查。
11. UI 与 API 回归。

## 11. 验收标准

### 11.1 数据验收

必须提供：

```text
User: 前 -> 后
Note: 前 -> 后
Attachment: 前 -> 后
admin.storageQuotaBytes
admin.storageUsedBytes
历史文本大小
历史附件大小
```

通过标准：

1. User / Note / Attachment 数量不异常减少。
2. `admin` 有额度。
3. `admin.storageUsedBytes` 与重算结果一致。
4. 旧便签和旧图片仍可打开。

### 11.2 UI 验收

必须通过：

1. 账号菜单能看到已用空间。
2. 已用 / 总量格式清楚。
3. 进度条显示正常。
4. 昵称、文字头像、外观切换、退出登录不受影响。
5. 亮色/暗色都可读。
6. 390px/320px 不重叠。

### 11.3 额度限制验收

必须通过：

1. 正常空间下可以上传图片。
2. 人工把额度调小后，上传图片被阻止。
3. 超额错误提示清楚。
4. 被阻止的上传不会产生附件记录。
5. 被阻止的上传不会留下孤儿文件。
6. 删除附件后空间用量下降。
7. 永久删除带附件便签后空间用量下降。
8. 软删除到回收站不会释放空间。

### 11.4 回归验收

必须复测：

1. 登录。
2. 修改昵称。
3. 新建普通便签。
4. 新建待办便签。
5. 编辑保存。
6. 搜索。
7. 归档/恢复。
8. 删除/恢复/永久删除。
9. 更多菜单添加图片。
10. 旧图片查看。
11. 断网防丢保护。

## 12. 不通过标准

出现以下任一情况不能通过：

1. 历史便签看不见。
2. 旧图片打不开。
3. `storageUsedBytes` 明显不准。
4. 超额后仍能上传图片。
5. 上传被拒但留下孤儿文件。
6. 删除附件后空间不下降。
7. 软删除释放空间。
8. 账号菜单显示重叠或破坏 M9 视觉。
9. 本轮混入管理员后台、注册、找回密码等非本轮范围。

## 13. 交付物要求

技术部交付时必须提供：

1. 改动文件清单。
2. schema 变更说明。
3. 生产数据库备份路径。
4. `db push` 结果。
5. 历史用量重算结果。
6. User / Note / Attachment 数量前后对比。
7. `admin` 额度与已用空间。
8. 账号菜单空间显示截图。
9. 超额上传拦截图或日志。
10. 删除附件后空间下降证据。
11. 回归测试结果。
12. 回退方案。

## 14. 回退方案

若出现历史数据不可见、附件异常、保存异常：

```text
停服务
恢复 M10.3 前数据库备份
回退 M10.3 代码
重新 build
重启服务
复查历史便签和附件
```

回退后确认：

1. `admin` 可登录。
2. Note 数量恢复。
3. Attachment 数量恢复。
4. 旧图片可打开。
5. 账号菜单恢复 M10.2 状态。
