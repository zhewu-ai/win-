# PinNote M10.12：跨设备刷新与同步可见性

日期：2026-08-08

## 1. 结论摘要

针对「同一账号两台电脑数据不互通、无刷新入口、「已同步」误导、静置抽搐」四个反馈，本轮实现 SPEC_M10_12：

1. **手动刷新入口（P0）**：编辑区工具栏 SaveStatus 旁 + 侧边栏搜索区各加一个圆形刷新按钮，点击进入「刷新中」旋转/禁用态，失败轻提示不清空内容，320px 窄窗口不挤压。
2. **刷新前保护本机未保存输入（P0）**：刷新前先 flush debounce pending + 重试 `lastFailedPayload`；仍失败则停止刷新并提示「本机有未保存内容且保存失败，请先重试保存」。保留 `mirrorNote()` 不覆盖非 synced 本地队列的保护。
3. **同一便签远端版本更新后编辑器要能更新（P0）**：`NoteEditor` 不再只按 `note.id` 重置，同时监听 `note.updatedAt`；仅在安全态（saved、无 pending、无失败载荷、无恢复草稿）下应用远端新版，不安全时绝不静默覆盖。
4. **「已同步」文案澄清（P0）**：`SaveStatus` 本机保存态默认文案 `已同步` → `已保存`，避免被误读为「多端最新」。
5. **抽搐排查（P0）**：定位到 `useSyncStatus` 每 30s 无条件 `runSync()`，即使无 pending 也翻转 `isSyncing`，带动 OfflineBar「正在同步…」闪现；改为仅在有 pending 时才触发，**消除最可能来源**。ResizeObserver / SaveStatus 宽度两类候选仍在，桌面壳 5 分钟静置观察后确认是否闭环（审计 P2）。

P1「低频自动拉取」按 SPEC 明确**推迟到下一阶段**，本轮只上手动刷新。

## 3. 关键实现

### 3.1 刷新流程（page.tsx `handleRefresh`）

1. 若 `refreshing` 已有请求在途 → 忽略本次（防重复）。
2. 调 `editorRefreshRef.current()`（编辑器 `flushAndEnsureSaved`）：
   - 先清掉 debounce timer，立即 flush 当前 pending updates 到服务器；
   - 若存在 `lastFailedPayloadRef`，先重试保存；
   - 重试后仍有失败载荷 → 返回 `false`，刷新中止，toast「本机有未保存内容且保存失败，请先重试保存」。
3. `fetchNotes(searchQuery, { silent: true })`：
   - `silent` 只置 `refreshing`（不置 `loading`，不闪骨架屏）；
   - 失败返回 `null` 且**不替换列表**（本次请求不落库，交由调用方提示）；
   - **成功时先 `mergeLocalPending(fetched, archived)` 再 `setNotes`**：把本地 pendingCreate / pendingUpdate / syncError / pendingDelete 合并进服务器快照后再展示，保证服务器旧快照**在任何路径下都不覆盖本机未同步内容**（`mirrorNote` 只保护 IndexedDB，这里补内存列表层——审计 P1）；
   - 返回 `undefined` 表示已有请求在途，忽略。
4. 刷新成功后若当前选中便签已被其他设备删除（且无搜索词）→ 退出编辑态，不继续编辑幽灵数据。
5. toast「已刷新」2s 自动消失。

### 3.2 同便签远端版本应用（NoteEditor）

- 重置 effect 依赖改为 `[note?.id, note?.updatedAt]`：ID 变了（切换便签）必重置；ID 没变但 `updatedAt` 变了（远端新版）仅当 `!localDirty` 才应用。
- `localDirty = saveStatus !== "saved" || pendingUpdates 非空 || lastFailedPayload 存在 || 本地恢复草稿中`——任一为真就不覆盖，等用户刷新/保存动作。
- **PATCH 5xx 场景的完整保护**：`saveNoteUpdate` 对 5xx 不抛错、返回本地合并记录（`saveStatus="saved"`、无失败载荷），单靠 `localDirty` 拦不住刷新后旧快照回写编辑器。内存层由 `mergeLocalPending` 兜底——合并后 `selectedNote` 仍是本地 pending 新版（`updatedAt` 与编辑器一致），`remoteVersionChanged` 恒为 false，编辑器不会重置（审计 P1 的完整闭环）。
- 远端应用成功时按 `updatedAt` 变化范围清理本地草稿，避免旧草稿残留。

### 3.3 抽搐修复（useSyncStatus）

原代码每 30s 无条件 `runSync()`，即使 pendingCount=0 也会把 `isSyncing` 置 true→false 一轮，OfflineBar 的「正在同步…」随之闪现。改为先查 pending/syncError 计数，>0 才 `runSync()`。离线时直接跳过。

## 4. 验收结果

### 4.1 本地（dev + 双会话）

- **基础手动刷新**：原始 `fetch()` 模拟设备 B 新建便签（服务器侧创建，不经本地 React state），A 会话点刷新 → 列表出现 B 新建便签。通过。
- **同便签内容刷新**：设备 B PATCH 更新同一条便签 title/content → A 会话点刷新 → 编辑器显示远端新版。通过。
- **不覆盖本机未保存内容**：输入中（debounce pending）点刷新 → 先 flush，输入内容保留且已到服务器；人为制造保存失败 → 刷新中止并 toast 提示，输入不被覆盖。通过。
- **PATCH 500 + GET 200 旧数据（审计 P1 补测）**：dev 浏览器挂 fetch 拦截使 `PATCH /api/notes/:id` 一律返回 500 → 编辑正文触发 PATCH → 500 转本地 `pendingUpdate`（编辑器 `saveStatus="saved"`，SaveStatus 显示「等待同步」）→ 恢复 fetch 后点击刷新（GET 200 返回旧内容）→ **编辑器与侧边栏列表均保留本地新内容，未被旧快照覆盖**。通过。离线新建（`pendingCreate`）场景同步验证：新建 POST 500 → 转本地 `pendingCreate` → 刷新后便签仍留在列表（修复前会从列表消失）。通过。
- **新便签与搜索状态**：带搜索词刷新只刷新当前搜索结果；清空搜索后刷新完整列表；其他设备删除当前选中便签 → 刷新后退出编辑态。通过。
- **桌面壳**：双栏/单栏/极简三种布局下刷新按钮均可见，320px 不挤压标题、SaveStatus、更多菜单（before/after 检查通过）。
- **抽搐**：已消除 30s `runSync` 空转这一**最可能来源**（修复后 30s 静置代码层面不再翻转 `isSyncing`）；桌面壳 5 分钟静置录屏仍需用户侧观察确认，暂不宣称为完整闭环（审计 P2）。

## 7. 风险与后续建议

1. **P1 低频自动拉取（60-120s）未做**：按 SPEC 明确推迟。下一阶段需满足「页面可见、在线、无 pending、编辑器非 saving/error 时才 pull，且必须 silent 不闪骨架屏、不抢焦点、不改滚动位置」；正在编辑同一条且有远端新版时只显示「有远端更新，点击刷新」轻提示，不自动覆盖。
2. **抽搐剩余候选（状态：待用户确认闭环）**：本轮消除了 30s `runSync` 空转这一最可能来源（代码层已确认不再空转），但 `ResizeObserver` 的 `toolbarMode` 切换与 SaveStatus 文案宽度两类候选未在本轮触碰；请用户在桌面壳静置 5 分钟观察，若仍有横跳再作为独立缺陷定位——在桌面壳录屏确认前，本轮结论不宣称为完整修复。
3. **「已同步」→「已保存」为弱化方案**：保留本机保存状态 + 刷新按钮独立承担拉取动作，符合 SPEC §三/§四「不建议直接把已同步整体替换」的取向；如产品要求更明确区分「远端最新」，可再叠加「刚刚刷新 HH:mm」角标。
4. **生产构建约束**：共享 VM 上必须 `npm run build -- --webpack`，Turbopack 会 OOM（上次事故教训）；preview 服务已在 Next 升级评估交付时清理（Caddy 站点 + systemd 单元移除，备份 `~/backups/Caddyfile-before-preview-clean-20260808185501`），本次构建后未重建，如后续需要独立预演环境需重新搭建。
