# M8.5 稳定感复测结论：仍未通过

日期：2026-08-06

复测环境：

- 本地代码：`64b2309`
- 本地服务：`http://localhost:3001`
- 浏览器视口测试：900 / 700 / 600 / 560 / 520 / 500 / 360 / 260

结论：

M8.5 有部分改善，但用户反馈“没有很多改善”是合理的。当前仍存在明显稳定感问题，尤其是 520-700px 之间的双栏布局和工具栏断点不匹配。

## 1. 已改善项

### 1.1 900px 宽度表现基本正常

复测数据：

- 侧边栏宽度：350px
- 编辑区宽度：550px
- 编辑器工具栏高度：56px
- 工具栏无横向/纵向 overflow
- 便签卡片宽度在高度变化时保持 325px

判断：

900px 以上宽度下，M8.5 改动基本有效。

### 1.2 滚动条 gutter 的代码存在

复测看到主要滚动容器已有：

```css
scrollbar-gutter: stable
```

浏览器端数据中，900px 高度 700 与高度 420 时，左侧卡片宽度均为 325px。

判断：

滚动条导致卡片宽度跳动的问题在 Web 端有改善。Windows WebView2 仍需实机确认。

## 2. 未通过问题

### M8.5-F01：700px 宽度下“便签/待办”文字仍竖排，工具栏高度被撑高

严重级别：P0

复测数据：

700px 视口下：

```text
侧边栏：350px
编辑器工具栏宽度：约 384px
工具栏高度：65px
模式按钮高度：48px
模式文字 rect：18px × 36px
```

现象：

- “便签”两个字仍然竖向排列。
- 工具栏高度从预期 56px 被撑到 65px。
- 这正是用户感受到“不稳定、不成熟”的主要来源之一。

根因判断：

- 当前用 Tailwind `sm` 控制模式文字显示。
- `sm` 是按整个 viewport 宽度 640px 判断。
- 但 700px 时左侧侧边栏占 350px，右侧编辑区只剩约 350-380px。
- 结果：viewport 大于 640，所以文字显示；但编辑器实际容器太窄，所以文字被挤成竖排。

结论：

不能用 viewport 断点决定编辑器工具栏是否显示文字。应该按编辑器容器宽度，或直接在双栏窄宽度下统一图标化。

验收要求：

1. 700px 总窗口宽度下，工具栏仍必须 56px 单行。
2. “便签/待办”文字不能竖排。
3. 如果右侧编辑区不足 520px，模式切换应直接显示图标，不显示文字。

### M8.5-F02：600/560/520px 从宽屏收窄时仍保持双栏，但右侧内容已经被裁切

严重级别：P0

复测数据：

从宽窗口一路缩窄时：

```text
600px：侧边栏仍显示 350px，右侧工具栏 right≈671px，超出 600px 视口
560px：侧边栏仍显示 350px，右侧工具栏 right≈668px，超出 560px 视口
520px：侧边栏仍显示 350px，右侧工具栏 right≈665px，超出 520px 视口
500px：进入单栏，侧边栏隐藏
```

现象：

- 技术部把自动收起阈值从旧的 768px 改到了 520px。
- 但 520-700px 之间，双栏仍然存在。
- 左侧固定 350px 后，右侧编辑区已经不够用。
- 用户从宽屏往窄屏拖动时，会看到右侧被挤压/裁切，而不是稳定收缩。

根因判断：

- `useNarrowMode` 当前逻辑是：

```text
小于 520px 才进入单栏
大于 580px 才退出单栏
```

- 这只解决了“768px 太早收起”的问题。
- 但没有解决“侧边栏固定 350px + 编辑区最小可用宽度”之间的空间冲突。

关键问题：

560px 的行为是状态相关的：

- 如果先缩到 500px，再拉到 560px，会保持单栏。
- 如果从 900px 直接缩到 560px，会保持双栏并裁切。

这种状态相关行为对用户来说仍然不稳定。

产品要求：

1. 双栏模式必须保证左右两栏都有可用空间。
2. 如果总宽度不足以容纳 `侧边栏 + 编辑器最小稳定宽度`，应进入单栏或自动压缩侧边栏。
3. 不能在 520-700px 区间保持一个“看似双栏但右侧被裁掉”的布局。

建议方案：

方案 A：提高进入单栏阈值。

```text
进入单栏：< 680px 或 < 700px
退出双栏：> 760px
```

方案 B：侧边栏在 520-760px 区间自动缩窄。

```text
侧边栏从 350px 缩到 260px
编辑区保留最小稳定宽度
```

方案 C：双栏使用 CSS grid/flex minmax。

```css
grid-template-columns: minmax(260px, 350px) minmax(360px, 1fr)
```

不足时进入单栏，不允许裁切。

建议优先：

采用方案 C，其次方案 A。不要继续只靠 520/580 迟滞。

### M8.5-F03：工具栏“单一 640px 断点”不等于稳定，因为右侧编辑区宽度不是 viewport 宽度

严重级别：P1

现象：

- 技术部文档说“断点合并为单一 640px”。
- 但 700px 总窗口时，右侧编辑区只有约 384px，仍显示文字和完整色球。

问题：

断点看的是 viewport，不是编辑器容器。只要侧边栏存在，编辑器实际宽度远小于 viewport。

产品要求：

- 编辑器工具栏应按自身容器宽度响应。
- 如果暂时不用 container query，则应按布局状态判断：
  - 双栏且总宽度小于 760px：工具栏图标化。
  - 单栏宽度小于 640px：工具栏图标化。

建议技术方案：

1. 使用 CSS container queries：

```css
@container editor (max-width: 520px) { ... }
```

2. 或用 ResizeObserver 测量编辑器工具栏容器宽度。
3. 不建议继续用全局 `sm` 判断编辑器内部工具栏。

验收要求：

1. 700px 双栏时，模式按钮不显示文字。
2. 700px 双栏时，色球不全部展开，进入颜色按钮。
3. 工具栏高度保持 56px。

### M8.5-F04：验收指引四档不够，漏掉了最容易出问题的 700px 双栏区间

严重级别：P1

技术部验收指引测试了：

但实际问题出在：

原因：

- 这些宽度仍可能处于双栏。
- 但编辑器实际宽度已经非常窄。
- 正好触发 viewport 断点和容器宽度不一致的问题。

验收标准需要补充：

必须增加以下宽度：

```text

560px

```

并且必须从宽到窄、从窄到宽各录一次，因为迟滞逻辑有状态差异。

## 3. 对技术部交付总结的判断

技术部说：

> 1280→700px 缩放保持双栏，修复旧 md:768 自动收起。

这句话本身成立，但产品体验不一定通过。

原因：

- 700px 保持双栏确实避免了侧边栏突然消失。
- 但 700px 双栏下右侧工具栏已经不稳定，文字竖排、工具栏变高。

也就是说：

```text
旧问题：侧边栏太早消失。
新问题：侧边栏保留太久，右侧空间不足。
```

M8.5 的目标不是“侧边栏尽量不消失”，而是“横向缩放稳定”。目前这个目标仍未完全达成。

## 4. 建议下一轮修复方向

### 4.1 用编辑器容器宽度，而不是 viewport 宽度

优先修工具栏：

- 模式文字
- 色球
- 保存状态
- 更多按钮

判断依据改成编辑区实际宽度。

### 4.2 重新定义双栏最小可用宽度

不要让双栏硬撑到 520px。

建议：

```text
侧边栏最小 260px
编辑区最小 360px
双栏最低约 620px，低于则单栏
```

如果侧边栏仍固定 350px：

```text
双栏最低约 720px，低于则单栏
```

## 5. 本轮复测结论

不通过。

原因：

1. 700px 双栏下模式文字仍竖排。
2. 700px 工具栏高度从 56px 增加到 65px。
3. 600/560/520px 从宽屏收窄时仍保持双栏，但右侧区域被裁切。
4. 现有验收四档漏掉了真正问题区间。
