# PinNote M10.11 用户活跃度观察：最近活跃时间与操作统计

日期：2026-08-08

## 1. 背景

PinNote 已进入真实内测阶段。管理员目前能看到用户列表、反馈、公告阅读情况，但仍缺少一个基础判断：

> 用户到底有没有在用？最近什么时候用过？大概做了哪些操作？

本轮目标不是做复杂数据分析平台，也不是做实时在线状态，而是补一个轻量、低负担、对内测运营有帮助的“用户活跃度观察”能力。

## 2. 产品原则

### 2.1 不做实时在线

本轮明确不做“在线 / 离线绿点”的实时状态。

原因：

1. 在线状态定义不稳定：用户开着页面不动、浏览器挂后台、电脑睡眠、网络断开，都可能造成误判。
2. 实时在线容易让管理员误以为是聊天软件级状态，但 PinNote 当前没有这个必要。
3. 实时在线通常需要心跳或 WebSocket，会增加实现和服务器负担。

### 2.2 不做心跳

本轮不新增定时 heartbeat：

- 不每 30 秒 / 60 秒主动打一次请求。
- 不因为页面停留、鼠标移动、滚动页面单独请求服务端。
- 不为“在线状态”制造额外流量。

### 2.3 只记录有意义操作

活跃度只在用户已经发起业务请求时顺手记录。

也就是说：用户确实做了某个产品动作，服务端本来就要处理请求，此时顺便更新活跃记录。

这样既能反映真实使用，又不会明显增加服务器负担。

## 3. 本轮目标

M10.11 做三件事：

1. **记录最近活跃时间**：管理员能看到用户上一次有意义操作发生在什么时候。
2. **记录最近操作类型**：管理员能看到用户上一次大概做了什么，例如“编辑便签”“提交反馈”。
3. **显示操作次数统计**：管理员能看到用户今日操作次数、近 7 天操作次数。

## 4. 本轮不做

明确不做：

1. 不做实时在线 / 离线状态。
2. 不做心跳接口。
3. 不记录鼠标移动、页面滚动、页面停留时长。
4. 不记录便签正文、标题、附件内容。
5. 不做复杂漏斗分析、留存分析、图表大屏。
6. 不做埋点平台。
7. 不对用户展示自己的活跃记录。

## 5. 什么算“有意义操作”

建议记录以下动作：

| action | 中文显示 | 触发场景 |
|---|---|---|
| `login` | 登录 | 用户登录成功 |
| `create_note` | 新建便签 | 创建普通便签或待办便签 |
| `edit_note` | 编辑便签 | 修改标题、正文、颜色、置顶、模式、待办内容 |
| `check_todo` | 勾选待办 | 勾选或取消勾选待办项 |
| `delete_note` | 删除便签 | 删除到回收站 |
| `restore_note` | 恢复便签 | 从回收站恢复 |
| `archive_note` | 归档便签 | 归档 |
| `unarchive_note` | 取消归档 | 从归档恢复到列表 |
| `permanent_delete_note` | 永久删除 | 单条或批量永久删除 |
| `upload_attachment` | 上传图片 | 上传图片附件 |
| `delete_attachment` | 删除图片 | 删除图片附件 |
| `submit_feedback` | 提交反馈 | 用户提交反馈工单 |
| `read_announcement` | 查看公告 | 用户关闭或确认公告弹窗 |
| `change_avatar` | 修改头像 | 上传或移除头像 |
| `change_password` | 修改密码 | 用户自行修改密码 |

技术部可以按现有接口实际情况合并部分动作，但管理员后台显示必须是用户能理解的中文文案。

## 6. 数据结构建议

### 6.1 User 表新增字段

```prisma
model User {
  lastActiveAt     DateTime?
  lastActiveAction String?
}
```

用途：

- 管理员用户列表快速展示“最近活跃”和“最近操作”。
- 避免每次列表都只依赖日志表聚合。

### 6.2 新增 UserActivityLog 表

```prisma
model UserActivityLog {
  id        String   @id @default(cuid())
  userId    String
  action    String
  metadata  String?
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id])

  @@index([userId, createdAt])
  @@index([createdAt])
  @@index([action])
}
```

用途：

- 统计今日操作次数。
- 统计近 7 天操作次数。
- 后续可扩展最近 20 条操作、活跃趋势。

### 6.3 metadata 边界

`metadata` 可选，且本轮建议尽量少用。

允许记录：

- `noteMode: "text" | "checklist"`
- `count: 3`
- `source: "bulk"`

禁止记录：

- 便签标题
- 便签正文
- 待办文字
- 附件文件名中可能含隐私的原始名称
- 用户输入的反馈内容

## 7. 服务端实现建议

新增公共方法，例如：

```ts
recordUserActivity(userId, action, metadata?)
```

每次记录时做两件事：

1. 更新 `User.lastActiveAt` 和 `User.lastActiveAction`。
2. 插入一条 `UserActivityLog`。

注意：

1. 该方法不能影响主业务接口成功率。
2. 如果活跃记录失败，可以记录服务端日志，但不应导致新建便签、编辑便签、提交反馈等主操作失败。
3. 不要在 GET 列表、GET 便签详情这类纯查看接口中大量记录，避免刷数据。
4. 登录成功可以记录，因为这是明确的用户行为。
5. 公告关闭 / 确认已读可以记录，因为它本来会写已读记录。

## 8. 管理员后台 UI

位置：管理员用户管理页。

每个用户增加以下信息：

1. 最近活跃时间
2. 最近操作
3. 今日操作次数
4. 近 7 天操作次数

展示示例：

```text
最近活跃：今天 16:32
最近操作：编辑便签
今日操作：12 次
近 7 天：38 次
```

无记录时显示：

```text
最近活跃：暂无
最近操作：暂无
今日操作：0 次
近 7 天：0 次
```

### 8.1 时间显示

建议显示口径：

- 今天：`今天 HH:mm`
- 昨天：`昨天 HH:mm`
- 更早：`YYYY-MM-DD HH:mm`
- 从未活跃：`暂无`

### 8.2 视觉要求

1. 不要做很显眼的在线绿点。
2. 信息应弱化展示，作为管理员辅助判断。
3. 320px 宽度下不能横向溢出。
4. 用户列表卡片不能因为新增字段变得过高或拥挤；必要时可把活跃信息放在第二行或折叠小字区域。

## 9. 管理员统计接口建议

现有 `GET /api/admin/users` 可以直接返回：

```json
{
  "users": [
    {
      "id": "xxx",
      "email": "user@example.com",
      "lastActiveAt": "2026-08-08T08:32:00.000Z",
      "lastActiveAction": "edit_note",
      "activityCounts": {
        "today": 12,
        "last7Days": 38
      }
    }
  ]
}
```

统计口径：

- 今日：按服务器当前自然日，建议以部署服务器时区为准。
- 近 7 天：`createdAt >= now - 7 days`。

如果担心用户量增加后列表接口聚合变慢，可以先用简单查询实现，后续再做缓存或每日汇总。本阶段内测用户量小，不需要提前复杂化。

## 10. 隐私与安全边界

本功能只用于内测运营观察，不用于窥探内容。

必须遵守：

1. 不记录便签内容。
2. 不记录待办内容。
3. 不记录附件内容。
4. 不记录反馈正文。
5. 不记录密码、邀请码明文、临时密码。
6. 管理员只能看到动作类型和时间，不看具体内容。

建议管理员后台用词：

> 最近操作：编辑便签

不要写成：

> 编辑了《某某项目报价》这条便签

## 11. 数据保留策略

本轮可以先不做自动清理，但建议技术部预留：

- `UserActivityLog` 只保留最近 90 天。
- 后续可加系统任务清理 90 天前日志。

如果本轮顺手做清理任务，必须保证：

1. 只删除 `UserActivityLog` 旧记录。
2. 不影响 User、Note、Attachment、FeedbackTicket。
3. 清理失败不影响主服务。

## 12. 验收用例

### 12.1 登录记录

1. 新用户登录成功。
2. 管理员打开用户列表。
3. 预期：
   - 最近活跃时间更新。
   - 最近操作显示“登录”。
   - 今日操作次数至少 +1。

### 12.2 编辑便签记录

1. 用户新建便签。
2. 修改标题或正文。
3. 管理员刷新用户列表。
4. 预期：
   - 最近操作显示“编辑便签”或“新建便签”。
   - 今日操作次数增加。
   - 不展示便签标题和正文。

### 12.3 待办记录

1. 用户打开待办便签。
2. 勾选一条待办。
3. 预期：
   - 最近操作显示“勾选待办”或合并显示“编辑便签”。
   - 不展示待办文字。

### 12.4 反馈记录

1. 用户提交反馈。
2. 管理员用户列表显示最近操作“提交反馈”。
3. 管理员反馈页仍可正常查看反馈内容。
4. 活跃日志本身不保存反馈正文。

### 12.5 不记录无意义操作

1. 用户打开页面后不操作，只滚动页面。
2. 不应因为滚动单独产生活跃日志。
3. 不应因为页面停留产生定时心跳日志。

### 12.6 权限保护

1. 普通用户不能访问活跃统计接口。
2. 未登录访问返回 401。
3. 非管理员访问管理员用户列表仍返回 403。

### 12.7 生产数据安全

1. 部署前备份生产数据库。
2. 迁移后旧用户 `lastActiveAt` 可为空。
3. 旧用户列表正常显示。
4. 旧便签、附件、反馈、公告数据不变。

技术部交付时需要提供：

1. 改动文件清单。
2. schema 变更说明。
3. 本地 `npx tsc --noEmit` 结果。
4. 本地 `npm run build` 结果。
5. 管理员用户列表截图或文字验收记录。
6. 登录、新建、编辑、反馈、公告已读的活跃记录实测。
7. 普通用户无法访问管理员统计的权限验证。
8. 生产部署前备份路径。
9. 生产部署后数据库表/字段确认。

## 14. 优先级

建议优先级：

1. P0：User 新增最近活跃字段，管理员列表展示最近活跃时间和最近操作。
2. P0：记录登录、新建/编辑便签、提交反馈。
3. P1：新增 UserActivityLog，统计今日和近 7 天操作次数。
4. P1：补齐归档、回收站、附件、公告已读、头像、密码等动作。
5. P2：90 天日志清理任务。

如果时间紧，至少先完成 P0。P0 已经可以解决“我不知道用户有没有在用”的核心问题。
